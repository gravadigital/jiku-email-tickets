# S-018: Permiso de subida - files.request-upload

**Status:** Ready
**Created:** 2026-08-31
**Source:** REQ-004

## Historia de Usuario

**Como** conector que ya sabe qué adjuntos de un mail pasaron la política local, el dedup y el tope,
**quiero** pedirle a `core` el permiso de subida para cada uno con `files.request-upload` y recibir un
`fileId` y una URL prefirmada, o un aviso de rechazo si `core` lo rechaza,
**para** obtener la autorización de escritura al storage sin que el conector decida nunca la clave, el
bucket ni la titularidad del archivo.

## Criterios de Aceptación

### CA-1: El payload de `files.request-upload` lleva exactamente cuatro campos

**DADO** un adjunto aceptado dentro del tope, con su `fileName` (generado o declarado), `mimeType`
(declarado o `application/octet-stream`), tamaño real y checksum ya calculados por S-017
**CUANDO** se publica el permiso de subida
**ENTONCES** el payload lleva **exactamente** `fileName`, `mimeType`, `fileSize` (≥ 1) y `checksum`
**Y** **no lleva** `uploader` ni `actor`: informar el uploader sería ruido, porque `core` **ignora**
cualquier identidad que el conector declare.
*(REQ-004 RF-14, RF-16; criterio 36; ADR-005)*

### CA-2: Se reutiliza `client.command()` sin ninguna regla nueva

**DADO** el permiso de subida
**CUANDO** se revisa el código de publicación
**ENTONCES** usa **el mismo `client.command('files.request-upload', payload)`** que ya usa
`requirements.new` desde S-005
**Y** el conector **no arma el subject ni parsea el envelope**: el SDK arma
`{instance}.{sub}.jiku-commands.v1.files.request-upload`, cubierto por el mismo comodín
`jiku-commands.v1.>` que ya autoriza el rol `internal-app`.
*(REQ-004 RF-14; ADR-002)*

### CA-3: Un éxito devuelve `fileId` y `uploadUrl` para el siguiente paso

**DADO** que `core` acepta el archivo
**CUANDO** responde con éxito
**ENTONCES** la respuesta se valida contra un schema propio (`fileUploadReplySchema` o equivalente) que
exige `fileId` y `uploadUrl` usables
**Y** el resultado se devuelve a quien orquesta (S-021), listo para que S-019 haga el `PUT`.
*(REQ-004 RF-14 — response de éxito)*

### CA-4: Un `failure` de `core` produce aviso de rechazo, no aviso de fallo

**DADO** que `files.request-upload` responde `failure` con `file_type_not_allowed` o `file_too_large`
para un archivo que el filtro local **sí** aceptó
**CUANDO** se procesa esa respuesta
**ENTONCES** el archivo se saltea con **aviso de rechazo** (la misma clase que un rechazo local, no la
de un fallo de subida)
**Y** el procesamiento **continúa** con el próximo adjunto, sin reintentar.
*(REQ-004 RF-17; criterio 22)*

### CA-5: El rechazo de `core` se loguea `warn` con el código, distinto del rechazo local en `info`

**DADO** el mismo `failure` de `core` del CA-4
**CUANDO** se loguea
**ENTONCES** la línea es de nivel **`warn`**, incluye el código (`file_type_not_allowed` /
`file_too_large`), el nombre y el MIME del archivo
**Y** esto es **distinto** del rechazo puramente local de S-017, que se loguea `info`: es el único
síntoma de que la política local está desalineada con la de `core`.
*(REQ-004 RF-40; criterio 40; ADR-003 §Riesgos)*

### CA-6: Las 9 ramas de diagnóstico del SDK se reutilizan sin ninguna rama nueva

**DADO** un rechazo del bus por subject, de `core` por rol, o un timeout del comando
**CUANDO** se traduce el error
**ENTONCES** se usa **la misma función `diagnosePublishFailure()`** ya existente desde S-005, **sin
modificarla**: las 9 ramas ya cubren los tres sistemas para cualquier comando, no sólo para
`requirements.new`.
*(REQ-004 §Comandos del Bus — files.request-upload; ADR-006)*

### CA-7: El timeout del comando es el default del SDK, distinto del timeout del `PUT`

**DADO** la publicación de `files.request-upload`
**CUANDO** se revisa su configuración de timeout
**ENTONCES** usa el **default del SDK (15000 ms)**, el mismo de `requirements.new`, **sin pasar el
tercer argumento `options`**
**Y** este timeout es explícitamente **distinto** del timeout de 30000 ms del `PUT` posterior, que es
una operación HTTP separada y la agrega S-019.
*(REQ-004 §Comandos del Bus — Timeout)*

### CA-8: Un fallo del comando distinto de `failure` de negocio produce aviso de fallo de subida

**DADO** que `files.request-upload` falla por una de las 9 ramas de diagnóstico del SDK (timeout del
bus, `core` caído, error de forma) — no un `failure` de negocio con código
**CUANDO** se procesa ese fallo
**ENTONCES** el archivo se saltea con **aviso de fallo de subida** (no de rechazo), se loguea `error`, y
el procesamiento continúa sin reintentar.
*(REQ-004 §Manejo de Errores — Tabla Completa, fila `files.request-upload` → 9 ramas)*

### CA-9: La función es invocable por archivo, en serie, y no orquesta el tick completo

**DADO** el módulo de esta story
**CUANDO** se revisa su interfaz
**ENTONCES** expone una función que recibe **un** adjunto aceptado y devuelve `{ fileId, uploadUrl }` o
un resultado de rechazo/fallo — no itera sobre la lista completa de adjuntos ni decide el orden: esa
orquesta la hace S-021.
*(REQ-004 §Story Split Propuesto — Story 2)*

### Cambios de API

#### Comando Nuevo para este Conector: `files.request-upload`

**Subject:** `{instance}.{sub}.jiku-commands.v1.files.request-upload` — ya cubierto por el comodín
existente, sin cambios de permisos.

**Payload:**

| Campo | Tipo | Origen | Nota |
|---|---|---|---|
| `fileName` | string, req | de S-017 (declarado o generado) | Mismo nombre que evaluó la política local |
| `mimeType` | string, req | de S-017 (declarado o `application/octet-stream`) | Declarado, no verificado |
| `fileSize` | int, req, ≥ 1 | tamaño real del `Buffer` | Nunca 0: ya rechazado por S-017 |
| `checksum` | string sha256, req | de S-017 | Calculado por el conector |

**Response (éxito):** `{ fileId, uploadUrl }`.

**Response (`failure`):** `file_type_not_allowed` / `file_too_large` — tratado como aviso de rechazo,
no de fallo.

**Ref:** RF-14 a RF-17; criterios 5-10, 22-23; ADR-003, ADR-005, ADR-006

### Cambios de Base de Datos

Ninguno del conector. `core` hace `INSERT` en `files` con `byteStatus: 'pending'`, construye la clave
de storage y firma la URL — el conector no elige ninguno de esos atributos y no los persiste.

### Flujo de Interacción

#### Escenario: permiso concedido

**Trigger:** un adjunto quedó en `aceptados` tras S-017.

**Flujo:**

1. **[`adjuntos`/`publicacion`]** `client.command('files.request-upload', { fileName, mimeType,
   fileSize, checksum })`
2. **[Bus → `core`]** valida doble lista blanca contra `system_settings` en caliente, `INSERT` en
   `files`, firma la URL de `PutObject`.
3. **[respuesta]** éxito → `{ fileId, uploadUrl }`, listo para S-019.

#### Escenario: `failure` de negocio

1. `core` responde `failure` con `file_type_not_allowed` o `file_too_large`.
2. Se anota aviso de rechazo (mismo bloque que los rechazos locales) y se loguea `warn` con el código.
3. Se continúa con el próximo adjunto sin reintentar.

**Outcome:** por cada adjunto aceptado, un permiso concedido o un aviso de rechazo — nunca una
excepción no controlada.

**Manejo de errores:** ver tabla completa en REQ-004 §Manejo de Errores — filas `files.request-upload`.

### Flujos Afectados

Ninguno todavía. La integración al flujo `ruteo-y-alta-del-requisito` la hace **S-021**.

### Consideraciones Técnicas

**Seguridad:**
- Ningún dato sensible nuevo en el payload: `checksum` y metadatos, sin contenido de archivo.

**Performance:**
- Un comando del bus por adjunto, en serie (la orquestación de S-021 decide el orden); timeout 15000 ms
  por intento, sin reintento.

**Dependencias:**
- Depende de S-017 para recibir adjuntos ya particionados, deduplicados y dentro del tope.
- Reutiliza `client.command()` y `diagnosePublishFailure()` de S-005, sin modificarlos.

## Dependencias

**Habilita:**
- S-019: Subida del byte - cliente del `PUT` (consume `uploadUrl`)
