# S-004: Identidad y conexión única al bus

**Status:** Ready
**Created:** 2026-08-27
**Source:** REQ-001

## Historia de Usuario

**Como** operador que despliega el conector (U-02),
**quiero** que el worker construya su identidad desde la key del machine user, abra **exactamente
una** conexión al bus y la conserve por toda la vida del proceso, y que si la conexión falla al
arrancar el worker **no arranque** diciendo cuál sistema lo rechazó,
**para** saber si las precondiciones de despliegue —machine user, rol `internal-app`, key, creds,
red— están bien hechas, en vez de descubrirlo tarde con un síntoma opaco.

## Criterios de Aceptación

### CA-1: Identidad construida desde la key, con una sola conexión

**DADO** un machine user creado en Zitadel con Access Token Type = JWT y el rol `internal-app`
asignado, su key JSON montada, el creds del sentinel alcanzable y `JIKU_PROJECT_ID` configurado
**CUANDO** arranca el worker
**ENTONCES** construye su identidad con `ServiceUser.fromKeyFile()`
**Y** abre **una sola** conexión al bus
**Y** loguea el arranque exitoso a stdout **sin exponer ninguna credencial**.
*(REQ-001 AC-1, RF-9, RF-10)*

### CA-2: El `user-id` del subject sale de la key, nunca del entorno

**DADO** la identidad construida
**CUANDO** se revisa de dónde sale el `user-id` que va en el subject
**ENTONCES** sale de `auth.userId`, derivado de la key
**Y** **no existe** ninguna variable de entorno que lo declare ni ningún camino de código que lo
tome del entorno.
*(REQ-001 RF-9, NFR-S03, invariante 17)*

### CA-3: Una sola conexión por proceso, conservada

**DADO** el código del adaptador del bus
**CUANDO** se busca la invocación de `connect()`
**ENTONCES** aparece **una sola vez**, en el arranque
**Y** el cliente resultante se conserva por toda la vida del proceso y se reusa
**Y** no hay ningún camino que abra una conexión por operación.
*(REQ-001 RF-10, NFR-P05, C-14)*

### CA-4: La key ilegible corta el arranque sin volcar su contenido

**DADO** un `JIKU_KEY_FILE` que apunta a un archivo inexistente o a un JSON mal formado
**CUANDO** arranca el worker
**ENTONCES** el worker **no arranca**
**Y** informa que la key no se pudo cargar
**Y** **no vuelca su contenido al log**.
*(REQ-001 AC-10)*

### CA-5: El rechazo del bus por subject es un fallo de arranque, y el log lo distingue

**DADO** un machine user **sin** el rol `internal-app` asignado en el project de gestión
**CUANDO** el worker intenta conectar al arrancar
**ENTONCES** la conexión se rechaza con `Authorization Violation`
**Y** el worker **no arranca** (exit ≠ 0)
**Y** el log dice que el rechazo es **del bus por subject** — un problema de **Zitadel**, no del
payload — junto con la clase de error del SDK y su `hint()`.
*(REQ-001 AC-11, RF-11)*

### CA-6: El fallo del refresh del token no mata el proceso

**DADO** un worker arrancado y conectado
**CUANDO** el refresh del token falla en background
**ENTONCES** se loguea como `error`
**Y** **el worker no muere**: el token vigente sigue sirviendo y lo que se rompe es el próximo
reconnect.
*(REQ-001 AC-17, RF-12, C-15, NFR-R04)*

### CA-7: El refresh exitoso no abre una segunda conexión

**DADO** un worker corriendo desde hace más tiempo que la vida útil del token
**CUANDO** el SDK refresca el token en background
**ENTONCES** el worker sigue corriendo con **la misma** conexión, sin abrir una segunda.
*(REQ-001 AC-4)*

### CA-8: El token nunca se persiste ni se loguea

**DADO** el worker arrancado y conectado
**CUANDO** se inspeccionan stdout y el disco
**ENTONCES** el access token **no aparece** en ninguna línea de log ni en ningún archivo: vive sólo
en memoria.
*(REQ-001 §Seguridad, NFR-S02, ADR-005)*

### CA-9: El conector no crea ni pide su fila en `users`

**DADO** el código completo del conector
**CUANDO** se busca cualquier intento de crear, insertar o solicitar su fila en `users` de Jiku
**ENTONCES** **no existe ninguno**: la fila la crea Jiku sola al consumir el evento del auth-callout
en la primera autenticación, con `identity_type: service` y `email` en `NULL`.
*(REQ-001 AC-3, ADR-005, G-03)*

### CA-10: Un test por clase de error de conexión manejada

**DADO** la suite de tests
**CUANDO** se ejecuta
**ENTONCES** cada clase de error del SDK que esta story maneja en producción tiene su test
(rechazo de conexión, key ilegible, fallo del refresh)
**Y** los tests usan `Client.fromConnection()` contra el NATS de Testcontainers, **sabiendo que eso
saltea el handshake de auth** y por lo tanto no prueba nada sobre Zitadel, el rol ni el prefijo de
inbox.
*(convención de testing §Gotchas; REQ-001 §Riesgos)*

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| jiku-mail-connector | Alto | Nuevo `src/infra/bus/`: construcción de identidad con `ServiceUser.fromKeyFile(keyFile, { issuer, projectId })`, un único `connect({ servers, instance, credsFile, auth, onTokenError })` invocado en el arranque, cliente conservado y expuesto al resto del proceso, `onTokenError` registrado que loguea `error` sin terminar el proceso, y traducción del fallo de conexión a fallo de arranque con la clase del SDK y su `hint()` | Pending |
| Jiku (`core`) | Ninguno | **No se modifica** (G-03). Recibe indirectamente el efecto de la autenticación: crea sola la fila del conector en `users` | — |
| Bus NATS + auth-callout + Zitadel | Ninguno | **No se modifica.** Sin cambios en `rules.yaml` ni en las plantillas: la plantilla existente ya publica sobre `jiku-commands.v1.>` con comodín, y el rol `internal-app` ya existe | — |

### Cambios de API

#### Endpoints Existentes a Modificar

**Ninguno.** El conector no expone HTTP; `docs/apis/` está vacío por decisión declarada.

#### Nuevos Endpoints

**Ninguno.** El conector no expone puerto, ni ruta, ni healthcheck (ADR-001); el healthcheck HTTP
está explícitamente fuera de alcance v1 (ADR-006).

#### Interacciones externas de esta story (el contrato real)

**Zitadel** — HTTPS, RFC 7523. El SDK firma con la key del machine user y obtiene el access token
(JWT con claim de roles, ~1 h de vida). El conector **no implementa nada** del intercambio: lo hace
el SDK. El token vive **sólo en memoria** (ADR-005).

**Bus NATS + auth-callout** — `connect({ servers, instance, credsFile, auth, onTokenError })` del
SDK, **exactamente una vez**. El SDK entrega el token **como getter, no como string** (patrón 5 del
PRD): el callout evalúa al conectar y NATS no revalida después.

**Esta story no publica ningún comando.** Deja el cliente conectado y listo; publicar es de S-005.

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

**Ninguna.** El conector no alcanza PostgreSQL: está tres saltos más allá (ADR-001, que además
prohíbe declarar `pg`, `sequelize`, `sequelize-typescript`, `typeorm`, `prisma`, `knex`).

#### Nuevas Tablas

**Ninguna.** Sin base propia, sin migraciones, sin estado en disco (ADR-001, NFR-R02).

#### Escrituras en la base de Jiku (efecto lateral, no provocado)

| Tabla de Jiku | Quién escribe | Qué queda |
|---|---|---|
| `users` | **Jiku sola**, al consumir el evento del auth-callout en la primera autenticación | La fila del conector, con `identity_type: service` y `email` en `NULL`. **El conector no la crea ni la pide** (CA-9, ADR-005) |

### Flujo de Interacción

#### Escenario A: Arranque exitoso (CA-1, CA-2, CA-3)

**Trigger:** `npm run start` / el `CMD` del contenedor, con la configuración validada (S-002) y el
logger construido (S-003).

**Flujo:**

1. **[jiku-mail-connector · `src/infra/bus/`]**
   - Acción: `ServiceUser.fromKeyFile(keyFile, { issuer, projectId })` — lee la key del archivo
     montado read-only.
   - Output: identidad con `auth.userId` derivado de la key; ese es el `user-id` que irá en el
     subject, **nunca uno del entorno**.

2. **[jiku-mail-connector → Zitadel]** (HTTPS, RFC 7523)
   - Acción: el SDK firma con la key y obtiene el access token (JWT con claim de roles, ~1 h).
   - Output: token **sólo en memoria**, expuesto como getter.

3. **[jiku-mail-connector → Bus NATS → auth-callout]**
   - Acción: `connect({ servers, instance, credsFile, auth, onTokenError })`, **exactamente una vez**.
     El callout evalúa el token al conectar; NATS no revalida después.
   - Output: cliente conectado, conservado por toda la vida del proceso.
   - **Efecto lateral no provocado:** esta autenticación es la que hace que Jiku cree la fila del
     conector en `users` (CA-9).

4. **[jiku-mail-connector · `src/shared/logger.ts`]**
   - Acción: emite la línea de arranque exitoso.
   - Output: una línea estructurada a stdout, **sin ninguna credencial** (S-003 redacta).

**Outcome:** proceso vivo, **una** conexión, y una línea de log de arranque exitoso sin credenciales.
El arranque completo (REQ-001 AC-1) queda cerrado con esta story.

**Manejo de errores:**
- Key inexistente o JSON mal formado → **no arranca**, informando que la key no se pudo cargar, **sin
  volcar su contenido** (CA-4).
- `JikuPermissionDenied` / `Authorization Violation` → **no arranca**; el log dice **rechazo del bus
  por subject**, problema de Zitadel y **no del payload**, con la clase del SDK y su `hint()` (CA-5).
- Bus inalcanzable (red) → **no arranca**, con la clase del SDK y su `hint()`. El proceso no queda
  vivo en un estado inútil.

#### Escenario B: Refresh del token en background (CA-6, CA-7)

**Trigger:** el SDK refresca el token al acercarse su expiración (~1 h), sin intervención del
conector.

**Flujo:**

1. **[SDK, en background]**
   - Acción: renueva el token contra Zitadel y actualiza el valor que el getter devuelve.
   - Output: token nuevo en memoria; **la misma** conexión sigue en uso, sin abrir una segunda.

2. **[jiku-mail-connector · `onTokenError`]** (sólo si el refresh falla)
   - Acción: el callback registrado loguea `error` con la clase y el `hint()`.
   - Output: una línea de error; **el proceso sigue vivo**.

**Outcome:** en el camino feliz, nada cambia y la conexión es la misma. En el fallo, queda registrado
que el próximo reconnect se va a romper, pero el worker sigue funcionando con el token vigente.

**Manejo de errores:**
- Fallo del refresh → `error` logueado y **proceso vivo** (CA-6, NFR-R04). **No es fatal**, a
  diferencia del fallo de conexión al arrancar: son dos momentos distintos y las dos reglas conviven
  (REQ-001 §Supuestos, conflicto aparente resuelto).

### Flujos Afectados

- **arranque-y-conexion-al-bus** (ref: docs/flows/arranque-y-conexion-al-bus.md) — **flujo nuevo,
  cerrado por esta story**. S-002 aportó la validación fail-fast y S-003 el logger; esta story agrega
  la construcción de identidad, el `connect()` único, el efecto lateral de la fila en `users` y el
  refresh del token con su fallo no fatal.

### Consideraciones Técnicas

**Seguridad:**
- **`user-id` derivado de la key**, nunca del entorno (CA-2, NFR-S03, invariante 17): tiene que
  coincidir con el `sub` que el callout lee para autorizar el subject. Si saliera del entorno, se
  podría declarar una identidad que no es la de la key.
- **Key y creds son archivos montados read-only** (ADR-005), no valores de entorno con el contenido.
- **El access token vive sólo en memoria**: nunca a disco, nunca al log (CA-8).
- **Costo aceptado y no minimizado:** el rol `internal-app` concede **los dos planos completos**
  (`commands: ALL`, `queries: ALL`) para un conector que usa 1 comando de 20 y ninguna consulta.
  Acotarlo exige un rol nuevo con su plantilla y su entrada en el mapa de `core`, y eso **modifica el
  producto** (G-03). Registrado como fuera de alcance v1, **no descartado** (ADR-005, Alternativa 1).
- **Red:** el worker corre **dentro de la red del bus**, que no está expuesta al ingress (RF-20,
  NFR-O07).

**Performance:**
- **Una conexión por proceso, no una por operación** (CA-3, NFR-P05): conectar cuesta un round-trip a
  Zitadel más el handshake que corre el auth-callout. Abrir una por operación multiplicaría ese costo
  y además ofrecería más superficie al callout.
- El token como **getter, no como string** (patrón 5 del PRD) es lo que permite que el refresh en
  background no requiera reconectar.

**Dependencias:**
- **Prerequisito:** S-003 — a propósito. El arranque y **cada fallo de conexión** tienen que salir
  por un logger que redacta; un logger agregado después dejaría sin cubrir el tramo más sensible.
- **De despliegue (a cargo de U-02, fuera del alcance implementable):** machine user en Zitadel con
  Access Token Type = JWT y rol `internal-app`, key JSON descargada (Zitadel la entrega **una sola
  vez**), creds del sentinel montado y alcanzable, project id de Zitadel configurado, y red al bus.
  Lo que **sí** entra en alcance es fallar de forma legible cuando falta cualquiera.
- **Riesgo declarado:** la entrega del evento que crea la fila en `users` **no es durable** (NATS sin
  JetStream, ADR-005). Si se pierde, el conector queda sin fila hasta su próxima autenticación;
  reconectar lo resuelve. Es una dependencia declarada del producto, **no un bug del conector**.
- **Límite de los tests:** `Client.fromConnection()` **saltea el handshake de auth** y por eso los
  tests **no prueban nada** sobre Zitadel, el rol ni el prefijo de inbox (CA-10). La verificación real
  sólo ocurre contra un despliegue.

## Dependencias

**Prerequisitos:**
- S-003: Logging estructurado con redacción (y transitivamente S-002 y S-001)

**Habilita:**
- S-005: Publicación de `requirements.new` y traducción de errores (necesita el cliente conectado)

**Externas:**
- Machine user en Zitadel con Access Token Type = **JWT** y rol `internal-app` asignado en el project
  de gestión. Sin el rol, la conexión al bus se rechaza.
- Key JSON del machine user descargada y montada. **Zitadel la entrega una sola vez:** no se puede
  volver a bajar, sólo reemplazar por una nueva.
- Creds del sentinel del bus montado y alcanzable, y el project id de Zitadel configurado.
- Instancia de Jiku desplegada y alcanzable.
- Red al bus: el conector va **dentro** de la red del bus, que no está expuesta al ingress.
