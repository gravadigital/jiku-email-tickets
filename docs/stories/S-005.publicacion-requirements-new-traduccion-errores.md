# S-005: Publicación de `requirements.new` y traducción de errores

**Status:** Ready
**Created:** 2026-08-27
**Source:** REQ-001

## Historia de Usuario

**Como** operador que verifica el despliegue del conector (U-02),
**quiero** un modo de verificación explícito que publique un `requirements.new` real con un payload
fijo y traduzca su respuesta distinguiendo **cuál de los tres sistemas rechazó** —el bus por subject,
`core` por rol, o `core` por forma—,
**para** confirmar que el conector puede escribir en Jiku y, cuando no puede, saber en qué sistema
está el arreglo en vez de leer un error opaco.

## Criterios de Aceptación

### CA-1: Publicación exitosa y requisito visible en Jiku

**DADO** un worker arrancado y conectado, con el `projectId` de prueba apuntando a un proyecto real
de Jiku
**CUANDO** se ejecuta el modo de verificación
**ENTONCES** se publica `requirements.new` vía `client.command()` con el payload fijo
**Y** `core` responde `success`
**Y** queda un Requisito visible en Jiku, en ese proyecto, con `type: incidencia`,
`priority: sin_prioridad`, `visibilityLevel: public` y `state: analisis`
**Y** se loguea el `id` del requisito creado **junto con el `projectId`**, en la misma línea.
*(REQ-001 AC-2, RF-15, RF-16)*

### CA-2: El modo de verificación es explícito y separado del arranque

**DADO** el worker
**CUANDO** se ejecuta `npm run start` (el arranque normal)
**ENTONCES** **no se publica ningún comando**: el modo de verificación es un script separado del
repositorio, nunca un efecto secundario de `start`.
*(REQ-001 RF-13, §Supuestos ambigüedad de flujo — invariante 9: si publicara en cada arranque, cada
reinicio dejaría basura permanente en el proyecto de Jiku)*

### CA-3: Composición exacta del payload fijo

**DADO** el modo de verificación
**CUANDO** se arma el payload
**ENTONCES** lleva `title` y `description` **literales del código**, el `projectId` **de la
configuración**, `type: 'incidencia'`, `priority: 'sin_prioridad'` y `visibilityLevel: 'public'`
**Y** **no lleva `state`** (el requisito nace en `analisis`, invariante 6)
**Y** **no lleva `actor`** (invariante 18: es la única clave de identidad que el plano de escritura
rechaza de plano)
**Y** **no lleva `fileIds`** (no hay adjuntos en este alcance; es de FG-4)
**Y** **no lleva `creator`** (`core` resuelve el actor del subject e ignora lo que el cuerpo declare).
*(REQ-001 RF-14, §Cambios de API)*

### CA-4: El payload se valida antes de publicar

**DADO** el payload armado
**CUANDO** se va a publicar
**ENTONCES** se valida con el schema Zod del comando usando `safeParse`
**Y** el tipo del payload está inferido del schema (`z.infer`), no escrito a mano
**Y** `title` respeta el máximo de 255 caracteres del contrato.
*(convención `validation`; ADR-003)*

### CA-5: El SDK arma el subject y el inbox; el conector no

**DADO** el código de publicación
**CUANDO** se revisa
**ENTONCES** usa `client.command('requirements.new', payload)`
**Y** **no arma subjects a mano** ni parsea envelopes
**Y** **no fija `inboxPrefix`**: el prefijo lo fija el SDK siempre.
*(REQ-001 RF-15, ADR-002)*

### CA-6: Timeout de 15000 ms

**DADO** el comando publicado
**CUANDO** nada responde
**ENTONCES** el timeout efectivo es de **15000 ms** — el default del SDK, tomado de la configuración
y **nunca por debajo de ese piso**.
*(REQ-001 RF-5, NFR-P03)*

### CA-7: `JikuPermissionDenied` — rechazo del bus por subject

**DADO** una identidad sin permiso sobre el subject del comando
**CUANDO** se publica
**ENTONCES** el error es `JikuPermissionDenied`
**Y** el log dice que rechazó **el bus, por subject, antes de que `core` viera nada**
**Y** que el arreglo está en **el rol de Zitadel**, y que **no implica nada sobre `core`**.
*(REQ-001 AC-11, RF-17)*

### CA-8: `caller_not_authorized` — `core` rechazó por rol

**DADO** un conector recién desplegado que todavía **no tiene fila en `users`**
**CUANDO** se ejecuta el modo de verificación
**ENTONCES** falla con `JikuFailure` / `caller_not_authorized`
**Y** el log dice que **`core` rechazó por rol**, no que el payload esté mal
**Y** que típicamente es la fila ausente en `users` y que **reconectar lo corrige solo**
**Y** una corrida posterior, con la fila ya creada, **tiene éxito**.
*(REQ-001 AC-12, RF-17)*

### CA-9: `project_not_found` — `core` rechazó por forma

**DADO** un `projectId` de prueba que no existe en la instancia de Jiku
**CUANDO** se ejecuta el modo de verificación
**ENTONCES** `core` responde `project_not_found`
**Y** se loguea **con el `projectId` usado**
**Y** **no se reintenta**
**Y** el log lo distingue como rechazo de **`core` por forma** — lo que además prueba que el plano de
escritura **sí está abierto** para esta identidad.
*(REQ-001 AC-13, RF-17)*

### CA-10: `invalid_fields` — `core` rechazó la forma del payload

**DADO** un payload al que le falta un campo requerido del contrato
**CUANDO** se publica el comando
**ENTONCES** `core` responde `invalid_fields`
**Y** el log lo distingue como rechazo de **`core` por forma**, no del bus
**Y** lo declara como **prueba de que el plano de escritura está abierto**.
*(REQ-001 AC-14, RF-17)*

### CA-11: `JikuTimeout` — nada respondió

**DADO** que `core` está caído
**CUANDO** se ejecuta el modo de verificación
**ENTONCES** a los **15 s** da `JikuTimeout`
**Y** se loguea la clase del SDK con su `hint()`
**Y** **no hay reintento**.
*(REQ-001 AC-15, RF-19)*

### CA-12: `JikuNoEndpoint` y `JikuInvalidRequest`

**DADO** que nada está suscripto al subject
**CUANDO** se publica
**ENTONCES** el error es `JikuNoEndpoint`, se loguea **de inmediato** con su clase y su `hint()`, sin
esperar el timeout
**Y DADO** un comando rechazado **localmente** por el SDK
**CUANDO** se publica
**ENTONCES** el error es `JikuInvalidRequest`, el log lo distingue como **error de armado del
conector** y aclara que **nada llegó a la red**.
*(REQ-001 §Manejo de errores, tabla de 7 clases)*

### CA-13: `errorCode` desconocido no se mapea a nada

**DADO** una respuesta de error con un `errorCode` que el conector no conoce
**CUANDO** se traduce el error
**ENTONCES** se loguea con su `code` y su `hint()`
**Y** **no se mapea a ningún caso conocido**.
*(REQ-001 AC-16, RF-18)*

### CA-14: Ningún caso se reintenta

**DADO** cualquiera de las ocho situaciones de error
**CUANDO** se maneja
**ENTONCES** el comando **no se reintenta**: el resultado del modo de verificación es informar el
fallo con la clase del SDK, el `code` y el `hint()`.
*(REQ-001 RF-19, C-19, NFR-R03)*

### CA-15: Repetible y sin idempotencia — cada corrida crea un requisito nuevo

**DADO** el modo de verificación ejecutado dos veces seguidas
**CUANDO** termina la segunda corrida
**ENTONCES** hay **dos** requisitos de prueba en Jiku
**Y** **ninguno de los dos se borra ni se modifica** — el conector no tiene comando de compensación
(invariante 9) y no hay idempotencia.
*(REQ-001 AC-6)*

### CA-16: La fila del conector en `users` se verifica, no se provoca

**DADO** que el requisito de prueba se creó correctamente
**CUANDO** se consulta la fila del conector en `users` de Jiku
**ENTONCES** existe, con `identity_type: service` y `email` en `NULL`, creada por Jiku en la primera
autenticación — el conector **no la creó ni la pidió**.
*(REQ-001 AC-3, ADR-005, G-03)*

### CA-17: Un test por clase de error del SDK

**DADO** la suite de tests
**CUANDO** se ejecuta
**ENTONCES** **cada** clase de error del SDK manejada en producción tiene su test — las siete de la
tabla más el caso del `errorCode` desconocido
**Y** el responder de `core` se implementa en el propio test, contra el NATS de Testcontainers
**Y** hay un test que verifica que **ningún** camino de error reintenta.
*(convención de testing, regla dura; REQ-001 RF-17, RF-18, RF-19)*

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| jiku-mail-connector | Alto | Nuevo `src/domain/publicacion/`: schema Zod del payload de `requirements.new` con tipos inferidos, armado del payload fijo, publicación con `client.command()`, log de éxito con `{ projectId, requirementId }`. Nuevo traductor de errores del SDK (las 7 clases + `errorCode` desconocido) que produce el diagnóstico de "quién rechazó". Nuevo script `verify` separado de `start`. Un test por clase de error, con responder de `core` en el test | Pending |
| Jiku (`core`) | Ninguno | **No se modifica** (G-03). Recibe `requirements.new`, que **ya existe**. Ningún comando nuevo, ningún endpoint, ninguna migración | — |
| Bus NATS + auth-callout + Zitadel | Ninguno | **No se modifica.** La plantilla existente ya publica sobre `jiku-commands.v1.>` con comodín | — |

### Cambios de API

#### Endpoints Existentes a Modificar

**Ninguno.** El conector no expone HTTP; `docs/apis/` está vacío por decisión declarada
(PRD arquitectura §Superficie expuesta).

#### Nuevos Endpoints

**Ninguno.** El "API" de este servicio es el bus.

#### Comando del bus consumido (el contrato real de esta story)

**`requirements.new`** — subject `{instance}.{sub}.jiku-commands.v1.requirements.new`
(ref: PRD arquitectura §Subjects de mensajería)

- **Servicio que lo atiende:** `core` de Jiku (queue group `jiku-commands`). **Ya existe** — sin
  cambios.
- **Publicación:** `client.command('requirements.new', payload)`. El conector **no arma el subject ni
  parsea el envelope** (ADR-002).
- **Reply:** por `_INBOX.{hash(sub)}.>`, prefijo fijado **por el SDK siempre**. El conector **no fija
  `inboxPrefix`**.
- **Timeout:** **15000 ms**, el default del SDK. **No se baja** (NFR-P03, ADR-006).

**Payload en este alcance** (campos y tipos de ADR-003 §Implementation Rules y de la entidad
**Requisito** en el PRD):

| Campo | Tipo | Valor en el modo de verificación | Origen |
|---|---|---|---|
| `title` | string, req, **max 255** | literal del código | CA-3 |
| `description` | text, req | literal del código | CA-3 |
| `projectId` | **int**, req | de la configuración | CA-3, S-002 |
| `type` | enum `funcionalidad`\|`mejora`\|`incidencia`\|`otro` | **`incidencia`** | default del conector |
| `priority` | enum `sin_prioridad`\|`baja`\|`media`\|`alta`\|`urgente` | **`sin_prioridad`** | default |
| `visibilityLevel` | enum `public`\|`internal` | **`public`** | default |

**Lo que el payload NO lleva, con su fuente:**

- **`state`** — el requisito nace en `analisis`, default de Jiku (invariante 6, ADR-003).
- **`actor`** — **la única clave de identidad que el plano de escritura rechaza de plano**
  (invariante 18, ADR-003, ADR-005).
- **`fileIds`** — se envía **sólo si hay al menos uno** (ADR-003); no hay adjuntos acá. Es de FG-4.
- **`creator`** — `core` resuelve el actor **del subject** e ignora lo que el cuerpo declare
  (ADR-005). Enviarlo sería informativo y engañoso.

**Fuera de alcance:** `files.request-upload` (FG-4), y **nada** en el plano de consultas
`jiku-queries.*` — el conector no lo usa (ADR-003). La lógica de C-16 (payload derivado del mail,
truncado, placeholders) pertenece a FG-3.

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

**Ninguna.** El conector no alcanza PostgreSQL: está tres saltos más allá — publica un comando,
`core` lo ejecuta, `core` escribe (ADR-001).

#### Nuevas Tablas

**Ninguna.** Sin base propia, sin migraciones (ADR-001, NFR-R02).

#### Escrituras en la base de Jiku (por comando, no por SQL)

| Tabla de Jiku | Quién escribe | Qué queda |
|---|---|---|
| `requirements` | **`core`**, al ejecutar `requirements.new` | Un requisito de prueba **por corrida** del modo de verificación, con `state: analisis`. **Nunca se modifica ni se borra** — no hay comando de compensación (invariante 9) |
| `users` | **Jiku sola**, en la primera autenticación | La fila del conector, `identity_type: service`, `email` en `NULL`. Se **verifica** (CA-16), no se provoca |

**Consecuencia aceptada:** el modo de verificación es repetible y **cada corrida deja un requisito
nuevo que nadie limpia** (CA-15). Sin idempotencia (ADR-001) y sin compensación (ADR-003), la
mitigación es operativa: correrlo contra un proyecto de prueba.

### Flujo de Interacción

#### Escenario: Modo de verificación (CA-1)

**Trigger:** ejecución **explícita y separada del arranque normal** — un script del repositorio
(p. ej. `npm run verify`), **nunca un efecto secundario de `start`** (CA-2).

> **Por qué separado:** invariante 9 — un requisito creado no se modifica ni se borra nunca. Si la
> publicación ocurriera en cada arranque, **cada reinicio dejaría basura permanente** en el proyecto
> de Jiku.

**Flujo:**

1. **[modo verificación]**
   - Acción: reusa el arranque completo (S-002 configuración, S-003 logger, S-004 identidad y
     conexión): misma configuración, mismo logger, misma identidad, **una sola conexión**.
   - Output: cliente conectado y listo para publicar.

2. **[jiku-mail-connector · `src/domain/publicacion/`]**
   - Acción: arma el payload **fijo** y lo valida con el schema Zod (`safeParse`) antes de publicar.
   - Output: payload válido, **sin `state`, sin `actor`, sin `fileIds`, sin `creator`**.

3. **[jiku-mail-connector → bus → `core`]**
   - Acción: `client.command('requirements.new', payload)`. El SDK arma el subject
     `{instance}.{sub}.jiku-commands.v1.requirements.new` y fija el `inboxPrefix`.
   - Output: comando publicado; espera la reply por `_INBOX.{hash(sub)}.>` con timeout de 15000 ms.

4. **[`core`]**
   - Acción: autoriza el caller leyendo `users.roles`; resuelve el actor **del `sub` del subject**;
     valida la forma; crea el requisito en una transacción con `state: analisis`.
   - Output: responde `success` con el `id`.

5. **[jiku-mail-connector]**
   - Acción: loguea el `id` del requisito **junto con el `projectId`** en la misma línea.
   - Output: `{ projectId, requirementId }`. **No reintenta nada.**

**Outcome:** un requisito visible en Jiku en ese proyecto, con `type: incidencia`,
`priority: sin_prioridad`, `visibilityLevel: public`, `state: analisis`; y una línea de log con
`{ projectId, requirementId }`. **Es la primera prueba de que el conector puede escribir en Jiku** —
el walking skeleton queda cerrado.

**Manejo de errores — la tabla es el entregable central de esta story** (CA-7 a CA-14; copiada de
ADR-006 y del PRD de arquitectura):

| Clase del SDK | `errorCode` | Quién rechazó | Qué dice el log | CA |
|---|---|---|---|---|
| `JikuPermissionDenied` | — | **El bus**, por subject, antes de que `core` viera nada | Problema del **rol en Zitadel**. **No implica nada sobre `core`** | CA-7 |
| `JikuFailure` | `caller_not_authorized` | El bus dejó pasar; **`core` rechazó por rol** | Típicamente **sin fila en `users`**. Reconectar lo corrige solo | CA-8 |
| `JikuFailure` | `invalid_fields` | `core` aceptó el caller y rechazó **la forma** | El payload. **Prueba de que el plano de escritura está abierto** | CA-10 |
| `JikuFailure` | `project_not_found` | `core`: el proyecto no existe | Se loguea **con el `projectId` usado**. También prueba que el plano está abierto | CA-9 |
| `JikuTimeout` | — | Nada respondió: `core` caído o lento | A los **15 s**, con la clase y el `hint()`. **Sin reintento** | CA-11 |
| `JikuNoEndpoint` | — | El bus dice **de inmediato** que nada está suscripto | Sin esperar el timeout | CA-12 |
| `JikuInvalidRequest` | — | Rechazado **localmente**: nada llegó a la red | Error de armado del conector | CA-12 |
| cualquiera | **desconocido** | — | Se loguea con su `code` y su `hint()` **y no se mapea a nada** | CA-13 |

**En los ocho casos: no hay reintento** (CA-14, RF-19, C-19, NFR-R03).

### Flujos Afectados

- **publicacion-requirements-new** (ref: docs/flows/publicacion-requirements-new.md) — **flujo nuevo
  creado por esta story.** Cubre el payload, la reply por `_INBOX` y **las 7 clases de error con su
  diagnóstico**.

  > **Nota para FG-3:** este flujo se **extiende**, no se reescribe: cambia el origen del payload
  > (fijo → derivado del mail, C-16) y se agrega el registro del alta con `messageId` (C-18). La
  > traducción de errores queda igual.

- **arranque-y-conexion-al-bus** (ref: docs/flows/arranque-y-conexion-al-bus.md) — no se modifica; el

### Consideraciones Técnicas

**Seguridad:**
- **Sin `actor` en el payload** (invariante 18): es la única clave de identidad que el plano de
  escritura rechaza de plano. `core` resuelve el actor del `sub` del subject, así que declararlo en el
  cuerpo sería a la vez inútil y peligroso.
- El log de éxito lleva `id` y `projectId` — identificadores, no contenido. En este alcance no hay
  cuerpo de mail que pueda filtrarse; la capacidad de redacción ya está puesta en S-003 para cuando
  lo haya.
- Ningún error se loguea con el payload completo si eso implicara volcar datos sensibles: el
  diagnóstico se basa en la clase, el `code` y el `hint()`.

**Performance:**
- **Timeout de 15000 ms**, deliberadamente por encima de los 10 s del servidor (NFR-P03). **Riesgo
  declarado:** alguien "optimiza" el timeout a 5 s y convierte los errores explicados de PostgreSQL
  —que corta a los 8 s— en timeouts mudos. Es el tipo de cambio que parece una mejora y empeora
  exactamente lo que se está protegiendo. Está como regla explícita con su razón (ADR-006, RF-5) y
  como piso en la configuración (S-002 CA-5).
- **Sin reintento** (CA-14): no hay backoff ni cola que dimensionar.
- **Sin concurrencia a modelar:** no hay tick ni lote en este alcance. El procesamiento secuencial de
  ADR-001 aplica desde FG-2.

**Dependencias:**
- **Prerequisito:** S-004 — necesita el cliente conectado. Sin conexión no hay nada que publicar.
- **`error-handling` se adopta sin `httpStatus`** (desviación declarada de REQ-001): la convención
  modela `AppError` con `abstract readonly httpStatus: number` y un handler que traduce al borde HTTP;
  **este servicio no tiene borde HTTP** (ADR-001). Se conservan la clase base, el `code` estable en
  `SCREAMING_SNAKE_CASE`, la prohibición de `throw new Error(...)` en dominio y la regla de no filtrar
  datos sensibles en `message`/`details`. **El "borde" de este servicio es el log**, y la traducción
  que ahí ocurre es esta tabla.
- **Convención candidata, no escrita todavía:** el uso del SDK (conexión única, token como getter,
  mapeo de clases de error) no tiene convención en el catálogo. Esta story **produce ese patrón**;
  formalizarlo es candidato a `/product-change-technical-definition` cuando FG-2/FG-3 confirmen que se
  estabilizó. No se escribe acá para no fijar una convención con un solo caso de uso.
- **Límite de los tests:** el responder de `core` se implementa **en el propio test** y
  `Client.fromConnection()` **saltea el handshake de auth**. Los tests cubren la traducción de las
  ocho situaciones, pero **no prueban nada** sobre Zitadel, el rol ni el prefijo de inbox — eso sólo
  se verifica contra un despliegue real.
- **De esta story dependen** FG-2 (que reemplaza el trigger), FG-3 (que reemplaza el origen del
  payload) y FG-4 (que agrega `fileIds`).

## Dependencias

**Prerequisitos:**
- S-004: Identidad y conexión única al bus (y transitivamente S-003, S-002, S-001)

**Habilita:**
- S-006: Dockerfile y precondiciones de despliegue (empaqueta algo que ya funciona)
- FG-2, FG-3 y FG-4 completos: este es el punto donde el plano de escritura queda probado

**Externas:**
- Una instancia de Jiku desplegada y alcanzable, con **al menos un `projectId` real para la prueba**.
- Las precondiciones de S-004 (machine user, rol, key, creds, red), a cargo de U-02.
- **Nota operativa:** correr el modo de verificación **contra un proyecto de prueba**. Cada corrida
  deja un requisito permanente que nadie puede limpiar (CA-15).
