# S-002: Configuración tipada con fail-fast

**Status:** Ready
**Created:** 2026-08-27
**Source:** REQ-001

## Historia de Usuario

**Como** operador que despliega el conector (U-02),
**quiero** que el worker valide toda su configuración al arrancar y, si falta algo, no arranque e
informe **la lista completa** de lo que falta en un solo mensaje,
**para** corregir el despliegue en una sola pasada en vez de descubrir una variable por corrida, y
no terminar con un proceso vivo que falla más tarde con un error opaco.

## Criterios de Aceptación

### CA-1: Punto de lectura único del entorno

**DADO** el código completo del conector
**CUANDO** se busca el acceso a `process.env`
**ENTONCES** aparece **únicamente** dentro de `src/config/`
**Y** ningún otro módulo lee el entorno ni llama a `loadConfig()` del SDK.
*(REQ-001 AC-19, RF-2, RF-19)*

### CA-2: Fail-fast con la lista completa de lo que falta

**DADO** que faltan `JIKU_CREDS`, `JIKU_KEY_FILE` y `JIKU_PROJECT_ID`
**CUANDO** arranca el worker
**ENTONCES** el worker **no arranca**, con exit code distinto de 0
**Y** informa **las tres juntas** en un solo mensaje
**Y** no intenta conectar a nada antes de fallar.
*(REQ-001 AC-7, RF-3)*

### CA-3: Una variable requerida faltante también corta el arranque

**DADO** que falta únicamente `JIKU_PROJECT_ID`
**CUANDO** arranca el worker
**ENTONCES** el worker **no arranca**, en vez de conectar y fallar después con un
`Authorization Violation` opaco — sin ese project id el token no lleva roles y no conecta a nada.
*(REQ-001 AC-8)*

### CA-4: Defaults declarados

**DADO** que no se configuró `JIKU_INSTANCE`, `JIKU_SERVERS`, `JIKU_ISSUER`, `JIKU_TIMEOUT` ni el
nivel de log
**CUANDO** arranca el worker
**ENTONCES** arranca con los defaults declarados: `JIKU_INSTANCE` = `dev`, `JIKU_SERVERS` =
`nats://localhost:4222`, `JIKU_ISSUER` = `https://id.grava.io`, `JIKU_TIMEOUT` = `15000` ms,
`LOG_LEVEL` = `info`.
*(REQ-001 AC-9, RF-4)*

### CA-5: El timeout no baja de 15000 ms

**DADO** un `JIKU_TIMEOUT` configurado por debajo de 15000
**CUANDO** se resuelve la configuración
**ENTONCES** el valor efectivo **no baja de 15000 ms**.
**Y** la razón queda documentada en el código: el servidor corta a los 10 s y PostgreSQL a los 8 s;
un timeout más corto convierte el error explicado en un timeout mudo.
*(REQ-001 RF-5, NFR-P03)*

### CA-6: Las variables de IMAP y del Mapa de Tickets todavía no se exigen

**DADO** que están presentes sólo las variables del bus y el `projectId` de prueba, y **ninguna**
variable de IMAP ni del Mapa de Tickets
**CUANDO** arranca el worker
**ENTONCES** arranca normalmente: en este alcance no hay ingesta y esas variables no son requeridas.
*(REQ-001 AC-5)*

### CA-7: Los defaults del SDK no se redeclaran a mano

**DADO** la configuración del bus
**CUANDO** se revisa cómo se resuelve
**ENTONCES** se lee con `loadConfig()` del SDK, invocado **dentro de `src/config/`**, y su resultado
se reexporta junto con el `env` validado
**Y** ningún default del SDK está copiado a mano en el código del conector.
*(REQ-001 §Consideraciones Técnicas, desviación 2; ADR-002)*

### CA-8: El `projectId` de prueba viene de la configuración

**DADO** la configuración validada
**CUANDO** se lee el `projectId` que usará el modo de verificación
**ENTONCES** sale de una variable de entorno requerida, no de un literal del código — para que U-02
apunte a un proyecto real de su instancia sin recompilar.
*(REQ-001 §Supuestos, alcance del payload de prueba)*

### CA-9: Los tipos se infieren del schema

**DADO** el módulo de configuración
**CUANDO** se revisan los tipos que expone
**ENTONCES** están inferidos del schema Zod (`z.infer`), no escritos a mano en paralelo.
*(convención `validation`)*

### CA-10: La configuración inválida no filtra secretos

**DADO** un valor de configuración que no pasa la validación
**CUANDO** se emite el mensaje de fallo
**ENTONCES** el mensaje nombra la variable y qué se esperaba, **sin volcar el valor** de ninguna
variable sensible (`JIKU_CREDS`, `JIKU_KEY_FILE` y su contenido).
*(REQ-001 RF-8, NFR-S06)*

### Flujo de Interacción

#### Escenario A: Arranque con configuración completa (CA-4, CA-6, CA-7)

**Trigger:** `npm run start` / el `CMD` del contenedor.

**Flujo:**

1. **[jiku-mail-connector · `src/index.ts`]**
   - Acción: importa `src/config/env.ts` como primer efecto del arranque.
   - Output: la validación corre antes de cualquier otra inicialización.

2. **[jiku-mail-connector · `src/config/env.ts`]**
   - Acción: `createEnv({ ..., emitErrors: true })` valida `process.env` contra el schema Zod.
   - Output: objeto tipado con las requeridas presentes y los defaults resueltos.

3. **[jiku-mail-connector · `src/config/`]**
   - Acción: invoca `loadConfig()` del SDK para la configuración del bus y reexporta su resultado
     junto con el `env` validado.
   - Output: configuración única del proceso, con los defaults del SDK sin duplicar.

**Outcome:** un objeto de configuración tipado, validado y único, listo para que el logger (S-003) y
el adaptador del bus (S-004) lo consuman. Ningún otro módulo vuelve a tocar el entorno.

**Manejo de errores:**
- Requeridas faltantes → `emitErrors: true` agrega **todos** los issues de Zod y lanza una sola vez
  con la lista completa; exit ≠ 0, sin conectar a nada (CA-2, CA-3).
- Valor con forma inválida (p. ej. `JIKU_TIMEOUT` no numérico) → mismo camino: entra en la lista
  agregada, sin volcar valores sensibles (CA-10).
- `JIKU_TIMEOUT` válido pero menor a 15000 → se eleva al piso, no es un error (CA-5).

#### Escenario B: Arranque con configuración incompleta (CA-2, CA-3)

**Trigger:** `npm run start` con el entorno mal armado.

**Flujo:**

1. **[jiku-mail-connector · `src/config/env.ts`]**
   - Acción: Zod acumula un issue por cada variable requerida ausente o mal formada.
   - Output: un solo throw con todos los issues agregados.

2. **[jiku-mail-connector · `src/index.ts`]**
   - Acción: el error corta el arranque; el proceso termina con exit ≠ 0.
   - Output: un mensaje con **la lista completa** de lo que falta.

**Outcome:** el proceso **no queda vivo** en un estado inútil, y U-02 corrige todo el despliegue en
una sola pasada.

**Manejo de errores:** no aplica — este escenario *es* el manejo de errores. Nada se conecta, nada se
publica, no hay estado parcial que limpiar.

### Consideraciones Técnicas

**Seguridad:**
- El punto de lectura único (CA-1) es lo que hace **auditable** que ningún secreto se lea desde un
  lugar inesperado: la propiedad se verifica con un `grep process.env` que devuelve un solo archivo.
- Los mensajes de validación nombran variables, **nunca valores** (CA-10): el error de una key mal
  formada no puede volcar la key.
- `JIKU_KEY_FILE` y `JIKU_CREDS` son **rutas a archivos montados read-only**, no el contenido en sí
  (ADR-005): esta story valida que la ruta esté declarada; que el archivo se pueda leer y parsear es
  de S-004.

**Performance:**
- La validación corre una sola vez, al arrancar. No hay revalidación por operación ni recarga en
  caliente: el conector es un proceso único y su configuración es inmutable por corrida.
- El piso de 15000 ms está deliberadamente **por encima** de los 10 s del servidor (NFR-P03).
  Bajarlo parece una mejora y empeora exactamente lo que se está protegiendo.

**Dependencias:**
- **Prerequisito:** S-001 (el proyecto tiene que compilar con `strict` y ESM antes de que exista
  este módulo).
- **Conflicto de convenciones resuelto:** `env-config` exige que `process.env` se lea sólo en
  `src/config/env.ts`, mientras que ADR-002 exige leer la configuración del bus con `loadConfig()`
  del SDK. Conviven porque `loadConfig()` se invoca **dentro** de `src/config/` (CA-7) — la
  propiedad de CA-1 se mantiene y los defaults del SDK no se duplican.
- **Habilita a S-003 y S-004**: el logger necesita `LOG_LEVEL` y el adaptador del bus necesita las
  `JIKU_*`. Por eso esta story va antes de sus dos consumidores.
