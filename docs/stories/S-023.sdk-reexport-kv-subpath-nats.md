# S-023: Minor del SDK — re-exportar el KV por el subpath `./nats`

**Status:** Done
**Created:** 2026-09-08
**Source:** REQ-005

> **⚠ REEMPLAZADA entera por [S-032](S-032.migracion-estado-espacio-kv-sdk.md)
> ([REQ-008](../requests/REQ-008.migracion-al-kv-del-sdk.md), 2026-10-08).** `jiku-ts` **nunca tuvo** ese
> re-export: lo traía el build 1.1.0 vendoreado, y la rama `dev` del SDK no. Desde S-032 el KV entra
> por `client.kv()` del SDK y el conector no tiene ninguna librería de KV en el árbol. Se conserva el
> texto original, no se borra.

## Historia de Usuario

**Como** equipo que va a mudar el estado del conector al KV de NATS,
**quiero** que el SDK `@gravadigital/jiku` re-exporte `@nats-io/kv` por su subpath `./nats` ya
existente, con la dependencia pinneada a `3.4.0` exacto,
**para** que el conector pueda construir el KV sobre la misma copia de `nats-core` que su conexión,
sin declarar `@nats-io/kv` como dependencia directa y sin reescribir la Implementation Rule de
ADR-002.

## Criterios de Aceptación

### CA-1: El subpath `./nats` exporta los símbolos del KV

**DADO** el SDK `@gravadigital/jiku` con el minor publicado
**CUANDO** el conector hace `import { Kvm } from '@gravadigital/jiku/nats'`
**ENTONCES** el símbolo resuelve, con tipos, tanto en el build de Node como en el de browser.
*(REQ-005 §Cambios de Dependencias — Los cambios, por repositorio)*

### CA-2: `@nats-io/kv` entra pinneado exacto, sin `^`

**DADO** el `package.json` del SDK
**CUANDO** se inspecciona el bloque `dependencies`
**ENTONCES** declara `"@nats-io/kv": "3.4.0"` — **exacto, sin `^` ni `~`**
**Y** lleva un comentario adyacente que explica que el pin no es cosmético: mientras `@nats-io/kv`
pinnee `nats-core` exacto, un `^3.4.0` permitiría que un `3.5.x` futuro arrastre un `nats-core` 3.5.x
y reintroduzca la doble copia sin que nadie cambie nada.
*(REQ-005 §Cambios de Dependencias — Consecuencia de diseño; riesgo 7)*

### CA-3: Los dos archivos de entrada re-exportan el KV

**DADO** `src/nats.node.ts` y `src/nats.ws.ts`, que ya existen y ya hacen
`export * from '@nats-io/nats-core'`
**CUANDO** se aplica esta story
**ENTONCES** cada uno gana una línea `export * from '@nats-io/kv';`
**Y** no se crea ningún subpath nuevo en el `exports` del `package.json`: `./nats` ya está declarado y
su docstring ya declara literalmente este propósito.
*(REQ-005 §Cambios de Dependencias — Los cambios, por repositorio)*

### CA-4: Una sola copia de `nats-core` en el árbol del conector — criterio de salida

**DADO** el conector con el minor del SDK ya instalado
**CUANDO** se corre `npm ls @nats-io/nats-core`
**ENTONCES** muestra **una sola** entrada (más sus `deduped`), sin una copia anidada bajo
`@nats-io/kv` ni bajo `@nats-io/jetstream`.
*(REQ-005 §CA-9.b — criterio de salida no negociable)*

### CA-5: El `instanceof` contra una clase de error del SDK da `true` — criterio de salida

**DADO** un error de permisos lanzado por una operación del KV
**CUANDO** se evalúa `error instanceof PermissionViolationError` con la clase importada del SDK
**ENTONCES** da `true`
**Y** con eso queda demostrado que hay una sola copia de `nats-core` en el árbol, que es lo que la
traducción de errores del conector (`diagnosePublishFailure()`, por clase) necesita para seguir
funcionando.
*(REQ-005 §CA-9.c — criterio de salida no negociable)*

### CA-6: La publicación es un **minor**, no un major

**DADO** que el cambio es puramente aditivo (dos `export *` y una dependencia nueva)
**CUANDO** se versiona el paquete
**ENTONCES** se publica como **minor**: ningún símbolo existente cambia de forma ni desaparece, y
ningún consumidor actual del SDK se rompe.
*(REQ-005 §Servicios Afectados)*

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `@gravadigital/jiku` (SDK, **otro repositorio**) | **Bloqueante** | `@nats-io/kv@3.4.0` exacto en `dependencies`; `export * from '@nats-io/kv';` en `src/nats.node.ts` y `src/nats.ws.ts`; publicar minor | Done |
| `jiku-email-tickets` | Ninguno en esta story | Se sube el rango del SDK en la story siguiente (S-024). **No declara** `@nats-io/kv` ni `@nats-io/jetstream` | — |

**Esta story no toca el repositorio del conector.** Su único entregable en `jiku-email-tickets` es
la verificación de los dos criterios de salida (CA-4, CA-5) sobre el paquete publicado.

### Cambios de API

**Ninguno.** El SDK no expone un contrato HTTP ni de mensajería propio que cambie: lo que cambia es
su superficie de módulo, y de forma puramente aditiva.

### Cambios de Base de Datos

**Ninguno.**

### Cambios de Dependencias

#### En `@gravadigital/jiku`

```jsonc
// package.json
"dependencies": {
  // Pinneado EXACTO a propósito, no es un descuido:
  // @nats-io/kv pinnea @nats-io/nats-core exacto (3.4.0 -> nats-core 3.4.0).
  // Con "^3.4.0" un 3.5.x futuro arrastraría un nats-core 3.5.x, npm no podría
  // deduplicar contra el ^3.4.0 de este paquete, e instalaría una SEGUNDA copia
  // de nats-core: el instanceof contra las clases de error del SDK dejaría de
  // funcionar. Subir esta version es deliberado y va junto con nats-core.
  "@nats-io/kv": "3.4.0",
  ...
}
```

**Verificación que sostiene el pin** (hecha en el diseño del REQ, contra el registry):

```
npm view @nats-io/kv@3.4.0 dependencies
  { "@nats-io/jetstream": "3.4.0", "@nats-io/nats-core": "3.4.0" }

npm view @nats-io/jetstream@3.4.0 dependencies
  { "@nats-io/nats-core": "3.4.0" }
```

El SDK declara `^3.4.0` de `nats-core` y hoy resuelve `3.4.0`. Las tres coinciden, npm deduplica y
queda una sola copia — **sin alinear rangos a mano, sin reescribir el `^3.4.0` del SDK y sin tocar
ADR-002**.

**Lo que NO se hace:** subir a `@nats-io/kv@3.3.1`, que pinnea `nats-core` `3.3.1` contra el `^3.4.0`
del SDK y es exactamente el escenario de doble copia que este pin existe para evitar. Fue el riesgo
declarado principal de la clarificación de REQ-005, y se resuelve por verificación de versión.

#### En `jiku-email-tickets`

**Ninguna dependencia nueva, ni en esta story ni en las siguientes** (RF-22). El conector no declara
`@nats-io/kv` ni `@nats-io/jetstream`: importa del subpath `./nats` del SDK.

**Ninguno.**

### Flujo de Interacción

#### Escenario: El conector construye el KV sobre la conexión del SDK

**Trigger:** S-024 importa `Kvm` para abrir los buckets.

**Flujo:**

1. **[`@gravadigital/jiku`]**
   - Acción: `src/nats.node.ts` re-exporta el namespace completo de `@nats-io/kv` junto al de
     `@nats-io/nats-core` que ya re-exportaba
   - Output: el subpath `./nats` expone `Kvm`, `KvWatchEntry`, `KvLimits` y las clases de error, todas
     de **la misma instancia del módulo** que la conexión

2. **[`jiku-email-tickets`]** (en S-024)
   - Acción: `import { Kvm } from '@gravadigital/jiku/nats'` y `new Kvm(client.connection)`
   - Output: un `Kvm` que comparte la copia de `nats-core` de la conexión

**Outcome:** un `instanceof` contra una clase de error del SDK da `true` sobre un error lanzado por
una operación del KV, porque hay una sola copia de `nats-core` en el árbol.

**Manejo de errores:**

| Situación | Comportamiento |
|---|---|
| `npm ls @nats-io/nats-core` muestra dos entradas | **La story no está terminada.** Es criterio de salida (CA-4), no una observación |
| El `instanceof` da `false` | Ídem (CA-5). Sintoma directo de la doble copia |
| Alguien "moderniza" el pin a `^` en un refactor futuro | El comentario del `package.json` lo previene; CA-4 lo detecta |

### Flujos Afectados

**Ninguno.** Esta story no cambia ninguna interacción documentada en `docs/flows/`: habilita la
importación que las stories siguientes usan.

### Consideraciones Técnicas

**Seguridad:**

- Ninguna capacidad nueva. El KV usa la misma identidad del machine user y los mismos permisos del
  auth-callout (ADR-005). El re-export no otorga nada por sí solo.

**Performance:**

- Sin impacto. Es una re-exportación de módulo: no agrega código en ningún camino caliente.

**Dependencias:**

- **Bloquea a las cinco stories siguientes.** El conector no puede importar del subpath un símbolo
  que todavía no se exporta (RF-23). Es una dependencia de secuencia dura, no una preferencia de
  orden.
- **ADR-002 se conserva intacta.** La Implementation Rule *"El proyecto MUST NOT declarar `nats` como
  dependencia directa"* es precisamente la razón de que el KV entre por el SDK y no por el
  `package.json` del conector.
- El test de propiedad `test/bus/source-properties.test.ts:80-90` (*"never opens a raw NATS connection
  outside the SDK"*) **sigue pasando sin modificarse**: busca `from 'nats'`, y el import es
  `from '@gravadigital/jiku/nats'`.

**Riesgo asumido:**

- El acoplamiento de versiones es del upstream, no una elección de este diseño. Mientras `@nats-io/kv`
  pinnee `nats-core` exacto, el SDK tiene que pinnear el KV exacto y subirlo deliberadamente junto con
  `nats-core`. Va documentado en el `package.json`, o el próximo que modernice el rango lo rompe
  (riesgo 7 de REQ-005).
