# S-009: Adaptador IMAP y el puerto `MailSource`

**Status:** Ready
**Created:** 2026-08-27
**Source:** REQ-002

## Historia de Usuario

**Como** conector que tiene que leer una casilla sin acoplar su lógica de tick al cliente IMAP,
**quiero** un puerto de dominio `MailSource` de tres operaciones —buscar, descargar y marcar— y un
adaptador con `imapflow` que conecta siempre sobre TLS, con el logging interno de la biblioteca
deshabilitado,
**para** que el tick se pueda testear doblando un borde chico y explícito, y para que ni las
credenciales ni el tráfico IMAP crudo puedan salir por stdout.

## Criterios de Aceptación

### CA-1: El puerto tiene tres operaciones, no dos

**DADO** `src/domain/ingesta/ports.ts`
**CUANDO** se revisa la interfaz `MailSource`
**ENTONCES** declara `searchUnseen(): Promise<number[]>`, `fetch(uid): Promise<RawMessage>` y
`markSeen(uid): Promise<void>`
**Y** `searchUnseen()` devuelve el **total sin recortar**, no un lote ya limitado.
*(REQ-002 §Cambios de API — contrato interno nuevo)*

### CA-2: La desviación respecto de la convención está justificada y documentada

**DADO** que la convención `testing` prescribe la firma `fetchUnseen(max): Promise<RawMessage[]>`
**CUANDO** se aplica esta story
**ENTONCES** la convención se **actualiza con la firma real de tres operaciones y su justificación**
—esa firma no puede satisfacer a la vez el warn de diferidos (necesita el total), el marcado de a uno
tras cada descarga, y el salteo sin marcar de una descarga fallida—
**Y** la convención **no queda mintiendo**: la desviación se registra, no se deja implícita.
*(REQ-002 §Cambios de API — desviación necesaria; §Impacto en Documentación Técnica)*

### CA-3: El recorte al cap no vive en el adaptador

**DADO** el adaptador IMAP
**CUANDO** se revisa
**ENTONCES** **no conoce `maxPerTick`** ni recorta nada: el cap y el conteo de diferidos son del tick,
que es código propio y testeable, no del borde doblado.
*(REQ-002 §Cambios de API — desviación necesaria)*

### CA-4: TLS incondicional

**DADO** el adaptador
**CUANDO** construye el cliente
**ENTONCES** pasa `secure: true` **incondicionalmente**: **no hay opción de texto plano** ni variable
que la habilite.
*(REQ-002 RF-12, CA-1)*

### CA-5: El logging interno de `imapflow` está deshabilitado explícitamente

**DADO** el cliente IMAP, cuyo default emite el tráfico crudo —que incluye el `LOGIN`—
**CUANDO** se revisa la configuración del cliente
**ENTONCES** lleva `logger: false` **incondicional**
**Y** un test lo afirma **sobre las opciones del cliente**: NFR-S06 no puede depender del default de
una dependencia.
*(REQ-002 RF-38, CA-44, Riesgo 6)*

### CA-6: Lock de `INBOX`, fija y no configurable

**DADO** el adaptador
**CUANDO** abre la casilla
**ENTONCES** toma el lock de `INBOX` con `getMailboxLock('INBOX')`
**Y** `INBOX` es una **constante del módulo de ingesta**, no una variable de entorno.
*(REQ-002 RF-4, RF-12)*

### CA-7: `searchUnseen` busca únicamente `\Unseen` y ordena UID descendente

**DADO** una casilla con mensajes leídos y no leídos
**CUANDO** se invoca `searchUnseen()`
**ENTONCES** usa `client.search({ seen: false })` y devuelve **sólo** los `\Unseen`
**Y** los devuelve ordenados **de más nuevo a más viejo (UID descendente)** — por **UID**, no por el
header `Date`, que es dato del cliente y puede venir mal.
*(REQ-002 RF-13 y RF-14, CA-3)*

### CA-8: `fetch` devuelve los bytes crudos y lanza si falla

**DADO** un UID
**CUANDO** se invoca `fetch(uid)`
**ENTONCES** devuelve un `RawMessage` con el `uid` y los **bytes RFC 822 crudos sin parsear**
**Y** si la descarga falla **lanza**, para que el llamador lo saltee **sin marcarlo `\Seen`**.
*(REQ-002 RF-16 y RF-17, §Cambios de API)*

### CA-9: `markSeen` marca un solo UID

**DADO** un UID
**CUANDO** se invoca `markSeen(uid)`
**ENTONCES** marca **ese** mensaje `\Seen`
**Y** la operación es de a uno: **el adaptador no ofrece marcado en lote**, porque el lote convertiría
un fallo a mitad de tick en reprocesado.
*(REQ-002 RF-16, §Cambios de API)*

### CA-10: Un fallo de conexión o de credenciales se propaga sin filtrar el secreto

**DADO** credenciales incorrectas o un host inalcanzable
**CUANDO** el adaptador intenta conectar
**ENTONCES** **lanza** para que el tick lo trate como fallo completo
**Y** ni el error propagado ni ningún log del adaptador contienen la contraseña, el usuario ni
fragmentos de tráfico IMAP crudo.
*(REQ-002 RF-10 y RF-37, CA-9, CA-43)*

### CA-11: `imapflow` se usa sólo desde `src/infra/imap/`

**DADO** el código del conector
**CUANDO** se busca el import de `imapflow`
**ENTONCES** aparece **únicamente** en `src/infra/imap/`
**Y** `src/domain/ingesta/` depende del **puerto**, nunca del cliente.
*(REQ-002 §Dependencias — "se usa SOLO desde src/infra/imap/"; convención `module-imports`)*

### CA-12: La conexión se cierra siempre

**DADO** un tick que terminó, con éxito o por un fallo
**CUANDO** se revisa el adaptador
**ENTONCES** `lock.release()` y `client.logout()` ocurren en un `finally`, de modo que **ninguna
conexión ni ningún lock quedan colgados** tras un fallo.
*(REQ-002 §Flujo de Interacción paso 5)*

### Cambios de API

#### Endpoints Existentes a Modificar

Ninguno.

#### Nuevos Endpoints

Ninguno. El conector no expone HTTP (ADR-001, overview).

#### Contrato interno nuevo — el puerto de dominio (el contrato real de esta story)

```ts
// src/domain/ingesta/ports.ts
export interface RawMessage {
  readonly uid: number;
  readonly source: Buffer;   // los bytes RFC 822 crudos, sin parsear
}

export interface MailSource {
  /** Los UIDs \Unseen, ordenados de más nuevo a más viejo. Devuelve el TOTAL, sin recortar. */
  searchUnseen(): Promise<number[]>;
  /** Descarga un mensaje. Si falla, lanza: el llamador lo saltea SIN marcarlo. */
  fetch(uid: number): Promise<RawMessage>;
  /** Marca \Seen. Se invoca de a uno, después de una descarga exitosa. */
  markSeen(uid: number): Promise<void>;
}
```

**Por qué tres operaciones y no la firma literal de la convención.** `fetchUnseen(max):
Promise<RawMessage[]>` no puede satisfacer tres requerimientos a la vez:

- **RF-15** exige el `warn` con **cuántos quedaron diferidos** (`encontrados − cap`). Una firma que
  devuelve ya recortada a `max` **pierde el total** y hace el contador inobservable.
- **RF-16** exige marcar `\Seen` **de a uno, inmediatamente después de cada descarga**. Un
  `Promise<RawMessage[]>` descarga el lote entero antes de devolver, así que el primer `markSeen`
  ocurriría después de la última descarga — exactamente el marcado en lote que el request descarta.
- **RF-17** exige que un mensaje **cuya descarga falla** se saltee sin marcarse. Con el lote resuelto
  de antemano, un fallo de descarga rechaza la promesa entera y **aborta el tick**.

Se conservan el nombre `MailSource` y su intención de doble de borde; **la convención `testing` se
actualiza como parte de esta story.**

### Cambios de Base de Datos

Ninguno (ADR-001). `RawMessage` vive en memoria mientras dura el procesamiento de ese mensaje.

### Flujo de Interacción

#### Escenario: Apertura de la casilla y búsqueda (CA-4 a CA-7)

**Trigger:** el tick pide un `MailSource` para el ciclo actual.

**Flujo:**

1. **[src/infra/imap]**
   - Acción: `new ImapFlow({ host, port, secure: true, auth: { user, pass }, logger: false })` con la
     configuración tipada de S-007. `secure: true` y `logger: false` son **incondicionales**
   - Output: cliente construido

2. **[src/infra/imap]**
   - Acción: `await client.connect()` → `await client.getMailboxLock('INBOX')`
   - Output: lock tomado. Si falla (credenciales, red) → **lanza**

3. **[searchUnseen]**
   - Acción: `client.search({ seen: false })` y ordena **UID descendente**
   - Output: el **total** de UIDs `\Unseen`, sin recortar

4. **[fetch]** (una vez por UID que el tick decida)
   - Acción: descarga el mensaje crudo completo
   - Output: `RawMessage { uid, source }`. Si falla → **lanza**

5. **[markSeen]** (una vez por descarga exitosa)
   - Acción: marca ese UID `\Seen`
   - Output: nada. **Nunca se revierte** (RF-19)

6. **[src/infra/imap]** cierre
   - Acción: `lock.release()` y `client.logout()` en el `finally`
   - Output: conexión cerrada, con éxito o con fallo

**Outcome:** el tick obtuvo los UIDs, los bytes que pidió y el marcado que aplicó. **Nada se
persiste.**

**Manejo de errores:**

| Fallo | Comportamiento del adaptador | Ref. |
|---|---|---|
| Credenciales incorrectas | **Lanza.** Sin credenciales en el error ni en el log | RF-10, CA-9 |
| Host inalcanzable | **Lanza** antes de tocar ningún mensaje: ninguno queda `\Seen` | RF-10, CA-10 |
| `fetch` de un UID que falla | **Lanza** ese `fetch`. El tick lo saltea **sin marcar** | RF-17, CA-14 |
| Red cortada a mitad | **Lanza.** Los ya marcados `\Seen` no se reprocesan | CA-13 |

### Consideraciones Técnicas

**Seguridad:**
- **TLS incondicional** (`secure: true`), sin opción de texto plano (RF-12).
- **`logger: false` incondicional.** Es el Riesgo 6 del diseño: el default de `imapflow` emite tráfico
  crudo, que incluye el `LOGIN`. El test afirma la opción **sobre el cliente**, no la ausencia de
  salida, para que la garantía no dependa de un default ajeno.
- La contraseña llega desde `config.imap` (dos niveles), cubierta por `'*.password'` en
  `REDACT_PATHS`. El adaptador **no la loguea nunca** de ninguna forma.
- **Ningún tráfico IMAP crudo** sale por stdout (RF-37, CA-43).

**Performance:**
- Una conexión por tick, abierta y cerrada dentro del tick. Sin pool ni conexión persistente: el
  volumen no lo justifica y una conexión viva entre ticks es estado que puede quedar roto sin
  síntoma.
- Descargas **secuenciales** (Arq-14): un mail a la vez, sin paralelismo.

**Dependencias:**
- **Prerequisito:** S-007 — el adaptador necesita host, puerto, usuario y password **tipados**.
- **`imapflow`** está preaprobada por Arq-9, con la misma versión mayor que el servicio en producción.
- **Es el borde que S-010 dobla en sus tests**, así que tiene que existir antes: el puerto define la
  superficie exacta que el tick puede simular sin red.
- **Deuda de convención declarada:** el overview registra que el poll IMAP y el scheduling por cron
  **no tienen convención** en el catálogo. Esta story y S-010 producen ese patrón; formalizarlo es
  candidato a `/product-change-technical-definition` cuando se estabilice.
