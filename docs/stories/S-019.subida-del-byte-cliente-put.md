# S-019: Subida del byte - cliente del PUT

**Status:** Completed
**Created:** 2026-08-31
**Source:** REQ-004

## Historia de Usuario

**Como** conector que ya tiene una URL prefirmada de `PutObject` para un adjunto,
**quiero** subir el byte directo al storage con un `PUT` HTTPS, sin credenciales de storage y con un
timeout acotado,
**para** entregar el contenido del archivo sin pasar por el bus —cuyo `max_payload` de 1 MB no alcanza
para adjuntos de hasta 10 MB— y sin quedar colgado si el storage no responde.

## Criterios de Aceptación

### CA-1: El `PUT` va directo a la `uploadUrl`, con `fetch` nativo y sin credenciales

**DADO** una `uploadUrl` recibida de `files.request-upload`
**CUANDO** se sube el byte
**ENTONCES** se hace `fetch(uploadUrl, { method: 'PUT', body: content })`, **sin ningún header de
credenciales de storage**
**Y** el conector **no tiene ni puede tener** credenciales de S3: la única autorización es la firma que
puso `core` en la URL.
*(REQ-004 RF-18, RF-19; criterio 18, 19, 44)*

### CA-2: El timeout es de 30000 ms por default, y es distinto del timeout del comando del bus

**DADO** el cliente del `PUT`
**CUANDO** se configura su timeout
**ENTONCES** usa `AbortSignal.timeout(config.adjuntos.putTimeoutMs)` con default **30000 ms**
**Y** este timeout es **independiente** del timeout de 15000 ms de `files.request-upload` (S-018): son
operaciones distintas, una de bus y otra HTTP directa.
*(REQ-004 RF-20; criterio 20, 21; ADR-003)*

### CA-3: Un 2xx es éxito, sin inspeccionar el cuerpo de la respuesta

**DADO** que el storage responde con cualquier código 2xx
**CUANDO** se procesa la respuesta
**ENTONCES** se considera éxito y **no se inspecciona el cuerpo** de la respuesta de S3
**Y** se acumula el `fileId` (recibido de S-018) para el payload del alta, junto con el placeholder que
le corresponde por su `mimeType`.
*(REQ-004 §Operación Nueva Fuera del Bus — Response éxito)*

### CA-4: Error de red, timeout y URL expirada se tratan exactamente igual

**DADO** que el `PUT` falla por error de red, por timeout a los 30000 ms, o porque la URL prefirmada
expiró
**CUANDO** se procesa el fallo
**ENTONCES** las tres causas producen **el mismo resultado**: aviso de fallo de subida, log `warn` sin
la `uploadUrl`, y continuar con el próximo adjunto
**Y** **no se pide un permiso nuevo** para ese archivo: pedirlo sería un reintento, prohibido por
NFR-R03.
*(REQ-004 RF-22; criterio 19, 20, 21)*

### CA-5: La `uploadUrl` nunca aparece en ningún log

**DADO** cualquier punto de log del cliente del `PUT` —éxito o fallo—
**CUANDO** se inspecciona el objeto logueado
**ENTONCES** la `uploadUrl` **no está presente en ningún campo**: es una credencial de escritura de
duración limitada, y loguearla la expone a cualquiera que lea el log.
*(REQ-004 RF-23; criterio 43)*

### CA-6: El byte nunca viaja por el bus

**DADO** el flujo completo de subida
**CUANDO** se revisa qué datos pasan por `client.command()`
**ENTONCES** el `content` del adjunto (el `Buffer`) **nunca es parte de ningún payload de comando del
bus**: sólo viaja en el cuerpo del `PUT` HTTPS directo al storage.
*(REQ-004 RF-18; criterio 18; ADR-003 §Context — max_payload de 1 MB)*

### CA-7: Un error inesperado del conector subiendo el byte también deja aviso de fallo

**DADO** un error inesperado durante la construcción del `PUT` (no un fallo del propio `fetch`, sino
una excepción del código del conector)
**CUANDO** se procesa ese adjunto
**ENTONCES** se captura, se loguea, se anota aviso de fallo de subida, y el procesamiento **continúa**
con el próximo adjunto — la misma garantía de aislamiento de fallos de la invariante 13.
*(REQ-004 criterio 24; invariante 13)*

### CA-8: El módulo sube un archivo por invocación, sin decidir el orden ni el resto del ciclo

**DADO** el cliente del `PUT` de esta story
**CUANDO** se revisa su interfaz
**ENTONCES** expone una función que recibe `{ uploadUrl, content, timeoutMs }` y devuelve éxito o
fallo para **un** adjunto — la orquestación en serie de todos los adjuntos de un mail la hace S-021.
*(REQ-004 §Story Split Propuesto — Story 3)*

### Cambios de API

Ninguno del bus: esta operación **no es un comando del bus**. Es un `PUT` HTTPS directo, documentado
acá porque es la única "API" externa nueva que este request agrega.

**Request:** `PUT {uploadUrl}` con `body: content` (el `Buffer` del adjunto), sin headers de
autorización propios.

**Response (éxito):** cualquier 2xx.

**Response (fallo):** error de red, timeout a los 30000 ms, o URL expirada — las tres iguales.

**Ref:** RF-18 a RF-23; criterios 19-21; ADR-003 §Decision, §Consequences

### Cambios de Base de Datos

Ninguno del conector. El storage actualiza `byteStatus` de la fila `files` tras el `PUT`, de forma
implícita y sin que el conector lo verifique ni lo consulte (invariante 16 — nadie verifica el byte).

### Flujo de Interacción

#### Escenario: subida exitosa

**Trigger:** un adjunto recibió `{ fileId, uploadUrl }` de S-018.

**Flujo:**

1. **[cliente del `PUT`]** `fetch(uploadUrl, { method: 'PUT', body: content, signal:
   AbortSignal.timeout(30000) })`
2. **[respuesta 2xx]** éxito → acumula `fileId` y el placeholder (`image/*` → `![attach:{id}]`, resto →
   `[attach:{id}]`).

#### Escenario: fallo del `PUT`

1. Error de red, timeout, o URL expirada.
2. Aviso de fallo de subida, `logger.warn({ nombre, mime }, ...)` **sin `uploadUrl`**.
3. `continue` con el próximo adjunto, sin pedir un permiso nuevo.

**Outcome:** el archivo queda subido (con `fileId` para el alta) o con un aviso de fallo, nunca
bloqueando el procesamiento del resto del mail.

**Manejo de errores:** ver REQ-004 §Manejo de Errores — fila "PUT a la URL prefirmada".

### Flujos Afectados

Ninguno todavía. La integración al flujo `ruteo-y-alta-del-requisito` la hace **S-021**.

### Consideraciones Técnicas

**Seguridad:**
- Cero credenciales de storage en el conector (NFR-S04).
- La `uploadUrl` nunca se loguea (CA-5) — es la protección más importante de esta story.

**Performance:**
- Un `PUT` de hasta 10 MB con timeout de 30000 ms es el caso más lento por archivo; en serie, un mail
  con 10 archivos de 10 MB puede tardar hasta 300 s en el peor caso, acotado y no ilimitado.

**Dependencias:**
- Depende de S-018 para recibir la `uploadUrl` por archivo.
- **Sin dependencias npm nuevas**: `fetch` y `AbortSignal.timeout` son nativos de Node ≥ 18.

## Dependencias

**Prerequisitos:**
- S-018: Permiso de subida - `files.request-upload`

**Habilita:**
- S-020: Composición determinística de la descripción (consume los avisos de fallo de esta story)
- S-021: Vínculo con el requisito y cierre del ciclo

**Externas:**
- El storage S3-compatible alcanzable por red desde donde corre el conector. Es una salida distinta
  de la del bus y debe verificarse aparte; no hace falta CORS ni credenciales.
