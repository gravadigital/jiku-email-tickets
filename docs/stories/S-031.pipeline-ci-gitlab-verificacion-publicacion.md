# S-031: Pipeline de CI en GitLab: verificación completa y publicación de la imagen

**Status:** In Progress
**Created:** 2026-09-25
**Source:** REQ-007

## Historia de Usuario

**Como** equipo que mantiene el conector,
**quiero** que cada push y cada merge request corran automáticamente el build, el typecheck y la
**suite completa** (incluidos los tests con NATS real y los que construyen la imagen), y que la
imagen de producción se publique en el registry del proyecto **sólo** cuando todo eso está en verde,
**para** que ningún cambio llegue a `dev` o `main` sin verificar y que la imagen que se despliega sea
siempre una que pasó la suite: `:dev` en `dev`, y la versión de `version.txt` más `:master` en `main`.

## Criterios de Aceptación

### Flujo principal

### CA-1: Push a una rama de feature verifica y no publica

**DADO** un push a una rama de feature (p. ej. `feature/S-032_x`) que toca código
**CUANDO** corre el pipeline
**ENTONCES** corren `compile` (`npm ci` → `npm run typecheck` → `npm run build`) e `image`
(`docker build --target production`) en el stage `build`, y `test` (`npm run test:teardown` con
`docker:dind`) en el stage `test`
**Y** la suite corre **completa**, sin filtros ni exclusiones: incluye los tests que levantan
`nats:2.10-alpine` y `nats:2.11-alpine -js` por Testcontainers y `test/docker-image.test.ts`, que
construye y ejecuta la imagen
**Y** ningún job de `release` corre.
*(REQ-007 CA-1, RF-1, RF-2, RF-6; Decisiones 1, 3, 4)*

### CA-2: Merge request verifica y muestra el resultado

**DADO** un merge request abierto contra `dev` o `main`
**CUANDO** se abre o se actualiza con un cambio de código
**ENTONCES** corre un pipeline de MR con `build` y `test`, y su resultado queda visible en el MR
**Y** un push a la rama de origen de ese MR (si no es `dev` ni `main`) **no** crea además un
pipeline de rama duplicado.
*(REQ-007 CA-2; Decisión 6)*

### CA-3: Push a `dev` en verde publica `:dev`

**DADO** un push a `dev` con la suite en verde
**CUANDO** termina el stage `test`
**ENTONCES** `release:dev` construye `--target production` y publica `$CI_REGISTRY_IMAGE:dev`, que
reemplaza al anterior
**Y** esto ocurre **aunque haya un MR `dev → main` abierto**.
*(REQ-007 CA-3, RF-4; Decisiones 2, 6)*

### CA-4: Push a `main` en verde publica la versión y `:master`

**DADO** un push a `main` con la suite en verde y `version.txt` = `0.1.0`
**CUANDO** termina el stage `test`
**ENTONCES** `release:main` publica `$CI_REGISTRY_IMAGE:0.1.0` y `$CI_REGISTRY_IMAGE:master`, que
apuntan a la misma imagen, en ese orden (la versión primero y el tag móvil después).
*(REQ-007 CA-4, RF-5; Decisión 8)*

### CA-5: `version.txt` existe con `0.1.0`, independiente de `package.json`

**DADO** el repo, que hoy tiene `version.txt` sin versionar con `0.0.1`
**CUANDO** se implementa esta story
**ENTONCES** `version.txt` queda versionado en la raíz con una sola línea `0.1.0` y salto de línea
final
**Y** ningún test ni job exige que coincida con el `version` de `package.json`.
*(REQ-007 CA-5, RF-7)*

### CA-6: Un cambio sólo de documentación no dispara el pipeline

**DADO** un push (que no es el primero de una rama nueva) o una actualización de MR cuyo cambio
toca sólo archivos fuera de la allowlist de `changes` (p. ej. `*.md`, `docs/**`, `.claude/**`)
**CUANDO** llega a GitLab
**ENTONCES** no se crea ningún pipeline
**Y** un cambio que toca `.gitlab-ci.yml` o `version.txt` **sí** lo dispara.
*(REQ-007 CA-6, RF-8; Decisión 5)*

### CA-7: El pipeline no corre en tags de git

**DADO** un push de un tag de git
**CUANDO** llega a GitLab
**ENTONCES** no se crea ningún pipeline: el release sale de `main`, no de tags.
*(Decisión 6)*

### Casos de error

### CA-8: Un test en rojo no publica nada

**DADO** un push a `dev` o `main` donde falla al menos un test (o la verificación de teardown)
**CUANDO** termina el stage `test` en rojo
**ENTONCES** el pipeline falla, `release:*` no corre, y `:dev`, `:master` y el tag de versión siguen
apuntando a la imagen anterior.
*(REQ-007 CA-7, RF-3)*

### CA-9: Un fallo de build corta los tests y el release

**DADO** un push donde falla `npm run typecheck`, `npm run build` o el `docker build --target
production`
**CUANDO** falla el stage `build`
**ENTONCES** `test` y `release:*` no corren y el pipeline queda en rojo.
*(REQ-007 CA-8)*

### CA-10: `version.txt` ausente, vacío o inválido corta el release de `main`

**DADO** un push a `main` con `version.txt` ausente, vacío o con un valor que no es semver (incluido
`dev`, `master` o `latest`)
**CUANDO** llega `release:main`
**ENTONCES** el job falla **antes** del `docker login` y del `docker build`
**Y** no se publica ninguna imagen: ni un tag de versión vacío, ni sólo `:master`.
*(REQ-007 CA-9; Decisión 8)*

### CA-11: Ramas de feature y MR no tocan el registry

**DADO** un push a una rama de feature o un MR, con la suite en verde
**CUANDO** termina el pipeline
**ENTONCES** `:dev`, `:master` y los tags de versión no cambian
**Y** ningún job de ese pipeline ejecuta `docker login` ni `docker push`.
*(REQ-007 CA-10, RF-6; Decisión 2)*

### CA-12: El pipeline tiene un test declarativo

**DADO** el `.gitlab-ci.yml`
**CUANDO** corre la suite

las 11 propiedades de §Verificación del pipeline, en el estilo de `test/dockerfile.test.ts`.
*(Decisión 5; §Verificación del pipeline)*

### CA-13: Ningún archivo de la raíz queda sin clasificar

**DADO** la allowlist de `changes` y la lista explícita de exclusiones
**CUANDO** alguien agrega un archivo o directorio nuevo en la raíz del repo
**ENTONCES** `test/gitlab-ci.test.ts` falla hasta que se clasifique en una de las dos listas.
*(Decisión 5, riesgo 5)*

### CA-14: Las keys de prueba funcionan con dind y no entran al contexto de build

**DADO** el job `test` con `TMPDIR=$CI_PROJECT_DIR/.ci-tmp`
**CUANDO** `test/docker-image.test.ts` monta la key y el creds con `-v`
**ENTONCES** el contenedor ve los archivos (el volumen `/builds` es compartido con `dind`)
**Y** `.dockerignore` contiene `.ci-tmp`, así que esos archivos no entran al contexto del `docker
build`
**Y** si la primera corrida muestra que el volumen no se comparte, se aplica el fallback (`docker
create` + `docker cp` + `docker start -a` en ese test) y se registra en la story.
*(Decisión 3, riesgo 2)*

deja de decir que *"quien la corre es el pipeline"*
**Y** `test/dockerfile.test.ts` y `test/docker-image.test.ts` siguen en verde sin modificarse
(salvo el fallback de CA-14).

### Decisiones de Diseño

#### Decisión 1: la suite corre sobre el checkout, **no** dentro de la imagen `test`

Los dos repos de referencia corren los tests con `docker run $PIPELINE_IMAGE npm test`, y el README
documenta ese mismo camino para la etapa `test`. **Acá no funciona, por dos razones que se
verificaron en el código:**

1. **El `.dockerignore` excluye `docs`, `*.md` y `.claude` del contexto.** Cuatro archivos de test
   (`deployment-docs`, `story-011-docs`, `story-028-docs`, `story-029-docs`) leen `README.md` y
   `docs/**`. Dentro de la imagen `test` esos archivos no existen y la suite falla en rojo por un
   motivo que no tiene que ver con el cambio. Sacarlos del `.dockerignore` rompe CA-4 de S-006
   (el `.dockerignore` es *"la mitad de la garantía de ningún secreto en la imagen"*).
2. **`test/docker-image.test.ts` construye la imagen con contexto `PROJECT_ROOT`** y afirma que no
   hay `.git` en ella. Dentro del contenedor `test`, el contexto sería el `/app` ya filtrado, lo que
   convierte en trivial lo que el test afirma.

**Decisión:** el job de test usa **`node:22-alpine`** (el mismo major que el `Dockerfile` y que el
`engines` floor, que `test/dockerfile.test.ts` afirma que coinciden) con el CLI de Docker instalado
(`apk add --no-cache docker-cli`) y un servicio `docker:dind`. Corre `npm ci` y `npm test` sobre el
checkout, que es lo mismo que corre un desarrollador. Es el modelo de `jiku/core` (`npm ci` +
`npm test` con la infraestructura que le da el pipeline), que el request tomó como referencia para
**qué** verificar.

La etapa `test` del `Dockerfile` **se conserva sin cambios**: sigue siendo un camino válido para
correr la suite a mano (el README lo documenta y `deployment-docs.test.ts:320` lo exige). Lo que
cambia es la frase del README que dice que *"quien la corre es el pipeline"*.

#### Decisión 2: la imagen de release se **reconstruye** en el stage de release, no se retaggea

Hay dos patrones en los repos de referencia:

- `mattermost-integration`: el build **publica** `:$CI_PIPELINE_ID` en el registry y el release lo
  retaggea.
- `mail-integration`: el release **reconstruye** `--target production` con `--cache-from`.

**Decisión: reconstruir** (patrón `mail-integration`). El stage `build` construye `--target
production` **sin publicarla**. Eso cubre CA-8: si la imagen no se construye, no corren los tests
ni el release. El release la vuelve a construir desde el mismo commit y el mismo lockfile, con
cache.

**Por qué:** publicar `:$CI_PIPELINE_ID` en cada push de feature y en cada MR llena el registry de
tags por pipeline. Son justamente los tags inmutables que el RF-9 deja fuera de alcance, y
obligarían a configurar una cleanup policy. Con la reconstrucción, **las ramas de feature y los MR
no escriben nada en el registry**, lo que hace que CA-10 valga por construcción y no dependa de
una regla.

**El costo, aceptado:** la imagen se construye tres veces por pipeline de `dev`/`main` (build,
`docker-image.test.ts` y release). La segunda y la tercera reusan capas. Lo publicado es el mismo
`Dockerfile` sobre el mismo commit y el mismo `package-lock.json` que la suite verificó (`npm ci`,
nunca `npm install`, que es lo que S-006 fijó por esta razón).

#### Decisión 3: `TMPDIR` dentro del checkout, para que los `-v` de los tests de imagen funcionen con dind

`test/docker-image.test.ts:340-350` monta la key y el creds con `-v ${VALID_KEY_FILE}:/run/secrets/...`,
y esas rutas salen de `mkdtemp(join(tmpdir(), 'jiku-key-'))` (`auth-helpers.ts:215, 243`). Con
`docker:dind`, **el daemon corre en otro contenedor**: un `-v /tmp/jiku-key-xxx` se resuelve contra
el sistema de archivos del contenedor `dind`, donde esa ruta no existe. Docker crea un directorio
vacío en su lugar y el test falla sin explicar por qué.

Lo que el job y el servicio `dind` **sí** comparten en el executor Docker de GitLab es el volumen de
builds (`/builds/...`). **Decisión:** el job de test define `TMPDIR: $CI_PROJECT_DIR/.ci-tmp` y lo
crea en `before_script`. `os.tmpdir()` respeta `TMPDIR`, así que **ningún test cambia**. Y `.ci-tmp`
entra al `.dockerignore`, así las keys de prueba no viajan en el contexto del `docker build` que
hace `docker-image.test.ts`.

**Fallback, si en la primera corrida el volumen no resultara compartido:** reemplazar los dos `-v`
de `docker-image.test.ts` por `docker create` + `docker cp` + `docker start -a`. Cambia un test,
no el código. Queda **documentado como riesgo**, no se hace de entrada.

#### Decisión 4: Testcontainers contra `dind` por variables de entorno, sin tocar código

Testcontainers resuelve el daemon desde `DOCKER_HOST` y `getHost()` devuelve el host de esa URL
(`docker`), así que `nats://docker:<puerto-mapeado>` es alcanzable desde el job. El job de test
define:

```yaml
DOCKER_HOST: tcp://docker:2376
DOCKER_TLS_CERTDIR: "/certs"
DOCKER_TLS_VERIFY: "1"
DOCKER_CERT_PATH: "/certs/client"
TESTCONTAINERS_HOST_OVERRIDE: docker   # explícito, aunque se derive de DOCKER_HOST
```

El `docker-cli` del job usa las mismas variables, así que `spawnSync('docker', ...)` y
`docker ps` apuntan al mismo daemon que Testcontainers. Eso es lo que `shared-container.test.ts`
necesita para contar **un solo** NATS.

`auth-helpers.ts:97-100` fija el puerto del host con un `freeHostPort()` que se le pregunta al SO
**del job**, no al del daemon. Con un `dind` nuevo por job no hay colisión. Se registra como riesgo
bajo.

#### Decisión 5: "sólo docs" se expresa como **allowlist** de rutas de código

GitLab `rules:changes` no admite negación (no hay equivalente a `paths-ignore`). La regla de
`workflow` corre el pipeline **sólo si cambió alguna de estas rutas**:

```yaml
.code-changes: &code-changes
  - src/**/*
  - test/**/*
  - scripts/**/*
  - vendor/**/*
  - package.json
  - package-lock.json
  - tsconfig*.json
  - vitest.config.ts
  - Dockerfile
  - .dockerignore
  - version.txt
  - .gitlab-ci.yml
```

`.gitlab-ci.yml` está en la lista **a propósito**, igual que en core (*"editing CI must still run
CI"*). Y `version.txt` también, porque un bump de versión tiene que publicar.

**El riesgo de una allowlist** es que un archivo nuevo en la raíz quede afuera y no dispare CI.
**Mitigación:** `test/gitlab-ci.test.ts` lista las entradas de la raíz del repo y exige que cada una
esté en la allowlist o en una lista explícita de exclusiones (`docs`, `*.md`, `.claude`, `.git*`,
`node_modules`, `dist`, `.env*`). Un archivo nuevo que nadie clasificó rompe la suite.

**Semántica de GitLab, registrada:** en el **primer push de una rama nueva** `changes` evalúa
siempre a verdadero, así que el pipeline corre aunque el commit sea sólo de docs. Es conservador y
se acepta. En los MR, `changes` compara contra la rama destino.

#### Decisión 6: sin pipelines duplicados, pero **nunca** suprimir los de `dev` y `main`

"Push y merge request" produce, con una rama que tiene un MR abierto, **dos pipelines por push**
(uno de rama y uno de MR). Eso duplica la carga de `dind`. La regla estándar de GitLab suprime el de
rama cuando hay un MR abierto (`$CI_OPEN_MERGE_REQUESTS`), **pero aplicada tal cual rompería
CA-3**: con un MR `dev → main` abierto, un push a `dev` no correría el pipeline de rama y **no se
publicaría `:dev`**.

**Decisión:** suprimir el pipeline de rama sólo si hay MR abierto **y la rama no es `dev` ni
`main`**. Los tags de git (`$CI_COMMIT_TAG`) no disparan pipeline: el release sale de `main`, no de
tags (RF-5).

#### Decisión 7: el release no se cancela a mitad y se serializa por tag

Siguiendo a core (`dev-images.yml`: *"a run in flight is not cancelled, so the registry never keeps
half of one build and half of another"*):

- Los jobs de `build` y `test` son `interruptible: true`. Si se activa "Auto-cancel redundant
  pipelines" en el proyecto, un push nuevo cancela la verificación vieja.
- Los jobs de release son `interruptible: false` y llevan `resource_group` (`release-dev` /
  `release-main`). Así dos pipelines de `dev` seguidos nunca publican en paralelo, y el orden de
  publicación sigue el orden de los pipelines.

#### Decisión 8: la versión se valida antes de construir nada (CA-9)

```sh
test -f version.txt || { echo "version.txt no existe: no se publica nada"; exit 1; }
VERSION="$(tr -d '[:space:]' < version.txt)"
echo "$VERSION" | grep -Eq '^[0-9]+\.[0-9]+\.[0-9]+([-.][0-9A-Za-z.-]+)?$' \
  || { echo "version.txt no es una version valida: '$VERSION'"; exit 1; }
```

Se valida **antes** del `docker build` y del login. Si falla, no se publica ni el tag de versión
ni `:master`, que es lo que CA-9 exige ("ni solo con `:master`"). El `tr -d` tolera el salto de
línea final y un CRLF. La regex exige forma semver, con sufijo opcional (`0.2.0-rc1`). Esto rechaza
también un `version.txt` que diga `dev` o `master` y pisaría un tag móvil.

Los dos tags se **construyen juntos** (`-t :$VERSION -t :master`) y se publican en ese orden: la
versión primero y el tag móvil después, así un fallo entre los dos pushes nunca deja `:master`
apuntando a una imagen sin versión.

### Diseño del pipeline

Esqueleto del `.gitlab-ci.yml`. La story fija los detalles y los pines exactos de imagen.

```yaml
stages: [build, test, release]

workflow:
  rules:
    - if: $CI_COMMIT_TAG
      when: never
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: *code-changes
    - if: $CI_PIPELINE_SOURCE == "push" && $CI_OPEN_MERGE_REQUESTS && $CI_COMMIT_BRANCH !~ /^(dev|main)$/
      when: never
    - if: $CI_PIPELINE_SOURCE == "push"
      changes: *code-changes

variables:
  DOCKER_HOST: tcp://docker:2376
  DOCKER_TLS_CERTDIR: "/certs"
  DOCKER_TLS_VERIFY: "1"
  DOCKER_CERT_PATH: "/certs/client"

.dind:
  services: [docker:27-dind]

.npm-cache:
  cache:
    key: { files: [package-lock.json] }
    paths: [.npm/]

# ---------------------------------------------------------------- build
compile:                      # typecheck + build (CA-8)
  stage: build
  image: node:22-alpine
  extends: .npm-cache
  interruptible: true
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run typecheck
    - npm run build

image:                        # la imagen de produccion se construye (CA-8); no se publica
  stage: build
  image: docker:27-cli
  extends: .dind
  interruptible: true
  script:
    - docker build --target production -t jiku-mail-connector:ci .

# ---------------------------------------------------------------- test
test:                         # suite completa: NATS real + tests que construyen la imagen (CA-1, CA-2)
  stage: test
  image: node:22-alpine
  extends: [.dind, .npm-cache]
  interruptible: true
  needs: [compile, image]
  variables:
    TMPDIR: $CI_PROJECT_DIR/.ci-tmp
    TESTCONTAINERS_HOST_OVERRIDE: docker
  before_script:
    - apk add --no-cache docker-cli
    - mkdir -p "$TMPDIR"
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run test:teardown   # la suite + la verificacion de teardown (TS-22)

# ---------------------------------------------------------------- release
.release:
  stage: release
  image: docker:27-cli
  extends: .dind
  interruptible: false
  needs: [test]
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"

release:dev:                  # CA-3
  extends: .release
  resource_group: release-dev
  rules:
    - if: $CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "dev"
  script:
    - docker pull "$CI_REGISTRY_IMAGE:dev" || true
    - docker build --target production --cache-from "$CI_REGISTRY_IMAGE:dev"
        --build-arg BUILDKIT_INLINE_CACHE=1 -t "$CI_REGISTRY_IMAGE:dev" .
    - docker push "$CI_REGISTRY_IMAGE:dev"

release:main:                 # CA-4, CA-9
  extends: .release
  resource_group: release-main
  rules:
    - if: $CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"
  before_script:
    - <validacion de version.txt de la Decision 8>    # ANTES del login y del build
    - !reference [.release, before_script]
  script:
    - docker pull "$CI_REGISTRY_IMAGE:master" || true
    - docker build --target production --cache-from "$CI_REGISTRY_IMAGE:master"
        --build-arg BUILDKIT_INLINE_CACHE=1
        -t "$CI_REGISTRY_IMAGE:$VERSION" -t "$CI_REGISTRY_IMAGE:master" .
    - docker push "$CI_REGISTRY_IMAGE:$VERSION"
    - docker push "$CI_REGISTRY_IMAGE:master"
```

**`npm run test:teardown` y no `npm test`:** es la suite completa **más** la verificación de que
el NATS del `globalSetup` no quedó corriendo (`scripts/verify-teardown.mjs`). En local es un paso
opcional porque requiere acordarse de correrlo; en CI no cuesta nada y es la única forma de
observar el teardown. Si falla sólo la verificación de teardown, el pipeline queda en rojo, que es
lo correcto.

**Por qué `compile` e `image` son dos jobs paralelos del stage `build`:** necesitan imágenes base
distintas (Node vs Docker CLI), y el fallo de cualquiera de los dos corta el stage de test por
`needs` (CA-8).

### Verificación del pipeline (`test/gitlab-ci.test.ts`)

Siguiendo el precedente de `test/dockerfile.test.ts` (propiedades **declarativas** del empaquetado,
leídas del archivo, sin Docker), el test afirma sobre el texto del `.gitlab-ci.yml`, **sin agregar
una dependencia YAML**:

| # | Propiedad | CA |
|---|-----------|----|
| 1 | Existen los stages `build`, `test`, `release`, en ese orden | RF-1 |
| 2 | El job de test corre `npm run test:teardown` (o `npm test`), **no** un subconjunto (`--exclude`, `test:ci`, filtros de archivo) | CA-1, RF-2 |
| 3 | El job de test usa `node:22-alpine`, el mismo major que el `FROM` del `Dockerfile` | Decisión 1 |
| 4 | El job de test declara el servicio `docker:*-dind` y `TMPDIR` bajo `$CI_PROJECT_DIR` | Decisiones 3-4 |
| 5 | `release:dev` y `release:main` tienen `needs: [test]` y sus `rules` nombran exactamente `dev` y `main` | CA-3, CA-4, CA-7, CA-10 |
| 6 | Ningún job fuera de `release:*` ejecuta `docker push` ni `docker login` | CA-10, Decisión 2 |
| 7 | `release:main` valida `version.txt` **antes** del primer `docker build` | CA-9 |
| 8 | `.gitlab-ci.yml` y `version.txt` están en la allowlist de `changes` | Decisión 5 |
| 9 | Cada entrada de la raíz del repo está en la allowlist o en la lista de exclusiones | Decisión 5 |
| 10 | `version.txt` existe, es una sola línea semver, y **no se exige** que coincida con `package.json#version` | CA-5, RF-7 |
| 11 | `.dockerignore` contiene `.ci-tmp` | Decisión 3 |

**Lo que este test no puede afirmar** (la regla de `workflow` en ejecución, que el registry reciba
los tags) se verifica con las corridas reales de la story. Ver §Plan de verificación en GitLab.

### Flujo de Interacción

#### Escenario A: push a una rama de feature o MR (CA-1, CA-2, CA-6, CA-8, CA-10)

**Trigger:** `git push` a `feature/S-0xx_*`, o apertura/actualización de un MR contra `dev`/`main`.

1. **GitLab: `workflow:rules`**
   - Tag de git → no hay pipeline.
   - MR → pipeline de MR si cambió alguna ruta de la allowlist (CA-2, CA-6).
   - Push con MR abierto y rama ≠ `dev`/`main` → no hay pipeline de rama; ya corre el del MR
     (Decisión 6).
   - Push → pipeline si cambió alguna ruta de la allowlist. Si el cambio es sólo docs, no hay
     pipeline (CA-6).
2. **Stage `build`** (paralelo)
   - `compile`: `npm ci` → `npm run typecheck` → `npm run build`.
   - `image`: `docker build --target production`.
   - Si alguno falla → el pipeline queda en rojo y `test` no corre (CA-8).
3. **Stage `test`**
   - `test`: `npm ci` → `npm run test:teardown`, con `dind` como daemon. La suite levanta
     `nats:2.10-alpine` (globalSetup), `nats:2.11-alpine -js` (tests del KV) y construye
     `jiku-mail-connector:vitest` (`docker-image.test.ts`).
4. **Stage `release`**
   - Ningún job cumple sus `rules` → no corre nada (CA-1, CA-10).

**Outcome:** el resultado del pipeline queda visible en el commit y en el MR (CA-2), y el registry
no cambia (CA-10).

#### Escenario B: push a `dev` (CA-3, CA-7)

1-3. Igual que A (la regla de Decisión 6 no suprime `dev`).
4. **`release:dev`** (`needs: [test]`, `resource_group: release-dev`)
   - `docker login` con el token del job.
   - `docker build --target production --cache-from :dev` → `-t $CI_REGISTRY_IMAGE:dev`.
   - `docker push :dev`. Reemplaza al anterior (CA-3).
   - Si `test` falló, `release:dev` no corre y `:dev` sigue apuntando a la imagen anterior (CA-7).

#### Escenario C: push a `main` (CA-4, CA-7, CA-9)

1-3. Igual que A.
4. **`release:main`** (`needs: [test]`, `resource_group: release-main`)
   - Valida `version.txt` (Decisión 8). Si falta, está vacío o no es semver → `exit 1` antes del
     login y del build. No se publica nada (CA-9).
   - `docker build` con `-t :$VERSION -t :master` → `push :$VERSION` → `push :master` (CA-4).
   - Si `version.txt` no cambió respecto del release anterior, el tag de versión se sobrescribe
     (supuesto aceptado en el request).

**Manejo de errores:**

| Falla | Dónde | Efecto |
|-------|-------|--------|
| Typecheck/build | `compile` | Rojo; `test` y `release` no corren (CA-8) |
| La imagen no se construye | `image` | Rojo; `test` y `release` no corren (CA-8) |
| Un test falla | `test` | Rojo; `release:*` no corre; tags intactos (CA-7) |
| Docker/dind no disponible | `test` | Rojo, con el mensaje de `global-setup.ts`: *"Docker es una precondicion..."*. El envoltorio de error ya existe |
| `version.txt` ausente/vacío/inválido | `release:main` | Rojo antes de construir; nada publicado (CA-9) |
| Push al registry falla entre `:$VERSION` y `:master` | `release:main` | Rojo; queda publicada la versión y `:master` sigue en la anterior. Se reintenta el job |

### Consideraciones Técnicas

#### Riesgos

1. **`version.txt` ya existe con `0.0.1` (resuelto).** El archivo está en el working tree, sin
   versionar, con `0.0.1`. Se confirmó el valor del request: **`0.1.0`**. La story lo reescribe y lo
   versiona.
2. **Volumen compartido con `dind`** (Decisión 3). Si el runner no comparte `/builds` con el
   servicio, los dos `-v` de `docker-image.test.ts` montan un directorio vacío. **Mitigación:** se
   verifica en la primera corrida de la story; el fallback (`docker cp`) está definido.
3. **Runner no privilegiado.** Sin `privileged = true`, `docker:dind` no arranca y ningún job de
   Docker corre. Los repos de referencia usan `dind` en la misma instancia, así que es improbable,
   pero es la primera cosa que falla y el error de GitLab es claro.
4. **Duración.** La suite construye la imagen y levanta contenedores. Se esperan varios minutos por
   pipeline (el `beforeAll` de `docker-image.test.ts` ya admite 600 s). Aceptado: el request pide
   la suite completa.
5. **Allowlist desactualizada** (Decisión 5). Mitigada por la propiedad #9 del test.
6. **Un cambio sólo de docs puede romper un test de docs sin que CI lo vea.** Hay cuatro archivos
   de test que leen `docs/**` y `README.md`, y un cambio que toca sólo `*.md` no dispara el
   pipeline (CA-6). El rojo aparece en el siguiente push de código. **Aceptado por el request**
   (*"como en core"*), pero se registra porque en core ningún test lee docs y acá sí.
7. **Pull-rate de Docker Hub.** `node:22-alpine`, `docker:27-*` y los `nats:*` salen de Docker Hub.
   Si el runner no tiene mirror, un límite de pulls puede dar un rojo que no es del código. Se
   registra; no se mitiga en este request.

#### Dependencias

- Runner de GitLab con executor Docker privilegiado y Container Registry habilitado en el proyecto.
- Ninguna dependencia con otras stories abiertas.

#### Performance

- Cache de npm por `package-lock.json` (`.npm/`) en `compile` y `test`.
- `--cache-from` + `BUILDKIT_INLINE_CACHE=1` en el release (patrón `mail-integration`).
- `interruptible: true` en verificación, para que un push nuevo cancele la corrida vieja si el
  proyecto activa el auto-cancel.

#### Seguridad

- **Sin secretos nuevos:** el login usa `$CI_REGISTRY_USER` / `$CI_REGISTRY_PASSWORD` del job,
  con `--password-stdin` (no `-p`, que queda en el log de procesos).
- Las ramas de feature y los MR **no hacen login al registry** (Decisión 2), así que un MR desde
  un fork o una rama no confiable no puede publicar.
- Las keys RSA y el creds que generan los tests son de prueba (`generateServiceAccountKeyFile()`),
  viven en `.ci-tmp` y quedan fuera del contexto de build por el `.dockerignore`.
- La imagen publicada es la de S-006 sin cambios: no-root, sin secretos, sin devDependencies. Y
  `docker-image.test.ts` lo reverifica en cada pipeline antes del release.
