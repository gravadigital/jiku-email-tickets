# Story Plan: S-002 (jiku-mail-connector) - Configuración tipada con fail-fast

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-002](../stories/S-002.configuracion-tipada-fail-fast.md)
- **Service:** jiku-mail-connector
- **Summary:** Construye el módulo único de configuración del worker: un `src/config/` que valida
  todo el entorno al arrancar con Zod + `@t3-oss/env-core`, corta el proceso con la lista completa de
  lo que falta, e integra `loadConfig()` del SDK para no duplicar sus defaults. Es el único lugar del
  servicio que toca `process.env`.

**Patrones vigentes:**

- **Errores:** jerarquía con `AppError` abstracta como base; nunca `throw new Error(...)` desde
  código de dominio. Convención `error-handling`.
- **Validación:** Zod, `safeParse` sobre `parse`, tipos **inferidos** del schema con `z.infer` —
  nunca escritos a mano en paralelo. Convención `validation`.
- **Testing:** Vitest. Unit tests para lógica pura (que es todo lo de esta story), integración contra
  NATS real sólo para el camino de publicación. Convención `testing` (custom del servicio).
- **Logging:** Pino a stdout con `redact`. **Es S-003, no esta story.** Esta story sólo declara y
  valida `LOG_LEVEL`; no construye el logger. Los mensajes de fallo de configuración salen por
  `stderr` directo, porque el logger todavía no existe cuando la validación corre.

### Convenciones activas relevantes

#### `_base` (Node) — siempre activa

- TypeScript obligatorio, `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022+`.
- Sin `any` salvo en fronteras con librerías sin tipos, y comentando la razón.
- Nombres: archivos y carpetas `kebab-case`; clases y tipos `PascalCase` sin prefijo `I`; funciones y
  variables `camelCase`; constantes globales `SCREAMING_SNAKE_CASE`.
- **Variables de entorno:** todas se cargan y validan **en un solo lugar** (`src/config/env.ts`).
  Validación al arrancar (fail fast). El resto del código consume el objeto tipado, no `process.env`.
  Las variables sensibles nunca se loguean.
- Orden de imports: librerías externas → imports absolutos del proyecto → relativos del mismo módulo,
  separados por línea en blanco.
- Comentarios: por defecto ninguno. Comentar **sólo el porqué** cuando no es obvio.
- `async/await` sobre `.then()`.

#### `env-config` (`@t3-oss/env-core`)

Reglas verbatim de la convención:

- Nunca llamar a `process.env.VAR` fuera de `src/config/env.ts`. Importar `env` en todos lados.
- Todas las variables deben estar declaradas y validadas en `env.ts`. Sin variables sin declarar.
- Las variables sensibles (secretos, keys) llevan una restricción mínima de longitud (al menos
  `z.string().min(1)`).
- Castear numéricas y booleanas con `z.coerce` — llegan como string del entorno.
- El servicio debe fallar **al arrancar** (no en el primer uso) si falta una requerida.
- Commitear `.env.example` listando todas las requeridas con valores vacíos y un comentario corto.
- `.env.local` y `.env.test` van al gitignore.
- Los secretos nunca se commitean: vienen del entorno de ejecución.

> **DESVIACIÓN REGISTRADA — `emitErrors: true` no existe en la versión instalada.**
> La convención muestra `createEnv({ ..., emitErrors: true })`. En `@t3-oss/env-core@0.13.11` esa
> opción **no existe**; la API es `onValidationError?: (issues: readonly StandardSchemaV1.Issue[]) => never`.
> El comportamiento que la convención busca (agregar todos los issues) **sí se cumple igual**: se
> verificó empíricamente que con 4 variables inválidas el handler recibe los 4 issues en **una sola
> llamada**, no uno por vez. Lo que NO sirve es el handler por defecto — ver "Integration Points".

#### `validation` (Zod)

- Nunca confiar en datos `unknown` de afuera sin pasarlos por un schema. **Incluye las env vars.**
- **Los schemas son la fuente de verdad de los tipos.** Si cambia el schema, cambia el tipo.
- Composición sobre duplicación: `.partial()`, `.omit()`, `.pick()`, `.extend()`.
- Para env vars, validar al arrancar el servicio.

#### `error-handling`

```ts
// src/shared/errors/base.ts
export abstract class AppError extends Error {
  abstract readonly code: string;
  abstract readonly httpStatus: number;
  readonly details?: Record<string, unknown>;

  constructor(message: string, details?: Record<string, unknown>) {
    super(message);
    this.name = this.constructor.name;
    this.details = details;
  }
}
```

Reglas verbatim:

- Siempre lanzar errores específicos. Nunca `throw new Error("...")` en código de dominio.
- Los `code` son **parte del contrato público**. Cambiar uno es un breaking change.
- **No incluir información sensible en `message` ni en `details`** (passwords, tokens, datos de otros
  usuarios, internals).
- Cada error tiene **un lugar canónico** donde se lanza. Si el mismo error puede surgir en N lugares,
  extraer un helper.

> **NOTA sobre `httpStatus`:** la clase base lo declara `abstract` aunque este servicio no expone HTTP
> (ADR-001). Se implementa igual para no divergir de la convención; su valor no se consume en ningún
> lado. `ConfigValidationError` usa `500` porque una configuración inválida es un fallo del despliegue,
> no del input de un cliente.

#### `module-imports` (custom del servicio) — **la más fácil de romper**

Mecanismo: subpath imports nativos de Node (`#`), declarados **dos veces apuntando a árboles
distintos**:

```jsonc
// package.json — RUNTIME, apunta a dist/
"imports": {
  "#config/*": "./dist/config/*",
  "#domain/*": "./dist/domain/*",
  "#infra/*":  "./dist/infra/*",
  "#shared/*": "./dist/shared/*"
}
```

```jsonc
// tsconfig.json — COMPILACIÓN, apunta a src/
"paths": {
  "#config/*": ["./src/config/*"],
  "#domain/*": ["./src/domain/*"],
  "#infra/*":  ["./src/infra/*"],
  "#shared/*": ["./src/shared/*"]
}
```

Reglas verbatim:

- Los imports intra-proyecto DEBEN usar un prefijo declarado en `package.json#imports`. Nunca rutas
  relativas que suban directorios (`../../`).
- Todo prefijo en `package.json#imports` DEBE tener contraparte en `tsconfig.json#paths`, y viceversa.
- Los dos lados DEBEN apuntar a árboles distintos: `paths` a `./src/*`, `imports` a `./dist/*`.
- El especificador DEBE llevar extensión `.js` explícita, **incluso desde archivos `.ts`**.
- Un prefijo nuevo DEBE agregarse a los dos archivos en el mismo cambio.
- **La resolución en runtime DEBE verificarse ejecutando el `dist/` compilado**, no con `tsc --noEmit`
  solo: un mapeo roto pasa el typecheck y falla al arrancar.
- Paquetes de reescritura (`tsc-alias`, `module-alias`) y loaders ESM custom NO deben agregarse.

Los cuatro prefijos ya existen; esta story **no agrega ninguno** (`#config/` y `#shared/` ya están
declarados). Ejemplo de import correcto:

```ts
import { SERVICE_NAME } from '#shared/service-info.js';
```

#### `testing` (custom del servicio)

Lo que aplica a esta story:

- **Los unit tests son para funciones puras.** Toda la lógica de esta story es pura: schema,
  formateo del error, resolución de la config. **Ningún test de esta story arranca el contenedor NATS.**
- Tests co-locados con el código o bajo `test/`, con sufijo `.test.ts`.
- `describe` nombra la unidad bajo prueba; `it` nombra el escenario. **Ambos en inglés llano.**
- Los tests no deben depender de env vars del host ni de servicios externos.
- Resetear mocks entre tests con `vi.clearAllMocks()` / `vi.unstubAllGlobals()`.
- Regla directa de la convención, sección "Integration with other conventions":
  > **env-config**: the fail-fast startup validation gets its own test per required variable — a
  > missing variable must abort with the **complete** list, not one at a time.
- **Mantener la salida de log de los tests callada** (`LOG_LEVEL=silent`), pero nunca silenciar los
  errores globalmente.

> **CUIDADO con el aislamiento del entorno.** Los tests de esta story manipulan el entorno. La regla
> "los tests no deben depender de env vars del host" obliga a que la función bajo prueba **reciba el
> entorno como parámetro** en vez de leer `process.env` directamente. Ver "Implementation Notes" de T3.

### Relevant ADRs

#### ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus

**Decisión:** Se consume `@gravadigital/jiku` `^1.0.0`. El conector no implementa nada del protocolo
del bus. Delega: construcción del subject, envelope, hash del prefijo de inbox, obtención y refresh
del token, entrega del token como getter, y traducción de errores a clases tipadas.

**Implementation Rules (verbatim):**

- El cliente del bus MUST ser `@gravadigital/jiku` en rango `^1.0.0`
- El proyecto MUST NOT declarar `nats` como dependencia directa
- El conector MUST NOT construir subjects a mano: el subject se arma con `client.command()`, nunca con
  concatenación de strings
- El conector MUST NOT armar ni parsear envelopes del protocolo a mano
- El conector MUST NOT fijar `inboxPrefix` por su cuenta: lo fija el SDK siempre
- La identidad MUST construirse con `ServiceUser.fromKeyFile()` — no con un token obtenido a mano ni
  con un JWT armado en el conector
- `connect()` MUST llamarse **exactamente una vez** al arrancar el proceso, y el cliente resultante
  MUST conservarse por toda la vida del proceso. Prohibido conectar por mail o por tick
- El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), **nunca** de una variable
  de entorno
- **La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los defaults a mano**
- **El timeout MUST quedar en el default del SDK (15000 ms). MUST NOT bajarse** — ver ADR-006
- `onTokenError` MUST estar registrado y MUST loguear el fallo del refresh como `error` sin terminar
  el proceso
- El runtime MUST ser Node.js **≥ 22.12** (el `engines` floor del SDK es parte de su superficie
  pública: subirlo es un major)
- El proyecto MUST usar **ESM** (`"type": "module"`): el SDK es ESM-only
- Los errores del bus MUST manejarse por las clases del SDK (`JikuPermissionDenied`, `JikuFailure`,
  `JikuTimeout`, `JikuNoEndpoint`, `JikuInvalidRequest`), no inspeccionando strings de mensaje

**Qué toca esta story:** sólo las dos reglas en negrita (`loadConfig()` y el timeout). Las demás son de
S-004/S-005. **Esta story no conecta a nada.**

#### ADR-005: Identidad como machine user de Zitadel

**Implementation Rules relevantes a esta story (verbatim):**

- **`JIKU_PROJECT_ID` MUST estar configurado y MUST validarse al arrancar. Sin él el token no lleva el
  claim de roles y no conecta a nada (el error dice sólo `Authorization Violation`)**
- **La key JSON MUST leerse de un archivo montado read-only. MUST NOT estar horneada en la imagen ni
  pasarse por variable de entorno**
- **El creds del sentinel de NATS MUST montarse como archivo read-only**
- El access token MUST vivir **sólo en memoria**. MUST NOT escribirse a disco ni loguearse
- El `user-id` del subject MUST salir de `auth.userId` (derivado de la key). MUST NOT leerse de una
  variable de entorno

**Consecuencia directa para T2:** `JIKU_KEY_FILE` y `JIKU_CREDS` son **rutas a archivos**, no
contenido. Esta story valida que la ruta esté declarada y no vacía. Que el archivo exista, se pueda
leer y parsear es **S-004** — no agregar acceso a filesystem en el schema.

#### ADR-006: Observabilidad por logs

**Implementation Rules relevantes (verbatim):**

- El nivel por defecto MUST ser `info`, configurable por variable de entorno
- MUST NOT loguearse nunca: **credenciales (IMAP, key JSON, token, creds de NATS)**, tráfico IMAP
  crudo, el cuerpo del mail (`body`), el contenido de un adjunto
- El timeout del comando MUST quedar en **15000 ms** (el default del SDK). **MUST NOT bajarse**

#### ADR-001: Worker único sin persistencia

**Implementation Rules relevantes (verbatim):**

- El proyecto MUST ser un único proceso Node.js sin servidor HTTP: no expone puerto, no tiene
  framework web, no define rutas
- El proyecto MUST NOT declarar dependencias de acceso a base de datos: `pg`, `sequelize`,
  `sequelize-typescript`, `typeorm`, `prisma`, `knex` o equivalentes
- El proyecto MUST NOT declarar `@aws-sdk/client-s3` ni ningún cliente de storage con credenciales
- El proyecto MUST NOT persistir estado en disco: sin archivos de estado, sin SQLite, sin caché en
  disco, sin volumen montado de escritura

### Integration Points

#### `loadConfig()` del SDK — contrato real de la versión instalada

Importado de `@gravadigital/jiku/node`. Firma:

```ts
export declare function loadConfig(path?: string): Promise<LoadedConfig>;

export interface LoadedConfig {
  servers?: string | undefined;
  instance: string;                    // NO opcional: loadConfig lo defaultea a 'dev'
  credsFile?: string | undefined;
  timeoutMs?: number | undefined;
  name?: string | undefined;
  zitadel: ZitadelConfig;
  path: string | undefined;            // el archivo del que salió, o undefined si no había
}

export interface ZitadelConfig {
  issuer?: string;
  clientId?: string;
  projectId?: string;
  keyFile?: string;
}
```

**Lo que `loadConfig()` hace realmente** (leído de `node_modules/@gravadigital/jiku/dist/node/config.js`):

1. Lee `~/.config/jiku/config.yaml` si existe. **Un archivo ausente NO es un error** — el entorno solo
   alcanza, y es como lo hace un servicio en contenedor.
2. Aplica los overrides del entorno sobre el archivo. Las variables que lee, de la constante `ENV`:

   ```ts
   export declare const ENV: {
     readonly servers: "JIKU_SERVERS";      readonly instance: "JIKU_INSTANCE";
     readonly creds: "JIKU_CREDS";          readonly timeout: "JIKU_TIMEOUT";
     readonly issuer: "JIKU_ISSUER";        readonly clientId: "JIKU_CLIENT_ID";
     readonly projectId: "JIKU_PROJECT_ID"; readonly keyFile: "JIKU_KEY_FILE";
   };
   ```

3. Expande `~` en las rutas de `creds` y `keyFile`.
4. Parsea el timeout con `parseTimeout()`, que acepta **milisegundos** (`15000`) **o duración**
   (`15s`, `1m30s`). Un valor que no es ninguna de las dos formas **lanza `JikuError`**.
5. Defaultea **únicamente `instance` a `'dev'`**.

**Lo que `loadConfig()` NO hace, y por eso el schema Zod es imprescindible:**

| No hace | Consecuencia |
|---|---|
| No exige **nada** | `credsFile`, `timeoutMs`, `zitadel.*` vuelven `undefined` sin protestar. **CA-2 y CA-3 no se cumplirían solos** |
| No aplica el default de `servers` | `DEFAULT_SERVERS = 'nats://localhost:4222'` existe en el SDK pero lo aplica `resolveOptions()` en el `connect()`, no `loadConfig()` |
| No aplica default de `issuer` | Deliberado del SDK: *"there is no sensible one... a library that guessed would either point at somebody else's or at a host that does not exist"* |
| No aplica piso al timeout | `resolveOptions()` sólo reemplaza valores `<= 0` por `DEFAULT_TIMEOUT_MS`. **Un `JIKU_TIMEOUT=5000` pasa tal cual** |

**Cómo conviven las dos capas (CA-1 + CA-7).** `loadConfig()` **sí** lee `process.env`, pero lo hace
**adentro del SDK**, no en código del conector. La propiedad de CA-1 —`grep process.env src/` devuelve
un solo archivo— se mantiene, y se cumple CA-7 llamándolo dentro de `src/config/`.

**Precedencia por valor, la tabla que T4 tiene que respetar:**

| Valor de `AppConfig` | Fuente que manda | Por qué |
|---|---|---|
| `credsFile` | `loadConfig().credsFile` | Expande `~`; el schema sólo garantiza que la variable esté declarada |
| `keyFile` | `loadConfig().zitadel.keyFile` | Ídem |
| `zitadelProjectId` | `loadConfig().zitadel.projectId` | Del SDK, ya normalizado |
| `instance` | `loadConfig().instance` | **El SDK ya defaultea a `'dev'`.** Redeclararlo violaría CA-7 |
| `servers` | **schema Zod** | `loadConfig()` no aplica el default; el conector sí lo necesita resuelto |
| `issuer` | **schema Zod** | El SDK deliberadamente no defaultea; el conector sí sabe cuál es el suyo |
| `timeoutMs` | **schema Zod (con piso)** | El piso de CA-5 es del conector, no del SDK |
| `logLevel` | **schema Zod** | El SDK no la conoce |
| `verifyProjectId` | **schema Zod** | El SDK no la conoce |

#### `@t3-oss/env-core@0.13.11` — API real y por qué hace falta un handler propio

La opción es `onValidationError`, no `emitErrors`:

```ts
/**
 * Called when validation fails. By default the error is logged,
 * and an error is thrown telling what environment variables are invalid.
 */
onValidationError?: (issues: readonly StandardSchemaV1.Issue[]) => never;
```

**Comportamiento por defecto, verbatim de `dist/index.js`:**

```js
const onValidationError = opts.onValidationError ?? ((issues) => {
    console.error("❌ Invalid environment variables:", issues);
    throw new Error("Invalid environment variables");
});
if (parsed.issues) return onValidationError(parsed.issues);
```

**Lo que se verificó empíricamente contra la versión instalada:**

- Con 3 requeridas ausentes + 1 con forma inválida, el handler se invoca **una sola vez con los 4
  issues**. La agregación que pide CA-2 funciona.
- Cada issue trae `path: ['NOMBRE_DE_LA_VARIABLE']` y un `message` descriptivo.
- Para `too_small` sobre un string, **el issue serializado no incluye el valor ofensor**.

**Por qué el handler por defecto igual no sirve, y son tres razones independientes:**

1. **No es "un solo mensaje" (CA-2).** Parte el reporte en dos: un `console.error` con el array crudo
   y un `Error` cuyo `message` es el genérico `"Invalid environment variables"` sin ningún nombre.
2. **Vuelca el objeto crudo (CA-10).** `console.error` con un array de issues lo inspecciona entero.
   No es un riesgo teórico: los issues de Zod 4 pueden llevar campos adicionales según el código de
   validación, y depender de que ninguno lleve el input es apoyarse en un detalle no contratado.
3. **No es testeable.** Un `Error` genérico obliga a los tests a hacer matching sobre stdout capturado
   en vez de sobre datos estructurados.

**Consecuencia:** T2 construye el handler. Es la pieza donde CA-2 y CA-10 se cumplen o no.

#### `emptyStringAsUndefined: true`

Recomendado por la propia librería, y acá es **necesario**: `JIKU_CREDS=` (vacío) en un `.env` mal
armado debe contar como ausente, no como el string vacío. Sin esta opción, un `.env` con la variable
declarada y vacía pasaría una validación laxa y fallaría más tarde al abrir el archivo — exactamente
el fallo diferido que la story existe para evitar.

Piso del timeout — el porqué va comentado en el código, lo pide CA-5:

```ts
// El servidor corta a los 10 s y PostgreSQL a los 8 s. Un timeout mas corto que el del servidor
// convierte un error explicado en un timeout mudo: el cliente se rinde antes de que el sistema
```

Forma del schema:

```ts
export const envSchema = {
  // Requeridas
  JIKU_CREDS: z.string().min(1),
  JIKU_KEY_FILE: z.string().min(1),
  JIKU_PROJECT_ID: z.string().min(1),
  JIKU_VERIFY_PROJECT_ID: z.coerce.number().int().positive(),
```

#### Technical Details

**Architectural Context References:**

- Convención `env-config`: `createEnv` con `runtimeEnv`; nunca `process.env` fuera de este archivo.
- Integration Points → `@t3-oss/env-core@0.13.11`: la opción es `onValidationError`, **no**
  `emitErrors`; el handler por defecto no sirve, por las tres razones documentadas ahí.
- Convención `module-imports`: importar `#config/schema.js` y `#config/errors.js` con extensión `.js`.

**Files to Create/Modify:**

- `src/config/env.ts` (crear)
- `test/config/env.test.ts` (crear)

**Implementation Notes:**

**La firma con `source` como parámetro es la decisión de diseño de esta tarea.** La convención
`testing` exige que "los tests no deben depender de env vars del host". Si `loadEnv()` leyera
`process.env` por dentro, cada test tendría que mutar el entorno global del proceso y restaurarlo, con
fugas entre tests que en Vitest —donde varios archivos comparten worker— aparecen como fallos
intermitentes. Recibiendo el entorno como parámetro, los tests pasan objetos literales y el archivo
sigue siendo el único que menciona `process.env`, una sola vez, en la línea que construye `env`:

```ts
export function loadEnv(source: Record<string, string | undefined>): Env {
  return createEnv({
    server: envSchema,
    runtimeEnv: source,
    emptyStringAsUndefined: true,
    onValidationError: (issues) => { throw toConfigValidationError(issues); },
  });
}

// La UNICA lectura de process.env en todo el servicio (CA-1).
export const env = loadEnv(process.env);
```

**Cuidado con el `export const env`:** se evalúa al importar el módulo, así que importar
`#config/env.js` **es** disparar la validación. Es el fail-fast que la story quiere, pero implica que
`test/config/env.test.ts` **no puede importar `env`** sin un entorno válido en el host. Los tests
importan **sólo `loadEnv`**. Vitest evalúa el módulo entero igual al importarlo, así que la
inicialización de `env` tiene que tolerar un entorno inválido durante los tests: **construir `env` de
forma perezosa** con un getter, o —más simple y sin trucos— dejar que `src/config/index.ts` (T4) sea
quien dispara la carga, y que `env.ts` exporte **sólo la función**.

**Resolución: `env.ts` exporta únicamente `loadEnv`.** La instancia única vive en T4, que ya es el
componedor de la configuración. Así `env.ts` se puede importar en un test sin efectos, y sigue siendo
el único archivo que menciona `process.env`... salvo que la lectura se mueva a T4, lo que rompería
CA-1. Para evitarlo: `env.ts` exporta también `loadEnvFromProcess()`, una función de una línea que
hace `return loadEnv(process.env)`. **`process.env` queda en `env.ts`, y nadie la evalúa al importar.**

```ts
/** La UNICA lectura de process.env del servicio (CA-1). Es una funcion, no una constante, para
 *  que importar este modulo no dispare la validacion — eso lo decide el arranque, no el import. */
export function loadEnvFromProcess(): Env {
  return loadEnv(process.env);
}
```

### Task 4: Integrar `loadConfig()` del SDK y exponer la configuración única

**Status:** Completed

#### Description

Compone la configuración final del proceso: invoca `loadConfig()` del SDK **dentro de `src/config/`** y
reexporta su resultado junto al `env` validado, como un único `AppConfig`. Es lo que hace que CA-1 y
CA-7 convivan: el SDK lee el entorno por su cuenta, pero lo hace adentro del SDK, así que el `grep` de
CA-1 sigue devolviendo un solo archivo del conector.

#### Acceptance Criteria

1. `src/config/index.ts` exporta `loadAppConfig(): Promise<AppConfig>` y el tipo `AppConfig`.
2. `loadConfig()` del SDK se invoca **exactamente una vez**, dentro de `src/config/index.ts`.
3. `AppConfig` expone: `servers`, `instance`, `credsFile`, `keyFile`, `zitadelProjectId`, `issuer`,
   `timeoutMs`, `verifyProjectId`, `logLevel`.
4. La precedencia por valor sigue exactamente la tabla de Integration Points.
5. `instance` proviene de `loadConfig()`, **no** del default del schema — el SDK ya lo defaultea a
   `'dev'` y redeclararlo violaría CA-7.
6. `verifyProjectId` es `number`.
7. Ningún default del SDK está copiado a mano fuera de `src/config/`.
8. `loadConfig()` no se invoca desde ningún otro archivo de `src/`.

#### Technical Details

**Architectural Context References:**

- ADR-002: *"La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los
  defaults a mano"*.
- ADR-005: `JIKU_PROJECT_ID` validado al arrancar; `keyFile` y `credsFile` son rutas a archivos
  montados read-only.
- Integration Points → `loadConfig()`: el contrato real, lo que NO hace, y **la tabla de precedencia
  por valor** — es la especificación de esta tarea.
- Convención `module-imports`: `@gravadigital/jiku/node` es un paquete externo, va en el primer grupo
  de imports.

**Files to Create/Modify:**

- `src/config/index.ts` (crear)
- `test/config/index.test.ts` (crear)

**Implementation Notes:**

Forma:

```ts
import { loadConfig } from '@gravadigital/jiku/node';

import { loadEnvFromProcess } from '#config/env.js';

export type AppConfig = { /* los 9 campos */ };

export async function loadAppConfig(): Promise<AppConfig> {
  // El env se valida PRIMERO: si falta algo, cortamos antes de tocar el filesystem que
  // loadConfig() lee para buscar ~/.config/jiku/config.yaml (CA-2: "no intenta conectar a
  // nada antes de fallar").
  const env = loadEnvFromProcess();
  const sdk = await loadConfig();

  return {
    servers: env.JIKU_SERVERS,
    instance: sdk.instance,
    credsFile: sdk.credsFile ?? env.JIKU_CREDS,
    keyFile: sdk.zitadel.keyFile ?? env.JIKU_KEY_FILE,
    zitadelProjectId: sdk.zitadel.projectId ?? env.JIKU_PROJECT_ID,
    issuer: sdk.zitadel.issuer ?? env.JIKU_ISSUER,
    timeoutMs: env.JIKU_TIMEOUT,
    verifyProjectId: env.JIKU_VERIFY_PROJECT_ID,
    logLevel: env.LOG_LEVEL,
  };
}
```

**Por qué los `??` y no tomar el valor del SDK a secas.** Para `credsFile`, `keyFile` y
`zitadelProjectId` el schema Zod ya garantizó que la variable está y no está vacía, así que
`loadConfig()` va a traerlas siempre. El `??` cubre el caso en que el SDK las devuelva `undefined` por
una razón que no controlamos, y **preserva el valor ya validado en vez de propagar un `undefined` a
S-004**. El del SDK va primero porque **expande `~`** en las rutas, que el schema no hace.

Para `issuer` la lógica es la inversa y vale la pena entenderla: el SDK **no defaultea** el issuer, así
que si el operador no configuró `JIKU_ISSUER`, `sdk.zitadel.issuer` viene `undefined` y el `??` cae al
default del schema (`https://id.grava.io`), que es exactamente lo que CA-4 pide. Si sí lo configuró,
ambos lados traen el mismo valor.

**El orden importa y es intencional:** `loadEnvFromProcess()` corre **antes** que `loadConfig()`.
`loadConfig()` lee el filesystem (busca `~/.config/jiku/config.yaml`) y puede lanzar `JikuError` si ese
archivo está mal formado. CA-2 pide que un entorno incompleto falle **sin intentar nada antes**, así
que la validación va primero.

**`AppConfig` se escribe a mano y eso NO contradice CA-9.** CA-9 exige que los tipos del *schema* se
infieran (`Env` con `z.infer`), y así es. `AppConfig` es un tipo de **composición** entre `Env` y
`LoadedConfig` del SDK — no duplica el schema, lo combina con un tipo externo. Definirlo
explícitamente es lo correcto: es el contrato que S-003, S-004 y S-005 van a consumir, y un tipo
inferido que cambie en silencio les rompería los tests.

**Dependencies:** `@gravadigital/jiku/node` (ya instalado), `#config/env.js`.

#### Testing Requirements

**Unit Tests:** TS-14, TS-12.

- Espiar `loadConfig` (con `vi.mock` sobre `@gravadigital/jiku/node`) y verificar **1 sola invocación**.
- `instance` sale del resultado de `loadConfig()`, no del schema: con `loadConfig` devolviendo
  `instance: 'prod'` y sin `JIKU_INSTANCE` en el entorno, `config.instance === 'prod'`.
- `issuer` cae al default del schema cuando `sdk.zitadel.issuer` es `undefined`.
- `credsFile` toma el valor **expandido** del SDK cuando difiere del crudo del entorno.
- **Orden:** con un entorno incompleto, `loadAppConfig()` rechaza con `ConfigValidationError` y
  `loadConfig` **no fue invocado**.

**Integration Tests:** ninguno — `loadConfig()` no toca la red.

**Manual Testing:** `grep -rn 'loadConfig' src/` devuelve sólo `src/config/index.ts`.

### Task 5: Cablear el arranque fail-fast en `src/index.ts`

**Status:** Completed

#### Description

Reemplaza el `bootstrap ok` de S-001 por el arranque real: la configuración se resuelve como **primer
efecto** del proceso, y un fallo corta con exit ≠ 0 imprimiendo la lista completa por `stderr`, sin
tocar la red.

#### Acceptance Criteria

1. `src/index.ts` importa `'dotenv/config'` como primera línea.
2. `loadAppConfig()` es el primer efecto del arranque, antes de cualquier otra inicialización.
3. Un `ConfigValidationError` se captura, se escribe `err.message` completo en `stderr`, y el proceso
   termina con `process.exitCode = 1`.
4. **No se escribe ningún valor de variable de entorno en `stderr`** — sólo `err.message`.
5. Con configuración válida el proceso termina con exit `0` y una línea de confirmación en `stdout`
   que **no contiene ninguna credencial ni ruta de secreto**.
6. `src/index.ts` no menciona `process.env` ni `loadConfig`.

#### Technical Details

**Architectural Context References:**

- Flow Context → Escenario B: *"el error corta el arranque; el proceso termina con exit ≠ 0"* y *"el
  proceso no queda vivo en un estado inútil"*.
- ADR-006: nunca loguear credenciales.
- Convención `env-config`: `import 'dotenv/config'` en el entry point.
- Convención `module-imports`: importar `#config/index.js` con extensión `.js`.

**Files to Create/Modify:**

- `src/index.ts` (modificar — reemplaza el contenido de S-001)

**Implementation Notes:**

```ts
import 'dotenv/config';

import { loadAppConfig } from '#config/index.js';
import { ConfigValidationError } from '#config/errors.js';
import { SERVICE_NAME } from '#shared/service-info.js';

async function main(): Promise<void> {
  const config = await loadAppConfig();

  // S-003 construye el logger y S-004 conecta al bus. En S-002 el arranque termina aca:
  // la configuracion resuelta ES el entregable, y que el proceso salga con 0 es la prueba
  // de que la validacion no corta un entorno valido.
  process.stdout.write(
    `${SERVICE_NAME}: configuracion valida (instance=${config.instance}, ` +
      `logLevel=${config.logLevel}, timeoutMs=${config.timeoutMs})\n`,
  );
}

main().catch((error: unknown) => {
  if (error instanceof ConfigValidationError) {
    process.stderr.write(`${error.message}\n`);
  } else {
    process.stderr.write(`${SERVICE_NAME}: fallo el arranque: ${String(error)}\n`);
  }
  process.exitCode = 1;
});
```

**Qué se imprime en el caso exitoso, y qué NO.** Sólo `instance`, `logLevel` y `timeoutMs` — tres
valores no sensibles. **Nunca** `credsFile`, `keyFile`, `zitadelProjectId` ni `servers`: las dos
primeras son rutas a secretos y las otras dos son topología del despliegue. ADR-006 prohíbe loguear
credenciales, y una ruta a un archivo de credenciales es información sobre dónde está el secreto.

**`process.exitCode = 1` en vez de `process.exit(1)`:** deja que Node drene los streams antes de
salir. Con `process.exit()` el mensaje de `stderr` se puede perder si el stream está bufferizado —
justamente el mensaje que la story existe para entregar.

**Dependencies:** `dotenv`, `#config/index.js`, `#config/errors.js`, `#shared/service-info.js`.

#### Testing Requirements

**Unit Tests:** ninguno propio — el comportamiento se verifica ejecutando el proceso (T6).

**Integration Tests:** TS-30 y TS-31 viven en T6, que es donde se compila el `dist/`.

**Manual Testing:**

1. `npm run build && node dist/index.js` sin variables → exit ≠ 0, las 4 variables en `stderr`.
2. Con `VALID_ENV` completo → exit `0` y la línea de confirmación.
3. Verificar a ojo que ningún valor de `JIKU_CREDS` ni `JIKU_KEY_FILE` aparece en ninguna salida.

## Notas de Implementación (globales)

### Desviaciones registradas respecto de la documentación

Tres. Las tres son de documentos de producto que asumen una API que la versión instalada no tiene, y
las tres están explicadas arriba con el detalle verificado:

1. **`emitErrors: true` no existe** en `@t3-oss/env-core@0.13.11`. La convención `env-config`, la story
   S-002 y el Paso 1 del flow lo mencionan. La opción real es `onValidationError`, y la agregación de
   issues que esos documentos buscan **se cumple igual**. → Actualizar el flow en el Step 6.5 de la
   implementación.
2. **`loadConfig()` no valida ni exige nada.** El flow sugiere que la config del bus "se lee con
   `loadConfig()`" sin aclarar que devuelve todo opcional. Por eso el schema Zod es imprescindible y no
   redundante.
3. **El piso de 15000 ms es del conector.** ADR-002 y ADR-006 dicen "el default del SDK, no bajarlo".
   El SDK sólo protege contra valores `<= 0`, así que un `JIKU_TIMEOUT=5000` pasaría. CA-5 va más
   lejos y eso lo implementa el schema.

### Decisiones tomadas durante la planificación

- **`JIKU_VERIFY_PROJECT_ID`** — el nombre de la variable del `projectId` de prueba (CA-8) no estaba
  declarado en ningún documento. Se fijó acá porque S-005 la consume. `VERIFY` la ata al modo de
  verificación, que es su único consumidor y su vida útil: cuando FG-3 traiga el Mapa de Tickets, el
  `projectId` saldrá del slug del mail y esta variable se retira.
- **Sin linter en esta story.** El repo no tiene ESLint ni Biome. Agregarlo desenfoca una story de
  configuración y generaría hallazgos en el código de S-001 que habría que arreglar acá. La
  verificación de calidad corre `typecheck` + `build` + `test`, que sí existen. Queda para S-006 o una
  story de tooling.
- **Sin `.env.dev` ni `.env.prod`.** Justificado en las Implementation Notes de T1.
