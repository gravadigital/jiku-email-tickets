# Story Plan: S-022 (jiku-mail-connector) - Propiedades del sistema completo y verificación e2e

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-022](../stories/S-022.propiedades-sistema-verificacion-e2e.md)
- **Service:** jiku-mail-connector
- **Summary:** Cierre del alcance v1 (FG-4 y REQ-004): afirmar con tests de propiedad sobre el
  **sistema completo** (no sólo los módulos puros de S-017 a S-021) el orden partición → dedup →
  tope, el tope no recalculado tras un fallo de `PUT`, el pico de memoria de un mail a la vez, que
  ningún log filtra contenido de adjunto ni `uploadUrl`, que ningún fallo de archivo cancela el
  requisito, y que dos mails idénticos producen descripciones idénticas; verificar de punta a punta
  (automatizado, sin instancia real de Jiku) el camino completo con un adjunto; y dejar los tres
  documentos de flujo, el overview, el README y el catálogo de código reusable al día. Sin código de
  producción nuevo salvo lo que los tests revelen.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`), Node.js **≥ 22.12** (impuesto por el SDK del bus).
- **Runtime:** worker único, sin servidor HTTP, sin puerto expuesto (ADR-001).
- **Dependencia central:** `@gravadigital/jiku` `^1.0.0` (ESM-only) — SDK oficial del bus NATS de Jiku.
- **Testing:** Vitest, contra un contenedor NATS real (Testcontainers) compartido por toda la suite; sin contenedor de base de datos (no hay ninguna).
- **Sin base de datos propia** (ADR-001): las entidades que el conector "crea" (Requisito, Archivo, Adjunto) las escribe `core`, no este servicio.
- **Módulos del dominio:** `ingesta`, `ruteo`, `publicacion`, `adjuntos` (los cuatro ya completos desde S-021; esta story no agrega un módulo nuevo).

### Service Architecture

```
src/
├── config/              # env.ts, schema.ts, index.ts, errors.ts — AppConfig completo
├── domain/
│   ├── ingesta/          # tick.ts (runTick/runIngestaTick), scheduler.ts, normalize.ts, ports.ts...
│   ├── ruteo/            # route-mail.ts (routeMail(), pura)
│   ├── adjuntos/         # particionar.ts, dedup.ts, tope.ts, procesar.ts, types.ts
│   └── publicacion/      # mail-payload.ts, description.ts, procesar-adjuntos-mail.ts,
│                         # publish-requirement.ts, upload-file.ts, upload-byte.ts, publish-errors.ts
├── infra/
│   ├── bus/              # identity.ts, connection.ts, errors.ts
│   └── imap/             # client.ts, errors.ts
└── shared/               # logger.ts, log-redaction.ts, shutdown.ts, motivo-descarte.ts, errors/
test/
├── global-setup.ts       # UN NATS de Testcontainers para toda la suite
├── bus/                  # helpers.ts (setupTestBus), responder.ts (respondTo — doble de `core`)
├── ingesta/               # tick.test.ts, tick-memory.test.ts, tick-redaction.test.ts, ...
├── publicacion/           # procesar-adjuntos-mail.test.ts, upload-file.test.ts, upload-byte.test.ts...
├── adjuntos/              # particionar.test.ts, dedup.test.ts, tope.test.ts, procesar.test.ts
└── fixtures/mails/        # .eml reales
```

**Patrón arquitectónico central:** un solo proceso, tres módulos internos (Ingesta, Ruteo,
Publicación) más el módulo `adjuntos`, comunicados por llamada de función directa dentro del mismo
proceso, secuencialmente, un mail a la vez (ADR-001). El **orquestador** que conecta partición/dedup/tope
(S-017) con el permiso de subida (S-018) y el `PUT` (S-019) es `procesarAdjuntosDelMail()`
(`src/domain/publicacion/procesar-adjuntos-mail.ts`), invocado desde `runTick()`
(`src/domain/ingesta/tick.ts`) **dentro de la misma iteración del mail**, antes de componer la
descripción final y publicar `requirements.new`.

**Error handling:** jerarquía de errores por clase, nunca por texto de mensaje (ADR-002). Las
funciones de dominio puras (`routeMail()`, `particionar()`, `deduplicar()`, `aplicarTope()`) **nunca
lanzan**: todo camino negativo es un valor de retorno tipado. Las funciones de publicación
(`requestFileUpload()`, `uploadFileContent()`, `procesarAdjuntosDelMail()`) tampoco lanzan para un
resultado de **negocio** (rechazo, fallo) — sólo `publishRequirementFromMail()` relanza `PublishError`,
que el tick captura y traduce a `counters.fallidos += 1`.

**Logging:** Pino, JSON a stdout siempre, objeto de contexto primero + mensaje estático segundo. Nunca
se loguea: credenciales, tráfico IMAP crudo, el cuerpo del mail, el contenido de un adjunto, ni la
`uploadUrl` prefirmada (ADR-006).

**Testing strategy:** unitarios para el núcleo puro (partición, dedup, tope, ruteo, composición);
integración contra el NATS real de Testcontainers con `Client.fromConnection()` para la publicación;
IMAP y el `PUT` prefirmado se doblan en el borde (interfaz `MailSource` y `fetch` stub /
servidor HTTP real de test respectivamente); `core` se dobla con un responder **en el propio test**
sobre el bus real (`test/bus/responder.ts`), nunca mockeando el bus.

### Relevant ADRs

**ADR-001: Worker único sin persistencia propia**

- **Decisión:** un solo servicio, sin base de datos, sin estado persistido. El único mecanismo de
  idempotencia es el flag `\Seen` de IMAP. Los tres módulos internos son partes del mismo proceso,
  comunicados por llamada de función, secuencialmente, un mail a la vez.
- **Implementation Rules (verbatim):**
  - El proyecto MUST ser un único proceso Node.js sin servidor HTTP: no expone puerto, no tiene
    framework web, no define rutas
  - El proyecto MUST NOT declarar dependencias de acceso a base de datos: `pg`, `sequelize`,
    `sequelize-typescript`, `typeorm`, `prisma`, `knex` o equivalentes
  - El proyecto MUST NOT declarar `@aws-sdk/client-s3` ni ningún cliente de storage con credenciales
  - El proyecto MUST NOT persistir estado en disco: sin archivos de estado, sin SQLite, sin caché en
    disco, sin volumen montado de escritura
  - El único mecanismo de deduplicación MUST ser el flag `\Seen` de IMAP, aplicado con
    `messageFlagsAdd` por UID
  - Un mensaje MUST marcarse `\Seen` en el mismo paso en que se descarga y parsea, antes de publicar el
    comando
  - Un mensaje que no se pudo descargar MUST NOT marcarse `\Seen` (así el próximo tick lo reintenta)
  - Un comando fallido MUST NOT reintentarse: se loguea y se descarta el mail
  - El procesamiento MUST ser secuencial: un mail a la vez, un tick a la vez, sin `Promise.all` sobre
    mails ni sobre ticks
  - Los tres módulos internos (Ingesta, Ruteo, Publicación) MUST comunicarse por llamada de función
    dentro del proceso, sin transporte intermedio
  - El despliegue MUST correr **exactamente 1 instancia** por casilla de mail

**ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus**

- **Decisión:** el conector no implementa nada del protocolo del bus; delega al SDK subject,
  envelope, hash del inbox, token y refresh, y las clases de error tipadas.
- **Implementation Rules (verbatim):**
  - El cliente del bus MUST ser `@gravadigital/jiku` en rango `^1.0.0`
  - El proyecto MUST NOT declarar `nats` como dependencia directa
  - El conector MUST NOT construir subjects a mano: el subject se arma con `client.command()`, nunca con
    concatenación de strings
  - El conector MUST NOT armar ni parsear envelopes del protocolo a mano
  - El conector MUST NOT fijar `inboxPrefix` por su cuenta: lo fija el SDK siempre
  - La identidad MUST construirse con `ServiceUser.fromKeyFile()` — no con un token obtenido a mano ni
    con un JWT armado en el conector
  - `connect()` MUST llamarse **exactamente una vez** al arrancar el proceso, y el cliente resultante
    MUST conservarse por toda la vida del proceso. Prohibido conectar por mail o por tick
  - El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), **nunca** de una variable
    de entorno
  - La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los defaults a mano
  - El timeout MUST quedar en el default del SDK (**15000 ms**). MUST NOT bajarse
  - `onTokenError` MUST estar registrado y MUST loguear el fallo del refresh como `error` sin terminar
    el proceso
  - El runtime MUST ser Node.js **≥ 22.12**
  - El proyecto MUST usar **ESM** (`"type": "module"`)
  - Los errores del bus MUST manejarse por las clases del SDK (`JikuPermissionDenied`, `JikuFailure`,
    `JikuTimeout`, `JikuNoEndpoint`, `JikuInvalidRequest`), no inspeccionando strings de mensaje

**ADR-003: Toda escritura por comandos del bus, con el byte fuera de banda**

- **Decisión:** dos comandos, `files.request-upload` (permiso + URL prefirmada) y `requirements.new`
  (alta, con `fileIds` de los ya subidos). El byte NO viaja por el bus: `PUT` directo con `fetch`
  nativo, sin credenciales de S3.
- **Implementation Rules (verbatim, completas — son el contrato que estos tests afirman):**
  - Toda escritura de dominio MUST hacerse publicando un comando por el bus. MUST NOT haber ninguna
    escritura directa a PostgreSQL ni a storage con credenciales propias
  - Los únicos comandos permitidos son **`files.request-upload`** y **`requirements.new`**. MUST NOT
    publicarse ningún otro
  - El conector MUST NOT publicar en el plano de consultas (`jiku-queries.*`) ni suscribirse a subjects
    de otros servicios
  - El byte de un adjunto MUST viajar por `PUT` HTTPS a la `uploadUrl` devuelta por
    `files.request-upload`. MUST NOT incluirse en el payload de ningún comando
  - El `PUT` MUST hacerse con `fetch` nativo y un timeout de **30000 ms**
  - El conector MUST NOT construir la clave de storage: la devuelve `core` implícitamente en la URL
    firmada
  - El payload de `files.request-upload` MUST incluir `fileName`, `mimeType`, `fileSize` y `checksum`
    (sha256 calculado con `node:crypto` sobre el contenido)
  - El payload de `requirements.new` MUST incluir `title`, `description`, `projectId`, `type`,
    `priority`, `visibilityLevel`, y `fileIds` **sólo si hay al menos uno**
  - `fileIds` MUST tener a lo sumo **10** elementos (el `maxItems` del contrato). Los adjuntos aceptables
    que exceden el tope MUST anotarse como aviso en la descripción
  - El conector MUST NOT enviar `state` en `requirements.new`: el requisito nace en `analisis`
  - El conector MUST NOT enviar la clave `actor` en ningún payload
  - `title` MUST truncarse a **255** caracteres antes de publicar
  - `title` y `description` MUST NOT quedar vacíos: si el mail los trae vacíos, MUST usarse los
    placeholders configurados
  - El filtro local de archivos MUST tratarse como conveniencia, no como autoridad: un rechazo de `core`
    (`file_type_not_allowed`, `file_too_large`) MUST manejarse como caso esperado, con aviso en la
    descripción
  - Dos adjuntos con el mismo `checksum` en el mismo mail MUST colapsarse a uno. Un colapsado MUST NOT
    generar aviso ni placeholder
  - El fallo de un adjunto (permiso o `PUT`) MUST NOT cancelar el requisito: se anota el aviso y se
    sigue
  - La descripción MUST componerse en este orden exacto: cuerpo base → avisos de rechazo → avisos de
    fallo de subida → **placeholders al final**
  - Los placeholders MUST ser `![attach:{id}]` para `image/*` y `[attach:{id}]` para el resto
  - Un requisito creado MUST NOT modificarse: no hay comando de compensación

**ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito**

- **Decisión:** logs estructurados a stdout, JSON en producción, nunca a archivo. El log distingue
  explícitamente qué sistema rechazó cada comando.
- **Implementation Rules (verbatim, las relevantes a esta story):**
  - Los logs MUST ir a **stdout**. MUST NOT configurarse ningún transport de archivo, en ningún entorno
  - El formato MUST ser **JSON en producción**
  - MUST NOT loguearse nunca: credenciales, tráfico IMAP crudo, el cuerpo del mail (`body`), el
    contenido de un adjunto
  - **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado
  - Un alta exitosa MUST loguear `messageId`, `projectId` y el `id` del requisito creado, juntos
  - Un fallo de comando MUST loguear la **clase de error del SDK** y, cuando exista, el `code` y el
    `hint()`. MUST NOT reducirse a un mensaje genérico de "falló el comando"
  - Cada tick MUST emitir una línea con los cinco contadores: `ingestados`, `parseados`, `creados`,
    `descartados`, `fallidos`
  - MUST NOT implementarse endpoint de healthcheck ni exportador de métricas en v1

#### `ruteo-y-alta-del-requisito.md`

**Estado actual (a modificar):** el diagrama de secuencia tiene seis participantes (`TICK`, `ROUTE`,
`PUB`, `BUS`, `CORE`, `LOG`) y el Paso 4 ("El armado del payload") documenta el payload **sin
adjuntos**: la tabla de campos no incluye `fileIds`, y dice *"Las tres claves siempre excluidas:
`state`..., `actor`..., `fileIds` (FG-4)"*.

La sección **Resultado** cierra con: *"nunca se acumula un array de mails ruteados ni de resultados de
ruteo entre `routeMail()` y la publicación. Es la propiedad que **FG-4 tiene que preservar
deliberadamente** cuando agregue los `Buffer` de los adjuntos."* — esta frase es la que pasa de
advertencia a hecho cumplido (CA-1).

**Cambios requeridos:**
1. **Participante nuevo** en el diagrama: `ADJ` (`procesarAdjuntosDelMail()`), entre `ROUTE` y `PUB`.
2. **Inserción del procesamiento completo de adjuntos entre el Paso 2 (árbol de decisión de
   `routeMail()`) y el Paso 4 (armado del payload)** — pasa a ser el nuevo Paso 3, y el resto se
   renumera. Debe incluir, en el diagrama y en texto:
   - La invocación `procesarAdjuntosDelMail(mail.attachments, config.adjuntos, { client, logger })`
   - Las tres ramas de rechazo/fallo: **rechazo local** (`particionar`/`deduplicar`/`aplicarTope`, log
     `info`), **`failure` de negocio de `core`** vía `requestFileUpload()` (log `warn` + `code`), y
     **fallo de `PUT`** vía `uploadFileContent()` (log `warn`), **todas ANTES de la publicación del
     alta** — ninguna cancela el mail, cada una deja su aviso.
3. **Paso 4 (armado del payload) actualizado:**
   - La tabla de campos gana la fila `fileIds`, **condicional**: sólo presente si
     `adjuntos.fileIds.length > 0` (nunca `fileIds: []`).
   - La `description` deja de ser sólo `mail.body` recortado: pasa a ser
     `componerDescripcion({ cuerpoBase, avisosDeRechazo, avisosDeFallo, placeholders })`, con la
     composición de **cuatro bloques** en orden fijo (cuerpo → rechazos → fallos → placeholders).
4. **La nota de "Resultado" pasa de advertencia a hecho cumplido:** reemplazar *"que FG-4 tiene que
   preservar deliberadamente"* por una afirmación de que **ya está preservado**, y **cómo**: el
   `mail.attachments` (único portador de los `Buffer`) se pasa directo a `procesarAdjuntosDelMail()`
   dentro de la misma iteración, sin copiarse a ningún array del tick, y se libera al terminar esa
   iteración (referenciar `procesarAdjuntosDelMail()` y su resultado sin `Buffer`,
   `ProcesamientoAdjuntosResultado`).

### Code Conventions

De `.claude/conventions/node/_base.md` (siempre activa):
- TypeScript `strict: true`, sin `any` salvo en bordes documentados.
- Archivos y carpetas en `kebab-case`; funciones/variables en `camelCase`; tipos/interfaces en
  `PascalCase` sin prefijo `I`.
- Fechas en ISO 8601 UTC en cualquier borde del sistema (no aplica directamente a esta story: no hay
  fechas nuevas en juego).
- Imports: librerías externas primero, luego imports absolutos del proyecto, luego relativos, con
  línea en blanco entre grupos.
- Comentarios: por default ninguno; sólo el "por qué" cuando no es obvio (patrón ya extensivamente
  usado en este repo — cada archivo de dominio explica sus decisiones no obvias en el comentario de
  cabecera).

De `docs/architectures/jiku-mail-connector/conventions/module-imports.md` (custom del servicio,
**obligatoria en TODO import intra-proyecto**):
- Imports intra-proyecto van con subpath nativo de Node, prefijo `#` (`#domain/...`, `#shared/...`,
  `#config/...`, `#infra/...`), **nunca** `../../`.
- Extensión `.js` explícita en el specifier, incluso desde `.ts`.
- Nunca `@/` (eso es de `_base`, mismo notación pero mecanismo distinto — este servicio usa el
  mecanismo nativo de Node, no un rewriter).

De `docs/architectures/jiku-mail-connector/conventions/testing.md` (custom del servicio, **reemplaza**
la convención de testing del catálogo — reglas obligatorias para TODOS los tests de esta story):
- **Un solo contenedor NATS por suite**, iniciado en `globalSetup` (`test/global-setup.ts`). **Nunca**
  un contenedor nuevo en `beforeAll` de un archivo ni dentro de un `it`.
- **`fileParallelism: false`**: ejecución secuencial de archivos de test — el bus es compartido y una
  suscripción viva de un test anterior contamina el siguiente.
- **Nunca mockear el bus.** Los tests de integración usan el NATS real vía `Client.fromConnection()`.
- **Doblar SÓLO en el borde:** IMAP vía la interfaz `MailSource`; el `PUT` prefirmado vía un servidor
  HTTP real de test o un stub de `fetch`. **Nunca** mockear las funciones de dominio propias
  (`particionar`, `deduplicar`, `aplicarTope`, `routeMail`, `procesarAdjuntosDelMail`, etc.) — si una
  story pide verificar el "sistema completo", eso significa invocar estas funciones reales, no dobles
  de ellas.
- **Cada clase de error del SDK manejada en producción debe tener su test.**
- **Fixtures de mail son bytes RFC 822 reales** (`.eml`) para la normalización; los escenarios de
  `tick.ts` con adjuntos de esta story pueden seguir construyendo el `.eml` inline con
  `multipart/mixed` (mismo patrón que `tick.test.ts` ya usa para S-021 — `mailConAdjunto()`,
  `mailConTresAdjuntos()`, `mailConExeRechazado()` — más simple que mantener archivos `.eml` binarios
  para adjuntos sintéticos pequeños).
- **Nunca dormir el reloj para esperar una condición** (`nc.flush()` para confirmar que una
  suscripción está activa, `Wait.*` para contenedores).
- Silenciar logs con `LOG_LEVEL=silent`/capturar con `createLogCapture()`, **nunca** silenciar errores
  globalmente.
- **No agregar un contenedor de base de datos.** Este servicio no tiene ninguna (ADR-001).

### Reusable Code

Funciones y helpers ya existentes que esta story **reutiliza directamente, sin modificar sus firmas**
(la story es de verificación, no de refactor):

**Servicios/orquestadores (`src/domain/...`):**
- **`runTick()` / `runIngestaTick()`** (`src/domain/ingesta/tick.ts`) — el punto de entrada de todos
  los tests de sistema completo de esta story. Firma: `runTick(mailSource: MailSource, config:
  AppConfig, logger: Logger, client: Client, normalize?: Normalize): Promise<void>`.
- **`procesarAdjuntosDelMail()`** (`src/domain/publicacion/procesar-adjuntos-mail.ts`) — el
  orquestador central de adjuntos (partición→dedup→tope→permiso→PUT), ya invocado desde `runTick()`.
  Devuelve `{ fileIds: number[], avisosDeRechazo: string[], avisosDeFallo: string[], placeholders:
  string[] }` — **nunca** un campo `content`/`Buffer`.
- **`particionar()`** (`src/domain/adjuntos/particionar.ts`) — evalúa `tamano_cero → extension → mime
  → tamano` en ese orden fijo, sobre `content.length` real.
- **`deduplicar()`** (`src/domain/adjuntos/dedup.ts`) — sha256 sobre `content`, colapsa el 2do+
  checksum repetido **en silencio** (sin aviso, sin log).
- **`aplicarTope()`** (`src/domain/adjuntos/tope.ts`) — toma los primeros
  `MAX_ATTACHMENTS_PER_REQUIREMENT` (10, constante importada de `#config/schema.js`), el resto pasa a
  `rechazados` con `regla: 'tope_excedido'`.
- **`requestFileUpload()`** (`src/domain/publicacion/upload-file.ts`) — un adjunto → `UploadResultado`
  (`concedido`/`rechazado`/`fallido`), nunca lanza.
- **`uploadFileContent()`** (`src/domain/publicacion/upload-byte.ts`) — `PUT` HTTPS directo con
  `fetch` nativo + `AbortSignal.timeout(timeoutMs)`, devuelve `PutResultado` (`subido`/`fallido`).
- **`componerDescripcion()`** (`src/domain/publicacion/description.ts`) — concatena con `'\n'`,
  filtrando partes vacías, en el orden `cuerpoBase, ...avisosDeRechazo, ...avisosDeFallo,
  ...placeholders`.
- **`buildRequirementPayload()`** (`src/domain/publicacion/mail-payload.ts`) — arma el payload final,
  incluye `fileIds` sólo si `.length > 0`.
- **`publishRequirementFromMail()`** (`src/domain/publicacion/publish-requirement.ts`) — publica,
  loguea éxito con `{ messageId, projectId, requirementId, archivosVinculados, archivosConAviso }` en
  una línea, o falla y relanza `PublishError` (el tick lo captura y cuenta `fallidos`).

**Test helpers (`test/...`):**
- **`setupTestBus()`** (`test/bus/helpers.ts`) — abre conexión NATS contra el contenedor compartido,

### Task 2: Propiedad — el tope no se recalcula tras un fallo de `PUT`, sobre el sistema completo (CA-6)

**Status:** Completed

#### Description

`test/publicacion/procesar-adjuntos-mail.test.ts` ya cubre exactamente este escenario **a nivel de

3. El responder de `files.request-upload` observa `count() === 10` — nunca 12: los 2 excedentes del

5. Ningún código de producción se modifica salvo que el test revele un bug real.

#### Technical Details

**Architectural Context References:**
- ADR-003: "Un mail con 15 adjuntos aceptables sube los primeros 10 y anota los otros 5 como no
  adjuntados" (aplicado aquí con 12 en vez de 15, y con 3 fallos de `PUT` intercalados).
- Test Scenarios → TS-3, con el input/output exacto.
- Reusable Code → patrón exacto ya usado en `test/publicacion/procesar-adjuntos-mail.test.ts` ("con 12
  aceptables y 3 PUT fallidos..."), a copiar y adaptar para invocar `runTick()` en vez de
  `procesarAdjuntosDelMail()` directamente.

**Files to Create/Modify:**
- `test/ingesta/tick.test.ts` (o el archivo nuevo de Task 1, si se optó por separar).

**Implementation Notes:**
- El servidor HTTP local necesita un contador de invocaciones (`let putCount = 0`) para decidir cuáles
  de los 10 `PUT` fallan — mismo patrón que ya existe en
  `test/publicacion/procesar-adjuntos-mail.test.ts` línea ~238 en adelante. Copiar ese patrón, no
  reinventarlo.
- El mail necesita 12 adjuntos con `content` **distinto** entre sí (nombres `adj-0.png` …
  `adj-11.png`), para que ninguno colisione con `deduplicar()` — a diferencia de TS-2 de Task 1, donde
  el contenido es deliberadamente el mismo.
- Verificar el orden de llegada de los `PUT` al servidor local no es determinístico en general
  (depende del orden de resolución de las promesas), pero como `procesarAdjuntosDelMail()` procesa en
  serie (nunca `Promise.all`), el orden observado por el servidor SÍ es determinístico: los primeros 3
