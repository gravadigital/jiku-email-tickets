# Story Plan: S-015 (jiku-mail-connector) - El payload derivado del mail y el alta

## Status

**Status:** Completed

## Story Reference

**Story:** [S-015](../stories/S-015.payload-derivado-del-mail-y-el-alta.md)
**Service:** jiku-mail-connector
**Summary:** Reemplaza el payload fijo del modo de verificación por uno derivado del mail entrante
(`title` recortado/truncado, `description` = cuerpo, `creator` = `client.userId`), agrega `creator`
como opcional al schema de `requirements.new`, cablea la publicación dentro del tick con conteo de
`creados`/`fallidos`, y agrega `messageId` a las líneas de log de éxito y de error.

## Architectural Context

### Tech Stack

- **Node.js ≥ 22.12** (impuesto por el SDK, ADR-002), TypeScript con `strict: true`, ESM
  (`"type": "module"`).
- **Zod** para validación de payloads (`newRequirementSchema`).
- **Pino** para logging estructurado.
- **`@gravadigital/jiku` ^1.0.0** — SDK oficial del bus (cliente NATS, identidad, comandos).
- **Vitest** + **Testcontainers** (un único contenedor NATS compartido por suite, `fileParallelism:
  false`). Sin base de datos (ADR-001).

### Service Architecture

```
src/
├── config/               # env.ts, schema.ts, index.ts (AppConfig, RuteoConfig)
├── domain/
│   ├── ingesta/           # normalize, tick, scheduler, ports (MailSource)
│   ├── ruteo/             # route-mail.ts (puro)
│   └── publicacion/       # requirement.schema.ts, requirement.types.ts,
│                           # verification-payload.ts, publish-requirement.ts, publish-errors.ts
│                           # ESTA STORY AGREGA: mail-payload.ts
├── infra/
│   ├── bus/               # connection.ts, identity.ts, errors.ts
│   └── imap/               # client.ts, errors.ts
└── shared/                 # errors/, logger.ts, log-redaction.ts, motivo-descarte.ts
```

**Dirección de dependencias, estricta:** `config -> ruteo`, nunca al revés. `ruteo/route-mail.ts` es
puro: no importa nada de `domain/publicacion`. El único módulo que compone `ingesta` + `ruteo` +
`publicacion` es `tick.ts` — esta story agrega esa composición ahí, no en ningún otro archivo.

**Error handling:** clases de error específicas que extienden `AppError` (`code`, `httpStatus`
abstracto en 500 porque el servicio no expone HTTP), nunca `throw new Error(...)` en dominio.
`RequirementValidationError` ya existe y **no cambia** — solo se le agrega `title`/`description` como
contenido real por primera vez.

**Testing:** convención custom `testing.md` — un solo contenedor NATS por suite (`globalSetup`),
ejecución secuencial, `core` doblado con un responder EN el bus real (`respondTo()` de
`test/bus/responder.ts`), IMAP doblado por interfaz (`MailSource`). Nunca se mockea el bus.

### Relevant ADRs

#### ADR-001: Worker único sin persistencia propia

- **Decisión:** un solo proceso, sin base de datos, sin estado persistido. Único mecanismo de
  idempotencia: el flag `\Seen` de IMAP.
- **Implementation Rules relevantes para esta story:**
  - Un comando fallido MUST NOT reintentarse: se loguea y se descarta el mail.
  - El procesamiento MUST ser secuencial: un mail a la vez, sin `Promise.all`/`Promise.allSettled`
    sobre mails.
  - Los tres módulos internos (Ingesta, Ruteo, Publicación) MUST comunicarse por llamada de función
    dentro del proceso, sin transporte intermedio.

#### ADR-002: SDK oficial `@gravadigital/jiku` como cliente del bus

- **Decisión:** el conector no implementa nada del protocolo del bus; delega todo al SDK.
- **Implementation Rules relevantes:**
  - El conector MUST NOT construir subjects a mano: se arma con `client.command()`.
  - `connect()` MUST llamarse exactamente una vez al arrancar; el cliente se reutiliza (ya existe:
    `client` llega por parámetro).
  - El `user-id` del subject MUST salir de `auth.userId` (`client.userId`), nunca de una variable de
    entorno.
  - El timeout MUST quedar en el default del SDK (**15000 ms**). MUST NOT bajarse.
  - Los errores del bus MUST manejarse por las clases del SDK, nunca inspeccionando strings de
    mensaje.

#### ADR-003: Escritura solo por comandos, con el byte fuera de banda

- **Decisión:** toda escritura es un comando del bus; solo `files.request-upload` y
  `requirements.new` están permitidos.
- **Implementation Rules relevantes para esta story:**
  - El payload de `requirements.new` MUST incluir `title`, `description`, `projectId`, `type`,
    `priority`, `visibilityLevel`, y `fileIds` **solo si hay al menos uno** (fuera de alcance aquí:
    no hay adjuntos en esta story).
  - El conector MUST NOT enviar `state` en `requirements.new`.
  - El conector MUST NOT enviar la clave `actor` en ningún payload.
  - `title` MUST truncarse a **255** caracteres antes de publicar.
  - `title` y `description` MUST NOT quedar vacíos: si el mail los trae vacíos, MUST usarse los
    placeholders configurados.
  - Un requisito creado MUST NOT modificarse: no hay comando de compensación.

#### ADR-005: Identidad de machine user con el rol `internal-app`

- **Decisión:** el actor de un requisito lo resuelve `core` del `sub` del subject (infalsificable);
  lo que el conector declare en `creator` es informativo y **`core` lo ignora**.
- **Implementation Rules relevantes:**
  - El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), nunca de una variable
    de entorno.
  - Lo que el conector declare en `creator` / `uploader` MUST tratarse como informativo: `core` lo
    ignora y resuelve el actor del subject.
  - El conector MUST NOT enviar la clave `actor` en el payload de ningún comando.

#### ADR-006: Observabilidad por logs estructurados, con el origen del rechazo explícito

- **Decisión:** logs a stdout, JSON en producción, y cada fallo de comando distingue explícitamente
  qué sistema rechazó.
- **Implementation Rules relevantes para esta story:**
  - MUST NOT loguearse nunca: credenciales, tráfico IMAP crudo, **el cuerpo del mail**, contenido de
    adjunto.
  - Cada mail procesado MUST dejar al menos una línea de log con su `messageId` y su resultado.
  - Un alta exitosa MUST loguear `messageId`, `projectId` y el `id` del requisito creado, juntos.
  - Un fallo de comando MUST loguear la clase de error del SDK y, cuando exista, el `code` y el
    `hint()`.
  - Cada tick MUST emitir una línea con los cinco contadores: `ingestados`, `parseados`, `creados`,
    `descartados`, `fallidos`.
  - El timeout del comando MUST quedar en **15000 ms**. MUST NOT bajarse.

### API Context

No hay `docs/apis/` para este producto — el conector no expone HTTP (ADR-001). El "contrato" es el
comando `requirements.new` del bus de Jiku, documentado íntegro abajo.

#### Comando `requirements.new` (existente, se reutiliza sin modificar su publicación)

Definido en `src/domain/publicacion/requirement.schema.ts`. El schema es **la única definición del
contrato en el repo**. Después de esta story:

```ts
export const TITLE_MAX_LENGTH = 255; // ya existe, exportada

export const newRequirementSchema = z
  .object({
    title: z.string().min(1).max(TITLE_MAX_LENGTH),
    description: z.string().min(1),
    projectId: z.number().int().positive(),
    type: z.enum(['funcionalidad', 'mejora', 'incidencia', 'otro']),
    priority: z.enum(['sin_prioridad', 'baja', 'media', 'alta', 'urgente']),
    visibilityLevel: z.enum(['public', 'internal']),
    creator: z.string().min(1).optional(), // <- AGREGADO por esta story (Tarea 1)
  })
  .strict(); // SE CONSERVA: sigue rechazando cualquier clave desconocida (incluido `actor`)

export const newRequirementReplySchema = z
  .object({ id: z.number().int().positive() })
  .loose(); // sin cambios
```

**Las cuatro claves excluidas, y la única que cambia de razón:**

| Clave | Va en el payload de esta story? | Razón |
|---|---|---|
| `state` | No | El requisito nace en `analisis` (default de Jiku) |
| `actor` | No | Única clave que el `.strict()` y el chequeo local del SDK rechazan de plano |
| `fileIds` | No | Los adjuntos se ignoran por completo en esta story (FG-4) |
| `creator` | **Sí** | `client.userId`. `core` lo **ignora** (resuelve el actor del `sub` del subject) |

**El payload derivado del mail (nuevo, `mail-payload.ts`):**

| Campo | Valor |
|---|---|
| `title` | `mail.subject.trim()` → `.slice(0, TITLE_MAX_LENGTH)` → si queda vacío, `config.ruteo.placeholderTitle` |
| `description` | `mail.body.trim()` → si queda vacío, `config.ruteo.placeholderBody` |
| `projectId` | El resuelto por `routeMail()` (ya en el tick) |
| `type` | `'incidencia'` — fijo, no configurable |
| `priority` | `'sin_prioridad'` — fijo |
| `visibilityLevel` | `'public'` — fijo |
| `creator` | `client.userId` |

**Respuesta de éxito:** se valida con `newRequirementReplySchema` (ya existe, sin cambios). Un éxito
sin `id` usable es un fallo — regla heredada de S-005, sin cambios.

### Database Context

**Ninguno.** El conector no alcanza PostgreSQL (ADR-001). La escritura la hace `core`, tres saltos
más allá: un `INSERT` en `requirements` de la base de Jiku, con `state: analisis` por default. No
existe `docs/db-schemas/` para este producto.

### Flow Context

No aplica un documento de flujo existente para copiar: los cuatro documentos de flujo (el nuevo
`ruteo-y-alta-del-requisito` y las modificaciones a los otros tres) los produce **S-016**, que cierra
el feature group. Esta story deja el comportamiento funcionando; la siguiente lo documenta.

El flujo que esta story implementa (Escenario A de la story, camino feliz) es:

1. **[`tick`]** dentro del loop, por mail y en serie, con `route.ok === true`:
   → `publishRequirementFromMail(mail, route.projectId, client, config.ruteo, logger)`
2. **[`publicacion`]** `buildRequirementPayload()` en `mail-payload.ts` deriva `title`, `description`,
   `creator`; `parseNewRequirement()` valida contra el contrato **antes de publicar**.
3. **[`publicacion` → Bus NATS]** `client.command('requirements.new', payload)` — reutilizado de
   S-005, sin tercer argumento `options`, timeout 15000 ms.
4. **[Bus NATS → `core`]** autoriza por `users.roles`, resuelve el actor del `sub` del subject
   (ignora `creator`), valida la forma, inserta con `state: analisis`. Responde `success { id }`.
5. **[`publicacion`]** valida con `newRequirementReplySchema`; loguea
   `{ messageId, projectId, requirementId }` en una línea; devuelve `{ requirementId }` al tick.
6. **[`tick`]** `counters.creados += 1`; continúa con el siguiente UID.

**Escenario B (fallo):** `diagnosePublishFailure()` (sin cambios) traduce el error; se loguea
`{ messageId, ...error.logContext(projectId) }`; se relanza; el tick captura por mail, incrementa
`fallidos`, hace `continue` (nunca aborta el lote), y no reintenta.

### Integration Points

**Bus NATS (interno, vía SDK):** ya cableado desde S-004/S-005. Esta story NO agrega conexiones
nuevas, NO arma subjects a mano, NO parsea envelopes. El único punto de publicación sigue siendo
`client.command(COMMAND, payload)` con dos argumentos, ahora invocado también desde el camino del
mail (antes solo desde el modo de verificación).

**No hay referencias externas nuevas** (`docs/references/`) que cargar para esta story: el contrato
del bus ya está íntegro en el Architectural Context de arriba.

### Code Conventions

- Archivos y carpetas en `kebab-case`; funciones/variables en `camelCase`; constantes globales en
  `SCREAMING_SNAKE_CASE`; tipos inferidos de schemas Zod, nunca escritos a mano en paralelo.
- **Imports intra-proyecto:** prefijo `#` nativo de Node (convención custom `module-imports`), nunca
  `@/` ni rutas relativas que suban directorios. Especificador con `.js` explícito, incluso en
  archivos `.ts`. Orden: librerías externas → `#imports` absolutos → `./relativos`, con línea en
  blanco entre grupos.
- **Comentarios:** por defecto, ninguno. Solo el "por qué" cuando no es obvio (este servicio comenta
  densamente sus decisiones verificadas — mismo estilo en el código nuevo).
- **Errores como valores vs. excepciones:** errores de negocio esperados (validación) se modelan con
  clases específicas y se lanzan con `throw`. Nunca `throw new Error(...)` en dominio.
- **Validación:** `safeParse`, nunca `parse`, para no dejar escapar el `ZodError` crudo con los
  valores rechazados en su `message`.

### Reusable Code

- **`client.command()`** (`publish-requirement.ts`, patrón de S-005) — el único punto de publicación
  al bus. Se reutiliza **intacto**: misma firma de dos argumentos, mismo timeout de 15000 ms del
  cliente. No se toca su mecánica; se agrega una segunda función hermana
  (`publishRequirementFromMail`) que comparte el mismo patrón try/catch/log/relanza.
- **`diagnosePublishFailure()` y `PublishError`** (`publish-errors.ts`) — **no se modifican**. Sus 9
  ramas ya cubren los tres sistemas que pueden rechazar. `error.logContext(projectId)` ya expone
  `diagnosis`, `sdkErrorClass`, `projectId`, `planoDeEscrituraAbierto` y condicionalmente `code`,
  `hint`, `errorMessage` — esta story solo agrega `messageId` en el objeto de log, no dentro de
  `logContext()`.
- **`newRequirementReplySchema`** (`requirement.schema.ts`) — se reutiliza sin cambios para validar
  la respuesta.
- **`parseNewRequirement()`** (`verification-payload.ts`) — función genérica de validación de
  cualquier payload contra `newRequirementSchema`; se reutiliza para el payload derivado del mail sin
  cambios en su firma.
- **`TITLE_MAX_LENGTH`** (`requirement.schema.ts`) — constante exportada; se **importa**, nunca se
  redeclara un `255` literal (CA-7).
- **`IncomingMail`** (`domain/ingesta/types.ts`) — trae `messageId`, `subject` (ya sin prefijos
  `Re:`/`Fwd:`, puede ser `''`), `body` (texto plano, puede ser `''`), `attachments` (se ignoran por
  completo en esta story).
- **`RuteoConfig`** (`config/index.ts`) — ya trae `placeholderTitle` y `placeholderBody` (S-012), con
  sus defaults `'Ticket recibido por mail'` y `'(mail sin contenido)'`.
- **`routeMail()`** (`domain/ruteo/route-mail.ts`) — ya resuelve `{ ok: true, projectId, slug }`;
  esta story no lo modifica, solo consume su resultado en la rama `ok` del tick.
- **`runTick()`** (`domain/ingesta/tick.ts`) — el loop existente donde se cablea la llamada. Hoy la
  rama `route.ok === true` solo loguea `'mail procesado'` y no incrementa `creados` (literal `0`).

  ```ts
  export interface PublishRequirementFromMailDeps {
    readonly client: Client;
    readonly logger: Logger;
  }

  export async function publishRequirementFromMail(
    mail: Pick<IncomingMail, 'messageId' | 'subject' | 'body'>,
    projectId: number,
    ruteoConfig: Pick<RuteoConfig, 'placeholderTitle' | 'placeholderBody'>,
    { client, logger }: PublishRequirementFromMailDeps,
  ): Promise<{ requirementId: number }> {
    const payload = parseNewRequirement(
      buildRequirementPayload(mail, projectId, client.userId, ruteoConfig),
    );

    let data: unknown;
    try {
      data = await client.command(COMMAND, payload);
    } catch (cause) {
      const error = new PublishError(diagnosePublishFailure(cause), cause);
      logger.error(
        { messageId: mail.messageId, ...error.logContext(projectId) },
        'fallo la publicacion de requirements.new',
      );
      throw error;

      logger.error(
        { messageId: mail.messageId, ...error.logContext(projectId) },
        'fallo la publicacion de requirements.new',
      );
      throw error;
    }

    logger.info(
      { messageId: mail.messageId, projectId, requirementId: reply.data.id },
      'requisito creado en Jiku',
    );

    return { requirementId: reply.data.id };
  }
  ```

### Task 5: Propiedades de seguridad y verificación final de cobertura

**Status:** Completed

#### Description

Extiende los tests de propiedad existentes (`test/publicacion/source-properties.test.ts`) para cubrir
los dos archivos nuevos/modificados (`mail-payload.ts`, el `publishRequirementFromMail` agregado a
`publish-requirement.ts`), y agrega un test de integración de extremo a extremo que ejercita un tick
completo con contenido real de cliente para confirmar que CA-25 se sostiene con datos reales, no solo
con los literales fijos del modo de verificación.

#### Acceptance Criteria

1. El escáner de `source-properties.test.ts` (`PUBLICACION_FILES`) incluye `mail-payload.ts` — el
   test de sanidad del scanner (`'finds the source files it is meant to scan'`) se actualiza si su
   umbral (`PUBLICACION_FILES.length >= 4`) necesita ajustarse tras agregar el archivo nuevo.
2. `'sends none of the four excluded payload keys'` sigue verificando `verification-payload.ts` (sin
   cambios) Y se extiende para verificar que `mail-payload.ts` tampoco escribe `state:`, `actor:`,
   `fileIds:` como claves literales.
3. `'invokes client.command in exactly one file'` sigue afirmando que solo
   `publish-requirement.ts` invoca `.command(` — `mail-payload.ts` y `tick.ts` NO deben invocar
   `.command()` directamente (la única invocación sigue centralizada).
4. Un test de integración con un tick completo, mail con contenido de cliente distintivo
   (`'CONTENIDO-SECRETO-DE-CLIENTE'` en `subject` y `body`), confirma que ese string NUNCA aparece en
   el output crudo de ningún logger a lo largo de: descarte, normalización, ruteo, publicación exitosa
   y publicación fallida.
5. `RequirementValidationError` con un valor de campo real de mail (no un literal fijo) sigue sin
   filtrar ese valor (TS-25).
