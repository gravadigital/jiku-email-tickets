# Story Plan: S-030 (jiku-mail-connector) - Derogación documental: ADR-003, el flujo del comentario y el PRD

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-030](../stories/S-030.derogacion-documental-adr003-flujo-prd.md)
- **Service:** jiku-mail-connector
- **Summary:** Cerrar REQ-006 por el lado documental: reescribir los dos textos de ADR-003 que
  **prohibían** el plano de consultas (la Implementation Rule y la frase de §Decision) más su
  `Status`, reescribir cinco lugares del flujo `publicacion-requirements-comment` que documentan el
  duplicado como **costo aceptado**, derogar con nota la CA-13 de S-027, actualizar el `overview.md`

**Esta story no toca una sola línea de código.** Es enteramente documental, y eso es exactamente el
riesgo que la separó de S-029: el valor observable ya se entregó, así que la tentación es saltearla.
Un documento que sigue prohibiendo lo que el código hace produce el siguiente cambio que lo revierte
**por respetar la regla**.

**La fuente de verdad de todo lo que se escribe acá es el código de S-029**, no el request: el CA-1
pide enumerar el caso habilitado *con sus cuatro filtros*, y esos nombres salen de
`src/domain/publicacion/lookup-attachment.ts`, no de una paráfrasis.

### El código que la documentación tiene que describir (S-029, ya implementada)

Esto es el ancla de todo el plan. La regla reescrita tiene que enumerar **esto**, verbatim.

**Archivo:** `src/domain/publicacion/lookup-attachment.ts`
**Función:** `lookupAttachmentByChecksum()`
**Es el cuarto archivo de contrato de `publicacion`, y el PRIMERO DE LECTURA.**

La llamada, verbatim del código:

```ts
page = await client.list(RESOURCE, {           // RESOURCE = 'attachments'
  filter: {
    entityType: ENTITY_TYPE,                   // ENTITY_TYPE = 'requirement'
    entityId: requirementId,                   // el requirementId de lookupThread()
    checksum: adjunto.checksum,                // el hash que ya calculó deduplicar()
    uploadedBy: client.userId,                 // el sub del caller, NUNCA del entorno
  },
  include: ['checksum'],
  fields: ['fileId'],
  limit: 1,
});
```

**Los cuatro nombres de filtro, exactos:** `entityType`, `entityId`, `checksum`, `uploadedBy`.
Cualquier reescritura de la Implementation Rule que los parafrasee (`tipo de entidad`, `id del
requisito`) queda **desalineada del código** y no sirve como regla verificable.

**Sus dos variantes de retorno, y ninguna de error:**

```ts
export type LookupAttachmentResultado =
  | { readonly tipo: 'reusado'; readonly fileId: number }
  | { readonly tipo: 'sin_match' };
```

**La degradación:** todo fallo —los seis códigos del contrato, el `JikuError` genérico, cualquier
clase del SDK— cae en el `catch`, loguea `warn` con
`{ checksum, requirementId, diagnosis, sdkErrorClass, resultado: 'consulta_fallida', code? }` y
devuelve `sin_match`. **`diagnosePublishFailure()` se reusa sin una sola rama nueva.**

**El orden real del pipeline** (de `procesar-adjuntos-mail.ts`): `particionar()` → `deduplicar()`
→ `aplicarTope()` → **consulta** → permiso → `PUT`. O sea **`intra-mail → tope → consulta`**, que
es el orden que el CA-5 pide documentar. El comentario del código lo dice explícito: el dedup
primero (una consulta por checksum **sobreviviente**) y el tope antes (no se paga consulta por un
excedente).

**La versión ejecutable de la regla, que NO se toca en esta story:**
`test/publicacion/source-properties.test.ts`, caso
`'touches the query plane only through attachments.list, only in the lookup module'`. Mantiene
prohibidos en **todo** `src/`: `client.query(`, `client.get(`, `client.iterate(`, `client.all(`,
`client.count(` y el literal `jiku-queries`; y permite `client.list(` **sólo** en
`lookup-attachment.ts`. El comentario de ese test dice literalmente *"LA REESCRITURA DEL TEXTO DE
ADR-003 ES DE S-030"* — es la nota que esta story viene a saldar.

### ADRs Relevantes

#### ADR-003: Toda escritura por comandos del bus, con el byte fuera de banda — **ES EL OBJETO DE LA STORY**

**Status actual (el texto que la Task 1 modifica):**

> **Status:** Accepted (regla de los comandos permitidos reescrita el 2026-09-08 por REQ-005 / S-027)

**§Decision, la frase que la Task 1 reescribe (verbatim):**

> **El conector no usa el plano de lectura del bus.** Sólo escribe. Ver
> [ADR-004](ADR-004-mapa-tickets-kv-local.md) para por qué no consulta antes de crear.

**Implementation Rules — la lista COMPLETA y verbatim.** Se copia entera porque el trabajo de la
Task 1 es cirugía sobre **dos** de estas líneas, y hay que ver exactamente cuáles no se tocan:

- Toda escritura de dominio MUST hacerse publicando un comando por el bus. MUST NOT haber ninguna
  escritura directa a PostgreSQL ni a storage con credenciales propias
- Los únicos comandos permitidos son **`files.request-upload`**, **`requirements.new`** y
  **`requirements.{id}.comment`**. MUST NOT publicarse ningún otro
  *(REESCRITA por REQ-005 / S-027: hasta entonces la enumeración era cerrada en los dos primeros. El
  tercero es el que convierte la respuesta de un cliente en un Comentario del Requisito, y es el
  único de los tres cuyo `method` lleva un id embebido — lo arma el publicador y el SDK deriva el
  subject, sin concatenar subjects a mano.)*
- **El conector MUST NOT publicar en el plano de consultas (`jiku-queries.*`) ni suscribirse a
  subjects de otros servicios** ← **ÉSTA es la que se parte en dos (CA-1)**
- El byte de un adjunto MUST viajar por `PUT` HTTPS a la `uploadUrl` devuelta por
  `files.request-upload`. MUST NOT incluirse en el payload de ningún comando
- El `PUT` MUST hacerse con `fetch` nativo y un timeout de **30000 ms**
- El conector MUST NOT construir la clave de storage: la devuelve `core` implícitamente en la URL
  firmada
- El payload de `files.request-upload` MUST incluir `fileName`, `mimeType`, `fileSize` y `checksum`
  (sha256 calculado con `node:crypto` sobre el contenido)
- El payload de `requirements.new` MUST incluir `title`, `description`, `projectId`, `type`,
  `priority`, `visibilityLevel`, y `fileIds` **sólo si hay al menos uno**
- `fileIds` MUST tener a lo sumo **10** elementos (el `maxItems` del contrato). Los adjuntos aceptables
  que exceden el tope MUST anotarse como aviso en la descripción
- El conector MUST NOT enviar `state` en `requirements.new`: el requisito nace en `analisis`, que es el
  default de Jiku
- El conector MUST NOT enviar la clave `actor` en ningún payload: es la única clave de identidad que el
  plano de escritura rechaza de plano
- `title` MUST truncarse a **255** caracteres antes de publicar (el contrato no declara `maxLength` y
  la columna es `varchar(255)`)
- `title` y `description` MUST NOT quedar vacíos: si el mail los trae vacíos, MUST usarse los
  placeholders configurados (defaults: `Ticket recibido por mail` y `(mail sin contenido)`)
- El filtro local de archivos MUST tratarse como conveniencia, no como autoridad: un rechazo de `core`
  (`file_type_not_allowed`, `file_too_large`) MUST manejarse como caso esperado, con aviso en la
  descripción
- Dos adjuntos con el mismo `checksum` en el mismo mail MUST colapsarse a uno. Un colapsado MUST NOT
  generar aviso ni placeholder
- El fallo de un adjunto (permiso o `PUT`) MUST NOT cancelar el requisito: se anota el aviso y se sigue
- La descripción MUST componerse en este orden exacto: cuerpo base → avisos de rechazo → avisos de
  fallo de subida → **placeholders al final**
- Los placeholders MUST ser `![attach:{id}]` para `image/*` y `[attach:{id}]` para el resto
- Un requisito creado MUST NOT modificarse: no hay comando de compensación

**El formato de la anotación de reescritura, que la Task 1 tiene que replicar** (CA-1 lo pide
explícitamente: *"con el mismo formato que la que ya lleva la regla de los comandos permitidos"*):
cursiva entre paréntesis, abriendo con `REESCRITA por REQ-XXX / S-XXX:`, y explicando **qué decía
antes** y **por qué cambió**.

### Contexto de Flujos

Los cuatro flujos que el CA-5 al CA-11 gobiernan, con su estado exacto de hoy.

#### `publicacion-requirements-comment.md` — se reescribe en CINCO lugares

**Frontmatter de hoy:**

```yaml
id: publicacion-requirements-comment
status: Implemented
created: 2026-09-09
last_updated: 2026-09-09
stories: [S-027]
```

**(1) §Descripción — el *"Lo que NO hace"*, verbatim** (CA-6 retira la tercera, conserva las dos
primeras):

> **Lo que NO hace, y es deliberado:** no modifica el Requisito (el Comentario es una entidad aparte),
> no consulta el Requisito antes de comentar, y no deduplica adjuntos contra el resto del hilo. Ver
> **Notas**.

**(2) El diagrama Mermaid — el `loop`, verbatim** (CA-7 le agrega el `alt` de la consulta):

```
    else con match
        KV-->>MC: requirementId
        loop por cada adjunto aceptado
            MC->>CORE: files.request-upload
            CORE-->>MC: fileId + uploadUrl prefirmada
            MC->>S3: PUT del byte
        end
```

**(3) Paso 3 ("Los adjuntos de la respuesta") — los DOS bloques de cita, verbatim.** Son el corazón
del CA-5, y las **dos** afirmaciones dejaron de ser ciertas:

> **El caso observado en la prueba local, y aceptado:** Gmail arrastra los adjuntos del mail
> original en la respuesta. El dedup intra-mail colapsa las repeticiones **dentro de esa respuesta**,
> pero el archivo **se sube de nuevo** porque ya estaba vinculado al Requisito por el mail original.
> Es una fila más en `files` y un objeto más en S3, y Jiku ya declara el archivo con 0..N vínculos
> como estado válido.
>
> **No se deduplica contra el hilo**, y la razón es la forma del contrato de consultas:
> `attachments.list` **no** devuelve `checksum` y `files` no tiene `list`. Deduplicar contra el hilo
> serían **N+1 consultas por respuesta** para evitar un placeholder repetido — y obligaría a tocar el
> plano de consultas, que ADR-003 prohíbe. Si en la práctica molesta, la solución correcta es pedirle
> a Jiku que `attachments.list` exponga `checksum` como incluible, y entonces el dedup es **una** consulta.

El encabezado del paso que **se conserva**: `procesarAdjuntosDelMail()`, *"la misma función y la
misma política"* que el alta — sigue siendo cierto, la consulta va **dentro** de esa función.

**(4) §Notas — la nota que se PRECISA, no se borra, verbatim** (CA-8):

> **No se consulta el Requisito antes de comentar.** Si se borró, `core` contesta
> `requirement_not_found` y **ese es el diagnóstico**. Consultar antes sería usar el plano de lectura
> que ADR-003 prohíbe, para adelantar un error que el comando ya da con más precisión.

La razón que **sobrevive** es la segunda mitad (*"adelantaría un error que el comando ya da con más
precisión"*). La que **cae** es *"usar el plano de lectura que ADR-003 prohíbe"*.

**(5) §Manejo de Errores — la tabla de hoy** (CA-9 le agrega una fila para el Paso 3):

| Paso | Error | Código | Comportamiento |
|---|---|---|---|
| 2 | El bucket de hilos no se puede leer | — | Descarta con `es_respuesta`. **No** se comenta: sin saber el Requisito no hay dónde |
| 2 | Ninguna referencia matchea | — | Descarta con `hilo_desconocido`. Log `warn`, **una sola línea** |
| 3 | Un adjunto lo rechaza la política local | — | **El comentario se publica igual**, con el aviso en su texto |
| 3 | Falla el `PUT` del byte | — | Ídem: aviso de fallo en el texto, el comentario **no** se cancela |
| 4 | `core` rechaza el comando (`requirement_not_found`, `file_not_owned`, cualquier otro) | `PUBLISH_ERROR` | `fallidos += 1`, **sin write**, sin reintento. El `for` **continúa** con el siguiente UID |
| 4 | Timeout / nada respondió | `PUBLISH_ERROR` | Ídem |
| 5 | Falla el write del hilo | — | Log `warn`. **El comentario NO se compensa** y `comentados` no se revierte |

**No aplican.** El entregable es Markdown. Las convenciones que gobiernan el resultado son

5. **Cada flujo modificado actualiza su frontmatter:** `last_updated` y `stories`.

## Test Scenarios

**Esta story no tiene tests ejecutables, y decirlo con precisión es parte del plan.** El entregable
es documentación: no hay código nuevo que testear, y **no se agrega ni un test**. En particular,
`test/publicacion/source-properties.test.ts` —la versión ejecutable de la regla que se reescribe—
**no se toca**: S-029 ya lo acotó, y esta story sólo alinea el texto de la ADR con lo que ese test
ya afirma.

### Task 1: Reescribir los dos textos de ADR-003 y anotar su `Status`

**Status:** Completed

#### Description

Es **el cambio más importante de la story** y el que justifica que exista: ADR-003 tiene hoy una
Implementation Rule **vigente** que dice *"El conector MUST NOT publicar en el plano de consultas
(`jiku-queries.*`) ni suscribirse a subjects de otros servicios"*, y el código de S-029 la viola —
correctamente, y con la mitigación ejecutable en el test de propiedad, pero la viola.

Un documento que sigue prohibiendo lo que el código hace produce el siguiente cambio que lo
revierte **por respetar la regla**. Eso es lo que esta tarea evita.

Son **tres ediciones en un archivo**, y las tres son cirugía: hay que partir una regla en dos
conservando una mitad intacta, reescribir una frase de §Decision conservando su puntero, y sumar una
segunda anotación al `Status` conservando la primera.

**Lo que NO es esta tarea:** una habilitación general del plano de lectura. La derogación es
**puntual y enumerada** — un caso, con sus cuatro filtros. Es el quinto riesgo del request y el
CA-2 existe exactamente para eso.

#### Acceptance Criteria

1. La Implementation Rule del plano de consultas queda **partida en dos reglas independientes**:
   una que conserva `MUST NOT suscribirse a subjects de otros servicios` **intacta**, y otra que
   reescribe la de publicar consultas.
2. La regla reescrita **enumera de forma cerrada** el único caso habilitado en v1: la consulta
   `attachments.list` para el reuso de adjuntos contra el hilo, con sus **cuatro filtros nombrados
   exactamente** `entityType`, `entityId`, `checksum`, `uploadedBy`.
3. La regla reescrita **no** contiene una habilitación genérica (*"puede consultar"*, *"puede usar el
   plano de lectura"*) sin enumeración.
4. La regla reescrita declara que la derogación es **puntual: un caso habilitado, no un plano
   abierto**, y conserva el puntero a **ADR-004** como razón de que el **alta** no consulte antes de
   crear.
