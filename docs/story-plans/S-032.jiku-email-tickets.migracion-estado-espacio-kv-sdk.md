# Story Plan: S-032 (jiku-email-tickets) - Migrar el estado al Espacio KV del SDK

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-032](../stories/S-032.migracion-estado-espacio-kv-sdk.md)
- **Request de origen:** [REQ-008](../requests/REQ-008.migracion-al-kv-del-sdk.md)
- **Service:** jiku-email-tickets
- **Summary:** Todo el estado del conector (Mapa de Tickets y Mapa de Hilos) pasa del KV crudo de
  `@nats-io/kv` —que hoy entra por el re-export del build 1.1.0 vendoreado— al **Espacio KV del SDK**
  (`client.kv()`), con el build local de `jiku-ts@edd1064`. El slug se consulta **una vez por mail
  nuevo** con `lookupTicket()` (sin `watch()` ni copia en memoria), los hilos viven en el mismo
  espacio con el prefijo `hilos.` y **dejan de expirar**, el arranque diagnostica el fallo de
  `client.kv()` **por clase del SDK**, y se borran el `watch()`, los dos buckets, las cuatro variables
  `KV_*` y el aviso del TTL. El comportamiento observable no cambia, salvo dos cosas que la story
  decide: un motivo nuevo (`slug_no_consultable`) y que los hilos no expiran.

**Atómica por necesidad.** Apenas se cambia el tarball, `Kvm` y el `KV` de `@gravadigital/jiku/nats`
dejan de existir y todo lo que los importa deja de compilar. No hay un estado intermedio que pase el
typecheck: las tareas parten la story **por módulo dentro de la misma rama**, cada una con su
verificación local (`npx vitest run <archivos>`, que transpila sin typechequear), y el typecheck y la
suite completa recién quedan en verde en la Task 15.

**Fuera de alcance (otras stories del mismo REQ):**

- **S-033:** E2E del espacio real (carga en caliente con la clave completa, aislamiento por instancia
  e identidad, hilo de 91 días sobre el tick, caída del KV, permisos reales del servidor), la
  reescritura de la documentación de operación (precondición 8 del README, comandos de U-02,
  `.env.example` en prosa, Parte 2 de `verificacion-e2e-manual.md`).
- **S-034:** ADR-001/002/004/006, los cuatro flujos, `overview.md` y el PRD.

**Patrones que se conservan:**

- **Dependencias por parámetro, en un objeto de opciones nombrado** (`{ client, logger }`,
  `{ space, slug, logger }`). Ningún módulo de `infra/kv` llama a `getLogger()` ni lee `process.env`:
  es lo que permite inyectar un logger de captura (`createLogCapture()`) en los tests.
- **Uniones discriminadas para resultados de tres estados**, nunca `T | undefined`:
  `ThreadLookupResult` es el precedente directo de `TicketLookupResult`.
- **Las operaciones del KV nunca lanzan en caliente**: el write absorbe su fallo con un `warn`; el
  lookup devuelve un estado distinguible de "sin match". Un solo intento, sin reintento (ADR-001).
- **El arranque falla rápido con un `AppError` propio** que expone su diagnóstico como **campos**
  (`diagnosis`, `errorClass`, `causes`…) y tiene **su propia rama** en `reportStartupFailure()`,
  separada de `BusConnectError` (cuando falla el KV, la conexión al bus funcionó).
- **Contexto de log PLANO de un nivel** (la redacción de Pino no tiene comodín profundo) y **mensaje
  estático**. Ningún campo se llama `key` (`REDACT_PATHS` lo redactaría en silencio).
- **Propiedades "no existe ningún camino de código que X"** afirmadas por **escaneo de `src/` con
  comentarios stripeados** (`test/shared/source-scan.ts`: `sourceFiles()`, `readSource()`).
- **Comentarios que explican el porqué** de cada decisión contraintuitiva (convención del servicio):
  los módulos nuevos llevan cabecera con sus razones, igual que `threads.ts`.

**Manejo de errores (convención `error-handling` + ADR-006):** clase específica que extiende
`AppError` (`code` estable en `SCREAMING_SNAKE_CASE`, `httpStatus = 500` porque es un fallo del
despliegue). `desconocido` es un diagnóstico legítimo: **nunca se mapea a otra causa**.

**Logging (convención `logging`):** `logger.info({ ...contexto }, 'mensaje estático')`; `warn` para
lo esperado y recuperable; `fatal` para el arranque que no puede seguir.

**Testing (convención `testing` custom del servicio):**

- Un NATS compartido por suite, arrancado en `globalSetup` (sin JetStream). Los tests del KV usan un
  contenedor propio con `-js` y **tag distinto** (`nats:2.11-alpine`) para no entrar en el conteo de
  `test/bus/shared-container.test.ts`. **El compartido sin JetStream es el doble gratis de "JetStream
  apagado".**
- **No se mockea el bus.** Se dobla sólo en el borde (IMAP por `MailSource`, el `PUT` por stub de
  `fetch`). Para "el KV falla en caliente" se envuelve el handle real con un `get()`/`put()` que
  rechaza: no se puede provocar contra un contenedor sano sin tirarlo abajo.
- **Toda clase de error del SDK manejada en producción tiene un test** que afirma el diagnóstico.
- Cliente del bus en tests: **`Client.fromConnection(nc, { instance, userId })`** con la conexión cruda
  de `@gravadigital/jiku/nats` (nunca `nats`). `TEST_INSTANCE = 'test'`, `TEST_USER_ID =
  'test-machine-user'` (`test/bus/helpers.ts`), así que el prefijo del espacio en tests es
  **`test.test-machine-user.`**.
- `describe` nombra la unidad; `it` el escenario (los tests del servicio están en español).

### Hallazgos verificados al planificar (no estaban en la story)

1. **El `KV` del SDK es una clase con campos privados ES (`#host`, `#prefix`) y constructor privado.**
   TypeScript la trata nominalmente: un objeto literal (un fake) **no es asignable a `KV`** sin
   `as unknown as KV`. Por eso el plan tipa el handle como **`KvSpace = Pick<KV, 'get' | 'put'>`**
   (ver "Diseño fijado por este plan"): los fakes lo satisfacen estructuralmente, y `delete()` deja de
   ser invocable sobre el handle **en tiempo de compilación** (refuerza CA-17).
2. **`get()` del SDK devuelve `Promise<KVEntry | undefined>`** con `value: Uint8Array` (no hay
   `.string()` ni `null`). Devuelve `undefined` cuando la clave nunca se escribió, se borró (marcador
   `DEL`/`PURGE`) o la expiró el TTL del bucket. La decodificación es `new TextDecoder().decode(entry.value)`.
3. **El truncado a primera línea de `causes` (el de `KvBucketMissingError` hoy) perdería los grants.**
   El mensaje de `JikuKVPermissionDenied` es multilínea: la primera línea es
   `jiku: kv: the bus refused binding the bucket ($JS.API.STREAM.INFO.KV_JIKU_KV)` y los tres grants de
   `requiredKVPermissions()` vienen **después**. CA-5 exige los grants en `causes`, así que
   `KvSpaceUnavailableError.causes` lleva el **mensaje completo** de cada error de la cadena.
4. **Diferencia de API fuera del KV entre el build 1.1.0 y `edd1064`:** en 1.1.0,
   `LoadedConfig.zitadel.issuer` era `string` (con default `'https://id.grava.io'` aplicado por
   `loadConfig()`) y el SDK exportaba `DEFAULT_ISSUER`; en `edd1064` `issuer` es **opcional y sin
   default**, y `DEFAULT_ISSUER` no se exporta. **No cambia el comportamiento:** `loadAppConfig()` ya
   hace `issuer: sdk.zitadel.issuer ?? env.JIKU_ISSUER` y el schema defaultea `JIKU_ISSUER` a
   `'https://id.grava.io'` (el mismo valor); el conector importa `DEFAULT_ISSUER` de su propio
   `#config/schema.js`. Lo único que queda mintiendo es el comentario de
   `test/config/index.test.ts` (líneas ~30-33, *"issuer NO es opcional en LoadedConfig desde el minor
   del SDK que trae el KV"*), que se corrige en la Task 1.
5. **El repo del SDK está en `../../jiku-ts`, limpio y en `edd1064`, sin `node_modules`.** `npm pack`
   dispara `prepack` (`npm run clean && npm run build`), que necesita `typescript`: hace falta
   `npm ci` en `jiku-ts` primero. El nombre que produce `npm pack` es `gravadigital-jiku-1.0.0.tgz`.
6. **El typecheck cubre `test/` y corre dentro de la suite** (`test/build-runtime.test.ts`). Al sacar
   `ruteo.ticketMap` y `kv` de `AppConfig`, **30 archivos de `test/`** con fixtures de `AppConfig` o
   literales de `ruteo` con `ticketMap` (27 que se adaptan y 3 que se borran, ver Task 12) dejan de
   compilar por propiedad en exceso, aunque Vitest los siga corriendo. Se limpian todos en la misma
   rama.
7. **Los tests del KV de hoy usan `threads.keys()` y `threads.delete()`** de `@nats-io/kv`
   (`countKeys()`/`keysOf()` en `tick-hilos.test.ts` y `tick-propiedades-kv.test.ts`). El `KV` del SDK
   **no lista claves**. El reemplazo es un espía de `put()` más `get()` dirigidos a las claves
   esperadas, sobre un **espacio fresco por test** (una identidad distinta por test: el prefijo los
   aísla, ya que no hay un bucket por test).
8. **No hay un estado intermedio que compile** (lo dice la story y se confirmó): `stores.ts`,
   `ticket-map.ts`, `threads.ts`, `tick.ts`, `scheduler.ts`, `test/infra/kv/helpers.ts`,
   `test/ingesta/fake-threads-kv.ts` y `scripts/local-worker.mjs` importan `Kvm` o el `KV` de `./nats`.

### ADRs Relevantes

#### ADR-001: Worker único sin persistencia propia

- **Decisión:** un solo proceso, sin base de datos; el `\Seen` de IMAP es el **único** mecanismo de
  idempotencia; procesamiento secuencial; sin reintento. Matizada por REQ-005: el estado vive en un
  almacén **del bus**, que no es persistencia propia. **REQ-008 no cambia lo que decide** (S-034 le
  agrega la nota de que el estado vive en el Espacio KV de `JIKU_KV`).
- **Implementation Rules (verbatim):**
  - El proyecto MUST ser un único proceso Node.js sin servidor HTTP: no expone puerto, no tiene
    framework web, no define rutas
  - El proyecto MUST NOT declarar dependencias de acceso a base de datos: `pg`, `sequelize`,
    `sequelize-typescript`, `typeorm`, `prisma`, `knex` o equivalentes
  - El proyecto MUST NOT declarar `@aws-sdk/client-s3` ni ningún cliente de storage con credenciales
  - El proyecto MUST NOT persistir estado en disco: sin archivos de estado, sin SQLite, sin caché en
    disco, sin volumen montado de escritura
  - El único mecanismo de deduplicación MUST ser el flag `\Seen` de IMAP, aplicado con
    `messageFlagsAdd` por UID
  - Un mensaje MUST marcarse `\Seen` en el mismo paso en que se descarga y parsea, antes de publicar el
    comando
  - Un mensaje que no se pudo descargar MUST NOT marcarse `\Seen` (así el próximo tick lo reintenta)
  - Un comando fallido MUST NOT reintentarse: se loguea y se descarta el mail
  - El procesamiento MUST ser secuencial: un mail a la vez, un tick a la vez, sin `Promise.all` sobre
    mails ni sobre ticks
  - Los tres módulos internos (Ingesta, Ruteo, Publicación) MUST comunicarse por llamada de función
    dentro del proceso, sin transporte intermedio
  - El despliegue MUST correr **exactamente 1 instancia** por casilla de mail
- **Cómo aplica:** `lookupTicket()` hace **un solo intento**; el resultado no se cachea; la consulta
  ocurre **después** del `markSeen` y nunca saltea un mail (no es idempotencia); el KV **no** se usa
  para deduplicar.

#### ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus

- **Decisión:** el conector no implementa nada del protocolo del bus; usa el SDK, una conexión por
  proceso, y maneja los errores por las clases del SDK. **REQ-008 la cumple mejor:** el KV pasa a ser
  del SDK, con sus clases de error (S-034 agrega la nota; la mención de S-023 queda como historia).
- **Implementation Rules (verbatim):**
  - El cliente del bus MUST ser `@gravadigital/jiku` en rango `^1.0.0`
  - El proyecto MUST NOT declarar `nats` como dependencia directa
  - El conector MUST NOT construir subjects a mano: el subject se arma con `client.command()`, nunca con
    concatenación de strings
  - El conector MUST NOT armar ni parsear envelopes del protocolo a mano
  - El conector MUST NOT fijar `inboxPrefix` por su cuenta: lo fija el SDK siempre
  - La identidad MUST construirse con `ServiceUser.fromKeyFile()` — no con un token obtenido a mano ni
    con un JWT armado en el conector
  - `connect()` MUST llamarse **exactamente una vez** al arrancar el proceso, y el cliente resultante
    MUST conservarse por toda la vida del proceso. Prohibido conectar por mail o por tick
  - El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), **nunca** de una variable
    de entorno
  - La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los defaults a mano
  - El timeout MUST quedar en el default del SDK (**15000 ms**). MUST NOT bajarse — ver
    [ADR-006](ADR-006-observabilidad-por-logs.md)
  - `onTokenError` MUST estar registrado y MUST loguear el fallo del refresh como `error` sin terminar
    el proceso
  - El runtime MUST ser Node.js **≥ 22.12** (el `engines` floor del SDK es parte de su superficie
    pública: subirlo es un major)
  - El proyecto MUST usar **ESM** (`"type": "module"`): el SDK es ESM-only
  - Los errores del bus MUST manejarse por las clases del SDK (`JikuPermissionDenied`, `JikuFailure`,
    `JikuTimeout`, `JikuNoEndpoint`, `JikuInvalidRequest`), no inspeccionando strings de mensaje
- **Cómo aplica:**
  - `client.kv()` viaja por la **conexión única** (`client.connection`): no se abre ninguna conexión
    nueva, y `test/bus/source-properties.test.ts` (un solo `connect()`, ningún `from 'nats'`) pasa
    **sin modificarse** (CA-3).
  - El diagnóstico del arranque es un **`instanceof` contra `JikuNoBucket` y `JikuKVPermissionDenied`**
    importadas de la **entrada principal** `@gravadigital/jiku`. Sin parsear el mensaje, sin comparar
    `name` ni `code` (CA-6).
  - Las claves del KV no son "subjects armados a mano": el conector arma sólo la **parte derecha**
    (`tickets.alfa`); el subject (`$KV.JIKU_KV.…`, `$JS.API.DIRECT.GET.…`) lo arma el SDK.
  - **No se pasa ningún `timeoutMs` ni `signal`** a `client.kv()`, `get()` ni `put()`: rige el del
    cliente (`config.timeoutMs`, piso 15000). Story §Performance: *"No se agrega un timeout propio."*
  - **Ninguna dependencia directa nueva**; `@nats-io/kv` y `@nats-io/jetstream` salen del árbol y
    `@nats-io/nats-core` queda en **una** copia (criterio de S-023 CA-4, que sostiene los `instanceof`
    contra las clases del SDK).
  - El `file:vendor/…` no es un rango `^1.0.0`: es la misma excepción **temporal** que ya regía para
    el 1.1.0 (S-024), anotada en el `Dockerfile`, hasta que el SDK se publique.

#### ADR-004: Resolver el proyecto con un KV del bus y no usar el plano de lectura

- **Decisión de fondo (no cambia):** el proyecto se resuelve contra un mapa `slug → projectId` que el
  conector tiene a mano, **sin consultar el plano de lectura** y **sin validar el proyecto** contra Jiku.
  **REQ-008 reformula las reglas del `watch()`**: pasan a ser *un `get` puntual por mail, sin copia en
  memoria*, y el fallo de consulta es `slug_no_consultable`. **El texto de la ADR lo enmienda S-034;
  este plan implementa la reformulación.**
- **Implementation Rules vigentes hoy (verbatim):**
  - El Mapa de Tickets MUST vivir en un **bucket KV del bus**, y el conector MUST seguirlo con
    `watch()` sobre una copia en memoria *(S-025: antes era "desde variable de entorno o archivo
    montado, al arrancar")*
  - El conector MUST NOT crear el bucket. Un bucket inexistente MUST provocar **fail-fast** con un
    error que **nombre el bucket** *(S-024)*
  - Un bucket **vacío** MUST ser aceptado como estado válido: el worker arranca y descarta todo con log
  - El conector MUST esperar la **carga inicial completa** antes de schedular el primer tick, para que
    ningún mail se rutee contra un mapa a medio llenar *(S-025)*
  - Una entrada con valor mal formado MUST **ignorarse con `warn` que nombre la clave**, sin tumbar el
    watch ni el proceso *(S-025: …)*
  - Un `delete` en el bucket MUST **sacar la clave** de la copia en memoria *(S-025)*
  - Si el `watch()` se cae, el conector MUST **conservar la última copia buena** y reintentar. MUST NOT
    vaciar el mapa *(S-025: …)*
  - El slug extraído del mail MUST normalizarse **a minúsculas** antes de buscarlo (comparación en
    minúsculas **en las dos puntas**)
  - El valor de cada entrada MUST ser el `projectId` entero de Jiku. MUST NOT ser el nombre del proyecto
    ni su slug
  - El conector MUST NOT verificar contra Jiku que el `projectId` exista antes de publicar
  - El conector MUST NOT publicar en el plano de consultas del bus (`jiku-queries.*`) **para rutear**
  - El slug MUST extraerse del `recipient` con la regex `^<prefijo>\+([^@]+)@`, case-insensitive, con el
    prefijo configurable (default: `tickets`)
  - El `recipient` MUST tomarse de `Delivered-To`, con `To` como **único** fallback
  - Un mail sin match de slug MUST descartarse con log, sin crear nada
  - Un slug sin entrada en el mapa MUST descartarse con log que **nombre el slug buscado**
  - La copia del mapa MUST vivir sólo en memoria: MUST NOT escribirse a disco ni cachearse fuera del
    proceso. El bucket del bus **no** es "fuera del proceso" en este sentido: es la fuente, no una caché
- **Cómo aplica en S-032 (la reformulación de REQ-008, que manda sobre el texto viejo):**

  | Regla vigente | Después de S-032 |
  |---|---|
  | *"seguirlo con `watch()` sobre una copia en memoria"* | **Un `get` puntual por mail nuevo** (`lookupTicket()`), **sin copia en memoria** |
  | *"MUST NOT crear el bucket… fail-fast que nombre el bucket"* | Se conserva: `JIKU_KV` no se crea; `client.kv()` que falla → no arranca, con `bucket: 'JIKU_KV'` |
  | *"bucket vacío MUST ser aceptado"* | Se conserva como **"espacio sin `tickets.*`"** (CA-15) |
  | *"esperar la carga inicial completa"* | **Desaparece** (no hay carga inicial) |
  | *"valor mal formado MUST ignorarse con `warn` que nombre la clave"* | Se conserva: `warn` que **nombra el slug**, sin el valor crudo → `slug_no_mapeado` (CA-11) |
  | *"`delete` MUST sacar la clave de la copia"* / *"si el `watch()` se cae…"* | **Desaparecen** (no hay copia ni watch). Un borrado vale **desde el mail siguiente** |
  | Minúsculas en las dos puntas, `projectId` entero, sin validar el proyecto, sin plano de consultas, regex y `recipient` | **Sin cambios** |
  | *"Un slug sin entrada MUST descartarse con log que nombre el slug"* | Se conserva (lo decide `lookupTicket()`, lo loguea el tick) |
  | *"La copia del mapa MUST vivir sólo en memoria"* | Ya no hay copia; **nada cachea** el resultado de `lookupTicket()` (CA-14) |
  | — | **Nueva (REQ-008):** un fallo de la consulta descarta como **`slug_no_consultable`** (CA-12) |

#### ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito

- **Decisión:** logs JSON a stdout; cada mail deja al menos una línea con su `messageId` y su
  resultado; el motivo de descarte es un literal exacto; la línea del tick lleva seis contadores.
  **REQ-008 agrega un motivo** (`slug_no_consultable`); el texto de la ADR lo enmienda S-034, igual
  que S-026 hizo con `hilo_desconocido` (la desviación se declara en el comentario de
  `MotivoDescarte`).
- **Implementation Rules (verbatim):**
  - Los logs MUST ir a **stdout**. MUST NOT configurarse ningún transport de archivo, en ningún entorno
  - El formato MUST ser **JSON en producción**
  - El nivel por defecto MUST ser `info`, configurable por variable de entorno
  - MUST NOT loguearse nunca: credenciales (IMAP, key JSON, token, creds de NATS), tráfico IMAP crudo, el
    cuerpo del mail (`body`), el contenido de un adjunto
  - El cliente IMAP MUST configurarse con `logger: false`
  - **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado.
    Ningún mail termina sin rastro
  - Un alta exitosa MUST loguear `messageId`, `projectId` y el `id` del requisito creado, juntos
  - Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`,
    `sin_message_id`, `no_parseable`, `hilo_desconocido`)
  - Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para
    cargarlo)
  - Un fallo de comando MUST loguear la **clase de error del SDK** y, cuando exista, el `code` y el
    `hint()`. MUST NOT reducirse a un mensaje genérico de "falló el comando"
  - Un `errorCode` desconocido MUST loguearse con su `code` y su `hint()` sin mapearse a otro error
  - Cada tick MUST emitir una línea con los seis contadores: `ingestados`, `parseados`, `creados`,
    `descartados`, `fallidos`, `comentados`
  - Un tick que difiere mails por el cap MUST loguear un `warn` con **cuántos** quedaron diferidos
  - Un fallo del refresh del token MUST loguearse como `error` (vía `onTokenError`) sin terminar el
    proceso
  - El timeout del comando MUST quedar en **15000 ms** (el default del SDK). **MUST NOT bajarse**
  - Un tick salteado por solapamiento MUST loguear un `warn`
  - MUST NOT implementarse endpoint de healthcheck ni exportador de métricas en v1
- **Cómo aplica:**
  - El catálogo pasa a **siete** literales con `slug_no_consultable`. Su distinción frente a
    `slug_no_mapeado` es *"cargar el slug"* contra *"arreglar el KV"* (mismo argumento que
    `hilo_desconocido` vs `es_respuesta`).
  - `slug_no_consultable` es un descarte: **suma en `descartados`**; la línea del tick sigue con **seis**
    contadores.
  - El descarte por `slug_no_mapeado` **y** por `slug_no_consultable` lleva el `slug` (el segundo para
    poder reconstruir los mails desde la casilla, Riesgo 3).
  - Ningún log nuevo lleva el **valor crudo** de una entrada del KV ni el cuerpo del mail.

- **Decisión:** la suite completa con NATS reales (`npm run test:teardown`) es el **único gate**; los

  - El job de test MUST correr la suite **completa** con `npm run test:teardown`. MUST NOT filtrarla

  - Sólo `release:dev` y `release:main` (y su plantilla `.release`) MUST hacer `docker login` o

  - Los releases MUST depender de `test` (`needs: [test]`) y sus `rules` MUST nombrar exactamente `dev`

  - El login MUST usar `--password-stdin` con `$CI_REGISTRY_USER` / `$CI_REGISTRY_PASSWORD`. MUST NOT

- **Los valores no cambian de formato:** entero en texto, leído con `parsePositiveId()`
  (`src/infra/kv/parse.ts`, sin cambios) sobre `new TextDecoder().decode(entry.value)`.
- **La clave del hilo no cambia:** `sha256hex()` sobre el `Message-Id` **crudo**, sin normalizar
  (invariante 23). Sólo gana el prefijo `hilos.`.
- **Los prefijos son constantes del código**, no configuración: cambiarlos dejaría huérfanas todas las
  entradas cargadas, y con una variable de entorno bastaría un typo.
- **El slug va en minúsculas** (invariante 4): lo normaliza `routeMail()` como hoy. Una entrada cargada
  como `tickets.Alfa` nunca matchea.

**Invariantes del PRD que esta story implementa o preserva (texto del PRD):**

- **3.** Un mail que no resuelve a un proyecto **no crea nada**. Crear un Requisito en el proyecto
  equivocado lo haría visible a un cliente que no debía verlo… El descarte es la falla segura.
- **4.** El slug se compara **siempre en minúsculas**, en las dos puntas del mapa.
- **22.** No se loguean nunca: credenciales, tráfico IMAP crudo, el cuerpo del mail, el contenido de un
  adjunto **ni el texto de un comentario**.
- **23.** La clave del Mapa de Hilos es el **sha256 en hex del `Message-Id` crudo**, nunca el
  `Message-Id` normalizado o escapado.
- **24.** Se escribe una entrada por **cada mail del hilo**: al crear el Requisito y al comentar con
  éxito. Si el comentario falla, **no se escribe** la entrada de esa respuesta.
- **26.** Una respuesta con match en el hilo **se comenta sin evaluar el slug**.
- **27.** Un fallo del write al Mapa de Hilos **nunca cancela el alta**: se loguea y la consecuencia
  asumida es que ese hilo no va a rutear después.
- **30 (REQ-008).** Si la consulta del slug **no se pudo hacer**, el mail se descarta con
  **`slug_no_consultable`** y una línea que nombra el slug, y **no se crea nada**. Un slug que no puede
  ser clave del KV, o una entrada con valor mal formado, **no** son este caso: se descartan como
  `slug_no_mapeado`, porque nunca van a resolver.
- **31 (REQ-008).** El conector accede al KV **sólo por su Espacio KV** (`client.kv()`), y nunca lee ni
  escribe claves de otra identidad ni de otra instancia. No declara el KV crudo ni lo toma de ningún
  re-export.
- **32 (REQ-008).** Una entrada del Mapa de Hilos **no expira**: el conector no aplica TTL ni lo
  verifica.

#### `mapa-de-hilos-en-kv` y `publicacion-requirements-comment`

**Hoy:** Paso 1, clave `sha256hex(Message-Id crudo)`; Paso 2, write **después** del alta, fuera de su
camino crítico, que **no lanza** (`warn` `{ messageId, messageIdHash, requirementId }`); Paso 3,

entrada mal formada y **corta** si `get()` rechaza (`{ found: false, consultable: false }` →

**Después:** mismo comportamiento con tres diferencias:

- El handle es **el espacio** (`space`), no `MAIL_THREADS`.
- La clave gana el prefijo: **`hilos.` + sha256hex(Message-Id)**. El campo `messageIdHash` del log
  sigue siendo **el hash solo** (64 hex), como hoy.
- `get()` devuelve **`undefined`** en lugar de `null`, y `lookupThread()` lo trata igual: "no está",
  sigue con la referencia siguiente.
- El `warn` del write fallido **gana `errorClass`** (CA-16): `{ messageId, messageIdHash, requirementId, errorClass }`.
- **Sin TTL**: una entrada de cualquier antigüedad matchea, porque **nada lee `entry.created`**.

```ts
export type TicketLookupResult =
  | { readonly found: true; readonly projectId: number }
  | { readonly found: false; readonly consultable: true }    // no está → slug_no_mapeado
  | { readonly found: false; readonly consultable: false };  // no se pudo consultar → slug_no_consultable

export interface LookupTicketOptions {
  readonly space: KvSpace;
  /** El slug YA en minúsculas (lo normaliza routeMail(), invariante 4). */
  readonly slug: string;
  readonly logger: Logger;
}

/** UN get, UN intento, sin caché. NUNCA lanza. */
export async function lookupTicket({ space, slug, logger }: LookupTicketOptions): Promise<TicketLookupResult> {
  if (!isStorableSlug(slug)) return { found: false, consultable: true };   // sin round-trip (Riesgo 7)

  let entry: KVEntry | undefined;
  try {
    entry = await space.get(ticketKey(slug));
  } catch (error) {
    logger.warn({ slug, errorClass: errorClassOf(error) }, 'no se pudo consultar el Mapa de Tickets; el mail se descarta como slug_no_consultable');
    return { found: false, consultable: false };
  }
  if (entry === undefined) return { found: false, consultable: true };

  const projectId = parsePositiveId(new TextDecoder().decode(entry.value));
  if (projectId === undefined) {
    // Nombra el slug, NUNCA el valor crudo (ADR-004 reformulada; invariante 22).
    logger.warn({ slug }, 'una entrada del Mapa de Tickets tiene un projectId invalido y se ignora');
    return { found: false, consultable: true };
  }
  return { found: true, projectId };
}
```
