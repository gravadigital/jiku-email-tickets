# Story Plan: S-004 (jiku-mail-connector) - Identidad y conexión única al bus

## Status

**Status:** Ready

## Story Reference

- **Story:** [S-004](../stories/S-004.identidad-conexion-unica-bus.md)
- **Service:** jiku-mail-connector
- **Summary:** El worker construye su identidad desde la key del machine user con
  `ServiceUser.fromKeyFile()`, abre **exactamente una** conexión al bus que conserva por toda la vida
  del proceso, y falla al arrancar —de forma legible, diciendo cuál sistema lo rechazó— cuando alguna
  precondición de despliegue no está. Cierra el flujo de arranque que S-002 y S-003 dejaron a mitad de
  camino; no publica ningún comando (eso es S-005).

## Architectural Context

### Hallazgos de la verificación contra el SDK instalado

Antes de todo lo demás, porque **cambian el plan** respecto de lo que la story asumía. Los cinco se
verificaron ejecutando el SDK instalado (`@gravadigital/jiku@1.0.0`), no leyendo su documentación.
Están acá arriba para que nadie los redescubra a mano.

**H1. `ServiceUser` valida la key en el CONSTRUCTOR, y tiene cuatro fallos distintos, no uno.**
CA-4 menciona dos (archivo ausente, JSON mal formado). Verificados los cuatro, todos `JikuError`:

| Entrada | Error del SDK | `cause` |
|---|---|---|
| Archivo inexistente | `jiku/auth: reading the service account key {path}` | `Error` con `code: 'ENOENT'` |
| JSON mal formado | `jiku/auth: parsing the service account key — this must be the JSON file Zitadel produced for a machine user, not a PEM on its own` | `SyntaxError` de `JSON.parse` |
| JSON válido sin `key`/`keyId`/`userId` | `jiku/auth: the service account key is missing key, keyId or userId; it does not look like a Zitadel machine user key` | — |
| `key` que no es una private key leíble | `jiku/auth: the \`key\` field of the service account is not a private key this runtime can read` | `Error` con `code: 'ERR_OSSL_UNSUPPORTED'` |

**Ninguno de los cuatro filtra el contenido de la key.** Verificado escribiendo un archivo cuyo
contenido era `-----BEGIN RSA PRIVATE KEY-----SUPERSECRETVALUE` y comprobando que ni el `message` ni
la cadena de `cause` contienen `SUPERSECRET`. Eso **no exime** de afirmarlo con un test: lo que hoy no
filtra puede filtrar en un minor, y CA-4 es precisamente sobre eso.

**H2. Los fallos de conexión SÍ son testeables de verdad, contra un NATS real.** CA-10 asume que sólo
existe `Client.fromConnection()` —que saltea el handshake de auth— y por lo tanto que no se puede
probar ningún rechazo. **Es superable:** un contenedor NATS levantado con `--auth <token>` produce un
`Authorization Violation` real, y el `connectError()` del SDK lo traduce. Verificado end-to-end:

| Escenario | Resultado verificado |
|---|---|
| NATS `--auth the-right-token` + token correcto | Conecta. `client.userId` = el `subject()` del token source, `inboxPrefix` = `_INBOX.i3cfdw5mxvnxogkd`, `closed === false` |
| Mismo NATS + token equivocado | `JikuError`: `jiku: the bus refused the credentials` (+ las cuatro causas usuales, `projectId` incluido) |
| `auth.token()` que lanza | `JikuError`: `jiku: obtaining an access token`, con la excepción original en `cause` |
| Host irresoluble | `JikuError`: `jiku: no NATS server answered at {servers}`, `cause.message` con `ENOTFOUND` |
| Puerto cerrado (`nats://127.0.0.1:1`) | `JikuError`: `jiku: connecting to {servers}` — **la rama genérica**, ver H5 |

Esto convierte los tests de CA-5 y CA-10 en tests reales en lugar de mocks. El costo es **un
contenedor NATS más** (con `--auth`, por archivo), porque el compartido del `globalSetup` no tiene
auth y no puede tenerlo sin romper los tests de S-001 que dependen de conectarse sin credenciales.

**H3. El `user-id` NO requiere red.** `serviceUser.userId` (getter) y `await serviceUser.subject()`
salen de la key directamente. Verificado: con una key RSA generada localmente y un `issuer`
inalcanzable, ambos devuelven `machine-user-abc` sin ninguna llamada de red. **CA-2 es afirmable en un
test unitario**, no sólo por inspección de código.

Corolario para los tests: `ServiceUser` **exige una private key RSA real** para construirse (el
constructor llama a `createPrivateKey`). Un fixture con `key: 'fake'` falla con
`ERR_OSSL_UNSUPPORTED`. Los fixtures se generan con `generateKeyPairSync('rsa', { modulusLength: 2048 })`
y `export({ type: 'pkcs1', format: 'pem' })` — el mismo formato `-----BEGIN RSA PRIVATE KEY-----` que
entrega Zitadel.

**H4. `connect()` pide el token ANTES de abrir el socket**, deliberadamente. Del código del SDK:

> *"Fail before connecting if no token can be had. A NATS authorization violation says nothing about
> which of the two credentials was the problem."*

Consecuencia para CA-5: **hay dos fallos distintos donde la story ve uno.** Zitadel no entregó el
token (`jiku: obtaining an access token`) y el bus rechazó el token (`jiku: the bus refused the
credentials`) son causas diferentes, con arreglos en lugares diferentes. El log tiene que
distinguirlas — es exactamente el criterio de ADR-006 aplicado un nivel más adentro.

**H5. La clasificación NO puede apoyarse en el texto del mensaje del SDK.** El regex de
`connectError()` es `/no servers available|CONNECTION_REFUSED|ECONNREFUSED|ENOTFOUND/i`, pero
`@nats-io/transport-node` reporta un puerto cerrado como `"connection refused"` **en minúscula y con
espacio**, que no matchea ninguna de las cuatro alternativas. Verificado: un puerto cerrado cae en la
rama genérica (`jiku: connecting to ...`) mientras un host irresoluble cae en la específica. Las dos
son `bus_inalcanzable` para el conector. Por eso `diagnoseConnectFailure()` clasifica por
**estructura** (`isJikuError`, la cadena de `cause`, `cause.code`), nunca por `String(error).includes(...)`.

**H6 (fuera de alcance de esta story, pero registrado acá porque su síntoma aparece tres servicios más
allá).** El SDK documenta que el scope **`profile` es obligatorio**:

> *"`profile` LOOKS UNNECESSARY FOR A SERVICE AND IS NOT. Jiku's auth-callout publishes an
> authentication event that core turns into a row in `users`, and core REQUIRES a name on that event.
> [...] a token minted with `openid` alone produces a nameless event, core discards it, no row is
> created, and every subsequent request is refused with `caller_not_authorized`. The failure is silent
> and lands three services away from its cause."*

El default del SDK ya es `['openid', 'profile']`, así que **lo correcto es NO pasar `scopes`**. Queda
como comentario en el código (Tarea 1) para que nadie lo "optimice" a `['openid']` más adelante: eso
rompería CA-9 —la fila en `users` no se crearía— con un síntoma que no señala su causa.

### Service Architecture

**Tipo:** `worker` en `node`. Sin HTTP, sin puerto, sin healthcheck, sin base de datos (ADR-001).

Estructura relevante, con lo que esta story agrega marcado:

```
src/
├── index.ts                    # MODIFICA: encadena identidad -> conexión (Tarea 4)
├── config/
│   ├── env.ts                  # el ÚNICO lector de process.env de todo el servicio
│   ├── schema.ts               # envSchema (10 variables), MIN_TIMEOUT_MS, defaults
│   ├── errors.ts               # ConfigValidationError
│   └── index.ts                # loadAppConfig() -> AppConfig
├── domain/
│   ├── ingesta/                # vacío (FG-2)
│   ├── ruteo/                  # vacío (FG-3)
│   └── publicacion/            # vacío (S-005)
├── infra/
│   └── bus/                    # CREA (Tareas 1-3): identity.ts, errors.ts, connection.ts
└── shared/
    ├── logger.ts               # createLogger/initLogger/getLogger (S-003)
    ├── log-redaction.ts        # REDACT_PATHS / REDACT_CENSOR (S-003)
    ├── service-info.ts         # SERVICE_NAME
    └── errors/                 # AppError (base.ts) + index.ts
test/
├── global-setup.ts             # UN NATS compartido para toda la suite (sin auth)
├── bus/helpers.ts              # setupTestBus() con Client.fromConnection()
├── bus/auth-helpers.ts         # CREA (Tarea 5): NATS con --auth, fake token source, key RSA
└── shared/log-capture.ts       # createLogCapture() (S-003)
```

**Patrones vigentes en el servicio:**

- **Puerto de lectura único del entorno.** Sólo `src/config/env.ts` menciona `process.env`, y hay un
  test que escanea `src/` para afirmarlo (`test/config/source-properties.test.ts`). El código de esta
  story **recibe todo por parámetro** — igual que el logger de S-003.
- **Construcción explícita, no efectos de import.** `loadAppConfig()` es async y el logger se
  inicializa desde `src/index.ts`. Nada se construye como efecto de importar un módulo.
- **Tests de propiedad por escaneo de fuentes.** Cuando un criterio es "no existe ningún camino de
  código que X", se afirma escaneando `src/` con los comentarios stripeados. El patrón está en
  `test/config/source-properties.test.ts` y esta story lo reusa para CA-2, CA-3 y CA-9.

**Manejo de errores:** jerarquía sobre `AppError` (abstracta, con `code` público y `httpStatus`).
Nunca `throw new Error(...)` en código de dominio. `httpStatus` se declara aunque el servicio no
exponga HTTP, para no divergir de la convención; su valor no se consume.

**Logging:** una sola instancia de Pino, a stdout siempre, JSON en producción, `redact` cableado.
Objeto de contexto primero, mensaje estático segundo. Nunca credenciales.

**Testing:** Vitest, un contenedor NATS compartido en `globalSetup`, `fileParallelism: false`
(secuencial: bus compartido). Doblar **sólo en el borde**. `testTimeout: 30_000`.

### Convenciones activas (del manifest)

`manifest.yaml` declara: `language: node`, `type: worker`, y las convenciones `logging`, `env-config`,
`validation`, `error-handling`, `testing`, `module-imports`, `dockerfile`. Las dos últimas relevantes
para esta story son **custom del servicio** (`docs/architectures/jiku-mail-connector/conventions/`) y
reemplazan a las del catálogo.

#### `module-imports` (custom) — reglas que esta story tiene que cumplir

Los imports intra-proyecto usan el mecanismo **nativo** de Node (`package.json#imports`), con el
prefijo `#` que Node exige. **No** `@/` (no es un subpath válido) y **no** paquetes de reescritura
(`tsc-alias`, `module-alias`) ni loaders ESM: están prohibidos.

- El mapeo se declara **dos veces**, apuntando a **árboles distintos**: `tsconfig.json#paths` a
  `./src/*` (compilación), `package.json#imports` a `./dist/*` (runtime). Si los dos apuntaran al
  mismo lugar, uno estaría mal.
- El specifier lleva extensión `.js` explícita, **incluso desde un `.ts`**: ESM no la infiere.
- **`#infra/*` ya está declarado en ambos lados**, así que esta story **no** necesita tocar
  `package.json` ni `tsconfig.json`. Verificado en los dos archivos.
- Orden de imports: librerías externas, luego imports absolutos del proyecto, luego relativos del
  mismo módulo, separados por línea en blanco.
- La resolución en runtime se verifica **ejecutando el `dist/` compilado**, no con `tsc --noEmit`:
  `tsc` no reescribe specifiers, así que un mapeo roto pasa el typecheck y muere al arrancar. Ya hay
  un test que lo cubre (`test/build-runtime.test.ts`).
- Vitest corre sobre las fuentes, así que tiene su propio `resolve.alias` en `vitest.config.ts`
  mapeando los cuatro prefijos a `src/`. **`#infra/` ya está mapeado ahí también.** Verificado.

#### `testing` (custom) — reglas que esta story tiene que cumplir

Reemplazo local del `testing` del catálogo: **sin base de datos y sin servidor HTTP** (ADR-001). Lo
que queda es Vitest, la disciplina de contenedor compartido y la ejecución secuencial.

- **Un NATS compartido por suite, arrancado en `globalSetup`.** Nunca un contenedor en un `beforeAll`
  por archivo, y nunca dentro de un `it`.
  - **Excepción justificada de esta story:** los tests de rechazo de conexión necesitan un NATS con
    `--auth`, que el compartido no puede tener (rompería los tests de S-001 que conectan sin
    credenciales). Es **un** contenedor extra, arrancado en el `beforeAll` de **un solo archivo** y
    parado en su `afterAll`. La regla existe para evitar N contenedores simultáneos; uno más,
    acotado a un archivo y con una razón escrita, no es lo que la regla prohíbe. Queda documentado
    en el propio helper.
- **Nunca agregar un contenedor de base de datos, migraciones o seeds.** Este servicio no tiene base.
- **No mockear el bus.** Los tests de integración usan el contenedor real.
- **Importar el cliente NATS de `@gravadigital/jiku/nats`, nunca de `nats`.** Vale igual en tests que
  en producción.
- **Doblar sólo en el borde.** Nunca mockear funciones de dominio propias.
- **Cada clase de error del SDK que el código maneja en producción tiene su test** que afirma el
  diagnóstico que produce. El valor de ADR-006 es el mapeo, y un mapeo sin test no es un mapeo.
- **Sin sleeps de reloj para esperar una condición.** Usar las estrategias `Wait.*` y esperar la
  condición observable.
- **Salida de logs callada** (`LOG_LEVEL=silent` o sink en memoria), pero **nunca silenciar errores
  globalmente**: un error tragado en un servicio cuyo único output son los logs es el peor artefacto
  de test posible.
- Archivos de test bajo `test/` o junto al código, sufijo `.test.ts`. `describe` nombra la unidad,
  `it` el escenario.
- **Gotcha declarado:** `Client.fromConnection()` saltea el handshake de auth, así que **no prueba
  nada** sobre Zitadel, el rol ni el prefijo de inbox. Ver H2: esta story mejora eso parcialmente con
  el NATS `--auth`, que sí ejercita el rechazo de credenciales del servidor — pero **sigue sin probar
  el auth-callout ni el rol `internal-app`**, que no existen en un NATS pelado. Esa verificación sólo
  ocurre contra un despliegue real.

#### `_base` (node) — lo aplicable

- TypeScript obligatorio, `strict: true`, sin `any` fuera de bordes con librerías sin tipos.
- Nombres: archivos y carpetas `kebab-case`, clases `PascalCase`, funciones y variables `camelCase`,
  constantes globales `SCREAMING_SNAKE_CASE`, tipos `PascalCase` sin prefijo `I`.
- Fechas en los bordes del sistema: **ISO 8601 UTC**. El log es el borde de este servicio (ya
  configurado con `pino.stdTimeFunctions.isoTime`).
- `async/await` sobre `.then()`. Una promesa sin `await` en un flujo crítico es un error.
- **Comentarios: por defecto ninguno; comentar sólo el POR QUÉ** cuando no es obvio (workaround,
  restricción externa, decisión sorprendente). Este servicio comenta densamente los "por qué"
  verificados, y es deliberado — ver el código de S-002 y S-003.

#### `error-handling` (catálogo) — lo aplicable

- Siempre errores específicos; nunca `throw new Error("...")` en código de dominio.
- Los `code` son **parte del contrato público**: cambiar uno es un breaking change.
- Ni `message` ni `details` llevan información sensible.
- Cada error tiene **un lugar canónico** donde se lanza. Si el mismo error puede surgir en N lugares,
  se extrae un helper.

#### `logging` (catálogo) — lo aplicable

- `logger.info({ context }, 'mensaje estático')`. **Nunca** interpolar variables en el mensaje.
- Niveles: `error` para un error que rompió una operación; `warn` para lo inesperado pero recuperable;
  `fatal` para "el servicio no puede continuar".
- Pino serializa `err` automáticamente con stack cuando es un `Error`.
- **Nunca** loguear tokens, credenciales, API keys. Confiar en `redact` **y además** no incluirlos.
- En tests: silenciar o usar un transporte de test. No contaminar la salida de CI.

### Relevant ADRs

#### ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus

**Decisión:** se consume el SDK `^1.0.0`. El conector **no implementa nada** del protocolo del bus:
delega la construcción del subject, el envelope, el hash del prefijo de inbox, la obtención y el
refresh del token, la entrega del token como getter, y la traducción de errores a clases tipadas.

**Contexto que justifica la decisión (las tres trampas del bus).** Ninguna de las tres falla
señalando su causa, y es por eso que se delegan:

1. **El prefijo de inbox.** Una conexión puede suscribirse a exactamente un inbox: el callout mintea
   el permiso sobre `_INBOX.{hash(sub)}.>`. Cualquier otro prefijo —incluido **el aleatorio que genera
   todo cliente NATS por default**— hace que la reply se publique donde nadie escucha. La request
   expira **sin ningún error visible**, y la violación de permisos queda en el log del *servidor*
   NATS, no del cliente. El síntoma apunta a que `core` está caído. No lo está.
2. **Las dos credenciales.** Se necesitan el creds del sentinel *y* el token de Zitadel, y ninguna
   alcanza sola: el creds se niega permisos a sí mismo, y lo que mintea los permisos reales es el
   token. Un token sin el claim de roles **no conecta a nada**, y el error dice sólo
   `Authorization Violation`.
3. **El token en un reconnect.** El auth-callout evalúa el token **al conectar**, y NATS no revalida
   después. Un reconnect vuelve a correr el callout, así que un token vencido hace que **el reconnect**
   sea rechazado — no la operación en curso. El cliente tiene que entregarle al bus **una función, no
   un string**.

**Implementation Rules (copiadas completas y verbatim):**

- El cliente del bus MUST ser `@gravadigital/jiku` en rango `^1.0.0`
- El proyecto MUST NOT declarar `nats` como dependencia directa
- El conector MUST NOT construir subjects a mano: el subject se arma con `client.command()`, nunca con
  concatenación de strings
- El conector MUST NOT armar ni parsear envelopes del protocolo a mano
- El conector MUST NOT fijar `inboxPrefix` por su cuenta: lo fija el SDK siempre
- La identidad MUST construirse con `ServiceUser.fromKeyFile()` — no con un token obtenido a mano ni
  con un JWT armado en el conector
- `connect()` MUST llamarse **exactamente una vez** al arrancar el proceso, y el cliente resultante
  MUST conservarse por toda la vida del proceso. Prohibido conectar por mail o por tick
- El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), **nunca** de una variable
  de entorno
- La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los defaults a mano
- El timeout MUST quedar en el default del SDK (**15000 ms**). MUST NOT bajarse — ver ADR-006
- `onTokenError` MUST estar registrado y MUST loguear el fallo del refresh como `error` sin terminar
  el proceso
- El runtime MUST ser Node.js **≥ 22.12** (el `engines` floor del SDK es parte de su superficie
  pública: subirlo es un major)
- El proyecto MUST usar **ESM** (`"type": "module"`): el SDK es ESM-only
- Los errores del bus MUST manejarse por las clases del SDK (`JikuPermissionDenied`, `JikuFailure`,
  `JikuTimeout`, `JikuNoEndpoint`, `JikuInvalidRequest`), no inspeccionando strings de mensaje

> **Nota del planificador sobre la última regla.** Las cinco clases que nombra son las de **fallo de
> comando** (S-005). Los fallos de **conexión** de esta story llegan como `JikuError` a secas —
> verificado en H2: los cuatro escenarios devuelven `JikuError`, no subclases. La regla se cumple en
> su espíritu clasificando por estructura (`isJikuError`, la cadena de `cause`) y **no** por el texto
> del mensaje, que además es frágil (H5).

#### ADR-005: Identidad de machine user con el rol `internal-app`

**Decisión:** un machine user de Zitadel con Access Token Type = **JWT** y el rol `internal-app`,
construido con `ServiceUser.fromKeyFile()`. **Sin cambios** en `rules.yaml` ni en las plantillas del
callout: el conector se declara como un caller más del bus, usando el rol que Jiku ya tiene definido
exactamente para esto.

| Pieza | Definición |
|---|---|
| Tipo de identidad | Machine user de Zitadel, Access Token Type = **JWT** |
| Construcción | `ServiceUser.fromKeyFile()` (RFC 7523) |
| Rol | **`internal-app`**, asignado en el project de gestión de Zitadel |
| Token | JWT con claim de roles, ~1 h, **refrescado en background por el SDK** |
| `user-id` del subject | El `sub`, **derivado de la key** (`auth.userId`), nunca de una variable |
| Fila en `users` | **La crea Jiku sola** en la primera autenticación |
| Cambios en el auth-callout | **Ninguno** |

**Implementation Rules (copiadas completas y verbatim):**

- La identidad MUST ser un machine user de Zitadel con Access Token Type = **JWT**
- El rol asignado MUST ser **`internal-app`** en el project de gestión de Zitadel
- La identidad MUST construirse con `ServiceUser.fromKeyFile(keyFile, { issuer, projectId })`
- El `user-id` del subject MUST salir de `auth.userId` (derivado de la key). MUST NOT leerse de una
  variable de entorno: tiene que coincidir exactamente con el `sub` que el auth-callout lee para
  autorizar el subject
- `JIKU_PROJECT_ID` MUST estar configurado y MUST validarse al arrancar. Sin él el token no lleva el
  claim de roles y **no conecta a nada** (el error dice sólo `Authorization Violation`)
- La key JSON MUST leerse de un **archivo montado read-only**. MUST NOT estar horneada en la imagen ni
  pasarse por variable de entorno
- El access token MUST vivir **sólo en memoria**. MUST NOT escribirse a disco ni loguearse
- El creds del sentinel de NATS MUST montarse como archivo read-only
- El conector MUST NOT enviar la clave `actor` en el payload de ningún comando: es la única clave de
  identidad que el plano de escritura rechaza de plano
- Lo que el conector declare en `creator` / `uploader` MUST tratarse como informativo: `core` lo ignora
  y resuelve el actor del subject
- El conector MUST NOT crear ni intentar crear su fila en `users`: la crea Jiku en la primera
  autenticación
- El conector MUST NOT modificar `rules.yaml` ni las plantillas del auth-callout
- El conector MUST NOT verificar la identidad del remitente del mail (fuera de alcance v1, declarado)
- Un fallo del refresh del token MUST loguearse como `error` vía `onTokenError` y MUST NOT terminar el
  proceso

**El costo del rol, declarado sin minimizar.** `internal-app` concede **los dos planos completos**
(`{ commands: ALL, queries: ALL }`) y ubica al caller en la clase `connector`, que no recorta ninguna
fila en las consultas. El conector va a poder mucho más de lo que necesita (usa 1 comando de 20 en
esta story y ninguna consulta). Acotarlo exige un **rol nuevo** con su plantilla y su entrada en el
mapa de `core`, y eso modifica el producto (G-03). **Fuera de alcance v1, no descartado.**

**Riesgo relevante para esta story:** la entrega del evento que crea la fila en `users` **no es
durable** (NATS sin JetStream). Si se pierde, el conector queda sin fila hasta su próxima
autenticación; reconectar lo resuelve. Es una **dependencia declarada del producto, no un bug del
conector** — el implementador no tiene que codear nada para mitigarlo.

#### ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito

**Decisión:** logs estructurados a stdout, JSON en producción, **nunca a archivo**. Y el log distingue
explícitamente **qué sistema rechazó**.

**Por qué importa acá:** en Jiku, cuando una escritura falla, hay un usuario mirando una pantalla que
recibe un error. **Acá no hay nadie.** Un ticket perdido no tiene síntoma, y el log es el único lugar
donde deja rastro.

**El origen del rechazo, explícito** (tabla del ADR — es de comandos, o sea S-005, pero el criterio
es el que esta story aplica a los fallos de conexión):

| Clase del SDK | Quién rechazó | Dónde está el arreglo |
|---|---|---|
| `JikuPermissionDenied` | **El bus**, por subject, antes de que `core` viera nada | El rol en Zitadel. **No implica nada sobre `core`** |
| `JikuFailure` / `caller_not_authorized` | El bus dejó pasar; **`core` rechazó por rol** | Típicamente sin fila en `users`. **Reconectar lo corrige solo** |
| `JikuFailure` / `invalid_fields` | `core` aceptó el caller y rechazó **la forma** | El payload. **Es prueba de que el plano de escritura está abierto** |
| `JikuFailure` / `project_not_found` | `core`: el proyecto no existe | El Mapa de Tickets |
| `JikuTimeout` | Nada respondió: `core` caído o lento | **El mail se perdió** (ya está `\Seen`), sin reintento |
| `JikuNoEndpoint` | El bus dice **de inmediato** que nada está suscripto | Sin esperar el timeout |
| `JikuInvalidRequest` | Rechazado **localmente**: nada llegó a la red | Error de armado del conector |

**Implementation Rules (copiadas completas y verbatim; las de esta story marcadas con →):**

- → Los logs MUST ir a **stdout**. MUST NOT configurarse ningún transport de archivo, en ningún entorno
- → El formato MUST ser **JSON en producción**
- El nivel por defecto MUST ser `info`, configurable por variable de entorno
- → MUST NOT loguearse nunca: credenciales (IMAP, key JSON, token, creds de NATS), tráfico IMAP crudo,
  el cuerpo del mail (`body`), el contenido de un adjunto
- El cliente IMAP MUST configurarse con `logger: false`
- **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado.
  Ningún mail termina sin rastro
- Un alta exitosa MUST loguear `messageId`, `projectId` y el `id` del requisito creado, juntos
- Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`,
  `sin_message_id`, `no_parseable`)
- Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para
  cargarlo)
- → Un fallo de comando MUST loguear la **clase de error del SDK** y, cuando exista, el `code` y el
  `hint()`. MUST NOT reducirse a un mensaje genérico de "falló el comando"
- Un `errorCode` desconocido MUST loguearse con su `code` y su `hint()` sin mapearse a otro error
- Cada tick MUST emitir una línea con los cinco contadores: `ingestados`, `parseados`, `creados`,
  `descartados`, `fallidos`
- Un tick que difiere mails por el cap MUST loguear un `warn` con **cuántos** quedaron diferidos
- → Un fallo del refresh del token MUST loguearse como `error` (vía `onTokenError`) sin terminar el
  proceso
- → El timeout del comando MUST quedar en **15000 ms** (el default del SDK). **MUST NOT bajarse**
- Un tick salteado por solapamiento MUST loguear un `warn`
- → MUST NOT implementarse endpoint de healthcheck ni exportador de métricas en v1

#### ADR-001: Worker único sin persistencia (lo aplicable)

Prohíbe declarar `pg`, `sequelize`, `sequelize-typescript`, `typeorm`, `prisma`, `knex`. Sin base
propia, sin migraciones, **sin estado en disco**. El conector no expone puerto, ni ruta, ni
healthcheck. Relevante para esta story en dos puntos concretos: el token **no se persiste** (CA-8,
TS-19) y no hay nada que agregar al `dist/` que escriba archivos.

### API Context

**No hay especificación OpenAPI para este servicio, y su ausencia es una decisión declarada, no un
hueco.** `docs/apis/` está vacío. El conector no expone HTTP, ni puerto, ni suscripción a subjects de

#### Zitadel — HTTPS, RFC 7523 (JWT profile grant)

El SDK firma con la private key de la key JSON y obtiene el access token. **El conector no implementa
nada del intercambio.** Del `d.ts` del SDK, verbatim:

> *"In Zitadel: create a machine user, set Access Token Type to JWT, grant it a role in the project,
> then add a KEY to it. Zitadel downloads a JSON file exactly once."*
>
> *"# ACCESS TOKEN TYPE MUST BE JWT — The auth-callout validates the token as a JWT against the
> issuer. A machine user left on the default opaque `Bearer` token type gets a token the callout
> cannot read, and the connection is refused. This is the single most common misconfiguration of this
> flow."*

Forma de la key JSON (`ServiceAccountKey`, la que Zitadel entrega — **una sola vez**):

```jsonc
{
  "type": "serviceaccount",
  "keyId": "...",
  "key": "-----BEGIN RSA PRIVATE KEY-----\n...",   // ES la clave privada
  "userId": "...",                                  // ES el user-id del subject
  "expirationDate": "..."                           // opcional
}
```

Tipo declarado por el SDK:

```ts
interface ServiceAccountKey {
  type?: string;
  keyId: string;     // requerido
  key: string;       // requerido — la private key en PEM
  userId: string;    // requerido — el sub de los tokens que mintea
  expirationDate?: string;
}
```

Token resultante: JWT con claim de roles, **~1 h**, **sólo en memoria**, expuesto como **getter, no
como string**. `REFRESH_SKEW_MS = 60000`: el SDK trata como expirado un token que le queda menos de un
minuto, para absorber el skew de reloj y el tiempo de vuelo.

#### Bus NATS + auth-callout — vía el SDK

`connect()`, **exactamente una vez**. El callout evalúa el token al conectar; NATS **no revalida**
después.

Las cuatro cosas que `connect()` hace y un connect NATS a mano no (del código del SDK, verbatim):

> 1. *"It sets the inbox prefix to `_INBOX.<hash(sub)>`. Without it every request times out with no
>    error anywhere the caller can see."*
> 2. *"It takes the token from the TokenSource on every (re)connect via `tokenAuthenticator`, so a
>    reconnect after the token expired re-authenticates instead of being refused."*
> 3. *"It derives the caller identity from the token's `sub`, so no subject has to be written by hand
>    and none can disagree with the credential presenting it."*
> 4. *"It asks for a token BEFORE connecting, so a broken identity configuration fails with what is
>    actually wrong instead of with a NATS authorization violation that names neither credential."*

**El contrato exacto de `ConnectOptions`** (del `d.ts` instalado — sólo los campos que esta story usa,
con sus notas verbatim donde importan):

```ts
interface ConnectOptions {
  servers?: string | string[] | undefined;
  instance?: string | undefined;       // 'dev' | 'prod'. Default 'dev'
  creds?: string | Uint8Array | null | undefined;   // el CONTENIDO del creds
  credsFile?: string | undefined;      // la RUTA, leída al conectar. Node only
  auth: TokenSource;                   // REQUERIDO — "the only thing that decides what you may do"
  timeoutMs?: number | undefined;
  name?: string | undefined;           // default 'jiku-ts'
  userId?: string | undefined;         // "LEAVE IT UNSET" — ver abajo
  onTokenError?: ((error: unknown) => void) | undefined;
  nats?: Record<string, unknown> | undefined;
}
```

Dos notas del SDK que son **reglas para esta story**:

- Sobre `userId`: *"Overrides the caller identity used in subjects. **LEAVE IT UNSET.** It is derived
  from the token's `sub`, and the callout only authorises publishing under one's own id, so a value
  that disagrees with the token produces an authorization violation rather than access to somebody
  else's namespace. It exists for diagnostics."* → **el conector NO lo pasa** (CA-2, TS-17).
- Sobre `nats`: *"`servers`, `authenticator`, `inboxPrefix` and `name` are set by this library and
  cannot be overridden — the first three are what make a connection to this bus work at all."*

**El `TokenSource`, y por qué tiene un método async y otro sync** (del `d.ts`, verbatim — explica el
patrón 5 del PRD mejor que cualquier paráfrasis):

> *"The NATS client asks for the token through an authenticator that is SYNCHRONOUS —
> `tokenAuthenticator(() => string)` — and it calls it on every connect AND on every reconnect.
> JavaScript cannot block there to mint a token, so the two halves are split: `token` is the async
> one [...]; `currentToken` is the sync one [...] and it is what the authenticator hands to the
> server. That split is the whole reason a long-lived connection survives a token expiry."*

```ts
interface TokenSource {
  token(options?: TokenSourceOptions): Promise<string>;
  currentToken(): string;      // '' antes del primer token() exitoso
  subject(options?: TokenSourceOptions): Promise<string>;
  expiresAt?(): Date | undefined;
}
```

`ServiceUser` implementa `TokenSource` y además expone `get userId(): string` — **sincrónico y sin
red** (H3). `claims()` y `expiresAt()` también están disponibles.

**Superficie de `Client` que esta story usa** (del `d.ts`):

```ts
class Client {
  get userId(): string;         // el sub del token: la identidad en cada subject
  get instance(): string;
  get inboxPrefix(): string;    // "for diagnostics"
  get timeoutMs(): number;
  get connection(): NatsConnection;
  get connectedUrl(): string;
  get closed(): boolean;        // si close() fue llamado
  close(): Promise<void>;       // drena y cierra
  // command()/query()/list()/get()/... son de S-005, NO de esta story
}
```

Doc de la clase, verbatim: *"It is safe for concurrent use and **should be long-lived: one per
process, not one per request**. Connecting costs a round trip to the identity provider and a NATS
handshake that runs the auth-callout."* — es CA-3 escrito por el propio SDK.

**Gotcha de `close()`:** `Symbol.asyncDispose` existe, pero la sintaxis `await using` **necesita Node
24 y es un error de sintaxis en Node 22**, que es el runtime de este servicio. Usar `close()` en un
`finally`, nunca `await using`.

#### Clases de error del SDK

```ts
class JikuError extends Error { }                    // base, con brand Symbol.for
function isJikuError(value: unknown): value is JikuError;
class JikuInvalidRequest extends JikuError { }        // rechazo LOCAL, nada salió a la red
class JikuNotConnected extends JikuError { }          // uso de un Client cerrado o nunca conectado
class JikuTimeout extends JikuError { }
class JikuNoEndpoint extends JikuError { }
class JikuPermissionDenied extends JikuError {
  readonly subject: string;
  readonly method: string;
}
class JikuFailure extends JikuError {
  readonly code: ErrorCodeValue;
  readonly errorMessage: string | undefined;
  readonly details: ErrorDetails | undefined;
  readonly method: string | undefined;
  hint(): string | undefined;    // undefined cuando el code se explica solo
}
```

**`isJikuError()` es preferible a `instanceof`, y el SDK dice por qué**, verbatim:

> *"`instanceof` is the natural test in JavaScript and it is the one documented here, but it compares
> constructor identity, and two copies of this package in one dependency tree have two different
> constructors. A `Symbol.for` brand is registry-global, so `isJikuError` keeps working across copies
> where `instanceof` quietly stops."*

**Los mensajes exactos que produce `connectError()`** (los tres, del código del SDK — el implementador
los necesita para clasificar por estructura sin depender de ellos):

```
jiku: the bus refused the credentials
  The sentinel creds got you to the auth-callout; what it rejected is the Zitadel token. The usual causes:
    - the token carries no project ROLES claim (set projectId / JIKU_PROJECT_ID), so no rule matched
    - the role it carries has no rule in the callout, so the connection is refused by design
    - a machine user whose Access Token Type is not JWT
    - the access token expired between being minted and being validated
```
```
jiku: no NATS server answered at {servers}
  Check the URL and that you can reach it (set JIKU_SERVERS). A browser needs the server's WebSocket listener (wss://), not the TCP port.
```
```
jiku: connecting to {servers}          # la rama genérica — ver H5
```

Y el de `connectWith()` cuando falla la obtención del token: `jiku: obtaining an access token`.

#### Pasos del flujo (los de esta story, copiados verbatim)

**Paso 3: Construir la identidad desde la key**
- **Origen:** jiku-mail-connector · **Destino:** interno (lee un archivo montado read-only) · **Tipo:** Interno
- **Acción:** `ServiceUser.fromKeyFile(keyFile, { issuer, projectId })`. El `user-id` que irá en el
  subject sale de `auth.userId`, **derivado de la key y nunca del entorno** (invariante 17).
- **Ref:** S-004; ADR-005; NFR-S03

**Paso 4: Obtener el access token**
- **Origen:** jiku-mail-connector · **Destino:** Zitadel · **Tipo:** REST (HTTPS, RFC 7523)
- **Acción:** el SDK firma con la key y obtiene el access token — un JWT con claim de roles, ~1 h de
  vida. El conector **no implementa nada** del intercambio.
- **Response (éxito):** access token, **sólo en memoria**. Nunca a disco, nunca al log. El SDK lo
  expone como **getter, no como string**.
- **Ref:** S-004; ADR-005; NFR-S02

**Paso 5: Conectar al bus**
- **Origen:** jiku-mail-connector · **Destino:** Bus NATS + auth-callout · **Tipo:** Interno (conexión NATS vía SDK)
- **Acción:** `connect({ servers, instance, credsFile, auth, onTokenError })` — **exactamente una
  vez**. El cliente resultante se conserva por toda la vida del proceso. El callout evalúa el token
  **al conectar** y NATS **no revalida** después. `onTokenError` queda registrado.
- **Response (éxito):** cliente conectado. Una línea de log de arranque exitoso, **sin ninguna
  credencial**.
- **Ref:** S-004; ADR-002; C-14, NFR-P05

**Paso 6: Jiku crea la fila del conector en `users` (efecto lateral)**
- **Origen:** Bus NATS (auth-callout) · **Destino:** Jiku (`core`) · **Tipo:** Evento
- **Evento consumido:** el evento del auth-callout de la primera autenticación de esta identidad.
- **Operación de BD:** tabla `users` (base de Jiku), INSERT, campos `identity_type: service` y `email`
  en `NULL`.
- **El conector no la crea ni la pide** (G-03, ADR-005). La **verifica**, no la provoca. La entrega de
  este evento **no es durable** (NATS sin JetStream): si se pierde, el conector queda sin fila hasta su
  próxima autenticación, y reconectar lo resuelve.
- **Ref:** S-004 CA-9, CA-16 de S-005; ADR-005

**Paso 7: Refresh del token en background**
- **Origen:** jiku-mail-connector (SDK) · **Destino:** Zitadel · **Tipo:** REST (HTTPS), recurrente
- **Acción:** el SDK renueva el token al acercarse su expiración y actualiza el valor que el getter
  devuelve. **La misma conexión sigue en uso** — no se abre una segunda.
- **Si falla:** el callback `onTokenError` loguea `error` y **el proceso sigue vivo**. El token vigente
  sigue sirviendo; lo que se rompe es el próximo reconnect.
- **Ref:** S-004; C-15, NFR-R04

**Paso 1 (S-002):** `src/config/env.ts` —el **único** módulo que toca `process.env`— valida con

> **Precisión del planificador sobre las filas 4 y 5.** La tabla dice "clase del SDK + `hint()`", pero

> `JikuError` a secas y **no tienen `hint()`** (H2). Lo que el log de esta story emite es: el
> diagnóstico del conector, el nombre de la clase, el mensaje del SDK (que **ya trae** las causas
> probables) y la cadena de `cause`. El `hint()` se consulta **si existe**, sin asumirlo.

#### Resultado del flujo

**Éxito:** un proceso vivo con **exactamente una** conexión al bus, y una línea de log de arranque
exitoso en stdout **sin ninguna credencial**.

**Estado final:** proceso vivo con una conexión conservada por toda su vida; access token en memoria,
refrescándose en background; fila del conector en `users` de Jiku creada por Jiku sola
(`identity_type: service`, `email` en `NULL`); logs estructurados en stdout. **Ningún archivo
escrito.**

**Notas del flujo relevantes para el implementador:**

- **Las cinco precondiciones de este flujo son manuales y no verificables por código** (machine user,

  aporta es que cada fallo diga cuál de los sistemas lo produjo.**
- **Los tests no cubren este flujo de punta a punta:** el auth-callout y el rol `internal-app` no
  existen en un NATS pelado. La verificación real sólo ocurre contra un despliegue.

## Divergencias registradas en la implementación

Cinco cosas que la implementación resolvió distinto de lo que este plan preveía. Se registran acá
porque las cinco se verificaron ejecutando el SDK o la suite, no razonando sobre la documentación.

**D1. Hay un SEXTO modo de fallo de conexión: el creds ilegible.** El SDK lee `credsFile` en
`readCredsBytes()` **antes** de abrir el socket y lo envuelve en
`jiku: the sentinel creds file "..." is unreadable`. Ni la story ni este plan lo enumeraban. Su
arreglo está en el **montaje del archivo** —no en Zitadel ni en la red— así que se diagnostica
aparte (`creds_ilegible`) en vez de colapsarlo en `bus_inalcanzable`.

**D2. `diagnoseConnectFailure()` NO clasifica el fallo de token; lo hace `connectToBus()`.** El plan
asumía que la función podría distinguir las tres causas por estructura. Verificado que no: la
excepción que lanza un `TokenSource` puede ser cualquier cosa (un fetch fallido, un `OAuthError`, un
`TypeError`) y no trae ninguna marca, así que por estructura es **indistinguible de un fallo
inclasificable**. Atribuirla por descarte —"si no es red ni creds ni autorización, debe ser
Zitadel"— habría violado el criterio 5 de la Tarea 2, que exige devolver `'desconocido'` antes que
adivinar. La solución: **`connectToBus()` pide el token él mismo antes de `connect()`**, así la
atribución es positiva —viene de la llamada que produjo el error— en vez de por eliminación. No
cuesta un round-trip de más: el SDK cachea el token.

**D3. `ConnectDiagnosis` tiene siete valores, no cuatro.** A los cuatro del plan se suman
`creds_ilegible` (D1), `key_ilegible` (que produce `src/index.ts` al loguear un `KeyLoadError`, para
que las dos ramas del `catch` hablen el mismo vocabulario) y `refresh_del_token_fallo` (que produce
`reportTokenRefreshFailure()`). Los tres últimos **no** los devuelve `diagnoseConnectFailure()`: es
el vocabulario del **campo `diagnosis` del log**, que es más ancho que el de esa función.

**D4. El test de reconexión (TS-21) exige fijar el puerto del host.** `restart()` de testcontainers
levanta el contenedor con un mapeo de puerto **nuevo**, y el cliente NATS sigue reintentando contra
el endpoint con el que se conectó. Con el puerto efímero por default el reconnect **no puede ocurrir
jamás**: el test expira a los 120 s sin haber probado nada. Con el puerto fijo, el archivo entero
pasa de 125 s a 6,8 s.

**D5. TS-22 no puede probar el puerto cerrado a nivel de proceso.** Es consecuencia directa de H4: el
token se pide antes de abrir el socket, así que sin un Zitadel alcanzable el arranque falla por token
y **nunca llega a la red**. La rama `bus_inalcanzable` se ejercita donde sí se puede, con un
`TokenSource` doblado (TS-9 y TS-10). Lo que TS-22 sí afirma a nivel de proceso es la key ilegible y
el fallo de token, ambos con exit ≠ 0 y su diagnóstico por el logger.

### Task 1: Construcción de la identidad desde la key

**Status:** Completed

#### Description

Crea `src/infra/bus/identity.ts` con `buildServiceUser(config)`, que envuelve
`ServiceUser.fromKeyFile()` del SDK y traduce sus fallos a un `KeyLoadError` del conector.

Es el Paso 3 del flujo y el primer eslabón de CA-1. Su valor no está en la línea que llama al SDK
—esa es una— sino en **dos propiedades**: que los cuatro fallos de la key produzcan un error legible
que nombre la ruta y **nunca** el contenido (CA-4), y que el `user-id` quede disponible **derivado de
la key**, cerrando la puerta a que alguien lo tome del entorno más adelante (CA-2).

**Contexto que el implementador necesita y no es obvio:** `ServiceUser` **valida la key en el
constructor** y tiene **cuatro** modos de fallo, no los dos que menciona CA-4 (ver H1 en Architectural
Context). Los cuatro llegan como `JikuError` con la causa real en `cause`. Verificado también que
**ninguno filtra el contenido hoy** — lo que no exime de afirmarlo con un test, porque es exactamente
lo que puede cambiar en un minor del SDK.

#### Acceptance Criteria

1. `buildServiceUser(config: AppConfig): Promise<ServiceUser>` invoca
   `ServiceUser.fromKeyFile(config.keyFile, { issuer: config.issuer, projectId: config.zitadelProjectId })`.
2. **No pasa `scopes`.** El default del SDK ya es `['openid', 'profile']`, y `profile` es **obligatorio**
   para que `core` cree la fila en `users`. Queda un comentario explicando por qué no se toca (H6).
3. Los **cuatro** fallos del SDK se traducen a `KeyLoadError` con el `JikuError` original en `cause`.
4. El `message` de `KeyLoadError` **nombra la ruta** (`config.keyFile`) y **jamás** interpola el
   contenido del archivo, ni el `message` del error del SDK que pudiera contenerlo.
5. El `user-id` se expone tomándolo de la key (`serviceUser.userId`), sin ninguna llamada de red.
6. El módulo **no lee `process.env`** y **no llama a `getLogger()`**: recibe la configuración por
   parámetro.
7. `tsc --noEmit` pasa sin diagnósticos.

### Task 2: Errores de arranque del bus con su diagnóstico

**Status:** Completed

#### Description

Crea `src/infra/bus/errors.ts` con `KeyLoadError`, `BusConnectError` y
`diagnoseConnectFailure(error)`.

Es la pieza que hace cumplir CA-5, y su razón de existir es la de ADR-006: **el log tiene que decir
qué sistema rechazó**, porque los arreglos están en lugares distintos. Un log que diga "no pudo
conectar" obliga a revisar Zitadel, la red y el creds a la vez.

**Contexto que el implementador necesita:** la story trata el fallo de conexión como **un** caso, y son
**tres** (H4): Zitadel no entregó el token, el bus rechazó el token, o el bus no contestó. Y la
clasificación **no puede apoyarse en el texto** del mensaje del SDK (H5): su propio regex no cubre el
`"connection refused"` en minúscula que reporta el transporte, así que un puerto cerrado cae en la rama
genérica mientras un host irresoluble cae en la específica. Clasificar por texto haría que el
diagnóstico dependa de un detalle que ya sabemos inconsistente.

#### Acceptance Criteria

1. `KeyLoadError extends AppError` con `code = 'BUS_KEY_LOAD_ERROR'`.
2. `BusConnectError extends AppError` con `code = 'BUS_CONNECT_ERROR'` y dos campos públicos:
   `diagnosis` y `sdkErrorClass`.
3. `diagnoseConnectFailure(error: unknown)` devuelve exactamente uno de:
   `'rechazo_del_bus_por_subject'` | `'zitadel_no_entrego_token'` | `'bus_inalcanzable'` | `'desconocido'`.
4. La clasificación se hace por **estructura**: `isJikuError()`, la forma de la cadena de `cause`, y
   `cause.code` cuando existe. **Ninguna** rama compara el texto del mensaje del SDK con un literal.
5. `'desconocido'` es un resultado legítimo y **no se mapea a otro**: un fallo que no encaja se loguea
   como desconocido con su clase y su cadena de causas (ADR-006: un `errorCode` desconocido se loguea
   sin mapearse a nada).
6. El mensaje de `BusConnectError` para `'rechazo_del_bus_por_subject'` dice explícitamente que el
   arreglo está en **Zitadel** (rol `internal-app` / Access Token Type = JWT / `JIKU_PROJECT_ID`) y que
   **no** es un problema del payload.
7. Si el error trae un `hint()` **se incluye**; si no lo trae, no se asume que exista (los fallos de
   conexión son `JikuError` a secas y **no** tienen `hint()`).
8. Ningún `message` ni `details` de estos errores puede contener una credencial, una ruta a un secreto,
   ni el contenido de la key.

#### Technical Details

**Architectural Context References:**
- **ADR-006 Implementation Rules:** un fallo MUST loguear la **clase de error del SDK** y, cuando exista,
  el `code` y el `hint()`; MUST NOT reducirse a un mensaje genérico; un código desconocido MUST loguearse
  sin mapearse a otro.
- **ADR-006 → tabla del origen del rechazo:** el criterio de "quién rechazó / dónde está el arreglo".
- **ADR-002 Implementation Rules:** los errores del bus se manejan por las clases del SDK, **no**
  inspeccionando strings de mensaje. Ver la nota del planificador sobre por qué eso se traduce en
  clasificar por estructura.
- **API Context → Clases de error del SDK:** `isJikuError()` y por qué es preferible a `instanceof`;
  los tres mensajes exactos de `connectError()`; `hint()` sólo existe en `JikuFailure`.
- **Hallazgos H4 y H5.**
- **Convención `error-handling`:** los `code` son contrato público; un error tiene un lugar canónico.
- **Reusable Code:** `AppError`, y `ConfigValidationError` (`src/config/errors.ts`) como **patrón a
  imitar**: expone los datos como campo (`variables`) además del `message`, para que los tests afirmen
  sobre estructura y no sobre texto capturado.

**Files to Create/Modify:**
- `src/infra/bus/errors.ts` (crear)

**Implementation Notes:**
- El tipo del diagnóstico se declara como una **unión de literales** exportada
  (`type ConnectDiagnosis = ...`), no como strings sueltos: es lo que hace que un `switch` en el punto
  de log sea exhaustivo para el typechecker.
- **Cómo distinguir Zitadel del bus por estructura, sin leer texto:** los dos son `JikuError`, pero se
