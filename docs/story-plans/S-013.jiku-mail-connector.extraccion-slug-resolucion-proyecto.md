# Story Plan: S-013 (jiku-mail-connector) - Extracción del slug y resolución del proyecto

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-013](../stories/S-013.extraccion-slug-resolucion-proyecto.md)
- **Service:** jiku-mail-connector
- **Summary:** Crear el módulo `ruteo` (hoy un `.gitkeep`) con una función pura `routeMail(mail, config.ruteo) → RouteResult` que aísla el email del `recipient` crudo, extrae y normaliza el slug del subaddress, lo resuelve contra el Mapa de Tickets, y devuelve el proyecto resuelto o uno de los cinco motivos de descarte — sin IMAP, sin bus, verificable con tablas de entrada/salida.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (Node ≥ 22.12), `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`.
- **Runtime:** Node.js, worker sin HTTP ni base de datos (ADR-001).
- **Testing:** Vitest. Sin containers para esta story: es dominio puro, sin NATS ni IMAP.
- **Sin dependencias npm nuevas.** El regex del subaddress es nativo (`RegExp`). Esta story **no toca `package.json`**.

### Service Architecture

Estructura relevante:

```
src/
├── config/
│   ├── schema.ts        # envSchema, incluye TICKET_MAP/TICKET_MAP_FILE, SUBADDRESS_PREFIX
│   └── index.ts         # AppConfig, RuteoConfig (YA EXISTE, S-012)
├── domain/
│   ├── ingesta/
│   │   ├── headers.ts    # extractSenderEmail() a renombrar (CA-3)
│   │   ├── normalize.ts  # produce sin_message_id (motivo literal, hoy sin enum)
│   │   └── types.ts      # IncomingMail
│   └── ruteo/
│       └── .gitkeep      # ESTA STORY LO REEMPLAZA POR CÓDIGO REAL
└── shared/
    ├── errors/
    ├── logger.ts
    └── log-redaction.ts  # REDACT_PATHS incluye 'key' y '*.key' (riesgo de colisión, CA-16)
```

**Patrón arquitectónico:** dominio puro por módulo (`ingesta`, `ruteo`, `publicacion`), compuesto únicamente por el tick (todavía no en esta story — lo hace S-014). `ruteo` no importa nada de `ingesta` ni de `publicacion`: es una función de `(IncomingMail parcial, config.ruteo) → RouteResult`.

**Manejo de errores:** el módulo `ruteo` **no lanza nunca**. Todos los caminos negativos son valores de retorno (`{ ok: false, motivo, slug? }`), no excepciones. Esto es una excepción deliberada a la convención general `error-handling` (que modela errores esperados con clases lanzadas): aquí no hay nada "excepcional" que lanzar, un `recipient` malformado es un resultado de negocio válido, no un error.

**Logging:** el ruteo **no loguea nada**. Es puro y determinístico; el llamador (el tick, en S-014) decide qué loguear a partir del `RouteResult` que recibe. Esto es consistente con `normalize()`, que sí loguea porque produce un descarte por sí misma (`sin_message_id`) y su llamador (el tick) no existía todavía cuando se escribió esa story.

**Testing:** unit tests puros, tablas de entrada/salida, sin containers (ver convención `testing` custom más abajo).

### Relevant ADRs

**ADR-004: Mapa de Tickets, KV local** (implícito — S-012 ya lo materializó; esta story es su **consumidor**, no su implementador)

- El `ticketMap` llega a `routeMail()` ya normalizado a minúsculas y validado — `ReadonlyMap<string, number>`. El lookup en caliente es un `Map.get()` sin transformar el mapa (la normalización ya ocurrió una vez, al cargar, en S-012).
- Los `projectId` del mapa no se validan contra Jiku: el conector publica el id y `core` valida por su cuenta (no aplica directamente a esta story, que no publica nada, pero explica por qué `routeMail()` no verifica el `projectId` de ninguna otra forma que `map.get()`).

**ADR-006: Observabilidad por logs estructurados** — aplica indirectamente: define el **catálogo cerrado** de los cinco motivos de descarte, que es lo que el `MotivoDescarte` de esta story debe reproducir literalmente.

- Implementation Rules relevantes (copiadas verbatim):
  - "Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`, `sin_message_id`, `no_parseable`)" — esta story **no loguea** (esa parte es de S-014), pero el enum que define debe usar exactamente estos cinco literales, en minúscula, sin variantes.
  - "Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para cargarlo)" — de ahí que `RouteResult` de descarte lleve `slug?` presente **solo** cuando `motivo === 'slug_no_mapeado'` (CA-13).
  - MUST NOT loguearse nunca: credenciales, tráfico IMAP crudo, el cuerpo del mail, el contenido de un adjunto. No aplica directamente al ruteo (que no loguea nada), pero **es la razón de fondo de CA-16**: el `RouteResult` nunca debe transportar el `recipient` completo ni nada que se le parezca a lo que el log no debe mostrar.

### Database Context

Ninguno. Sin base de datos (ADR-001). El "mapa" es un `ReadonlyMap<string, number>` en memoria, cargado por `loadAppConfig()` (S-012), no persistido en ningún lado.

### Flow Context

No hay un flow document que esta story modifique todavía — el flujo `ruteo-y-alta-del-requisito` lo crea **S-016**, cuando el comportamiento completo (ruteo + publicación) ya está cableado al tick. Esta story agrega una función pura que **todavía no está conectada a nada**.

El **árbol de decisión** (del Diseño Técnico de la story, autoritativo para esta implementación):

```
┌─ referenceIds.length > 0 ────────────→ { ok:false, motivo:'es_respuesta' }        (RF-20)
│     ¡ANTES de extraer el slug! Una respuesta no gasta el regex ni el lookup
│
├─ recipient vacío / no matchea / slug vacío ─→ { ok:false, motivo:'sin_slug' }     (RF-21)
│     aísla el email → aplica ^<prefijo>\+([^@]+)@ (i) → minúsculas
│
├─ !map.has(slug) ────────────────────→ { ok:false, motivo:'slug_no_mapeado', slug } (RF-22)
│
└─ resuelto ──────────────────────────→ { ok:true, projectId, slug }
```

**El camino feliz con casing mixto** (Escenario B de la story, autoritativo):

```
recipient crudo:  'Soporte Tickets <TICKETS+Alfa@grava.io>'
   │
   ├─ extractSenderEmail() (renombrada) → 'TICKETS+Alfa@grava.io'   (preserva casing)
   ├─ /^tickets\+([^@]+)@/i             → captura 'Alfa'
   ├─ .toLowerCase()                    → 'alfa'
   └─ map.get('alfa')                   → 42        (el mapa ya vino normalizado de S-012)
   →  { ok: true, projectId: 42, slug: 'alfa' }
```

### Integration Points

Ninguno externo. No hay bus, no hay IMAP, no hay servicios externos. La única "integración" es interna: `routeMail()` consume el `RuteoConfig` que compone `loadAppConfig()` (S-012) y consumirá, en el futuro (S-015), la resolución de `senderEmail`-equivalente ya construida en `ingesta/headers.ts`.

### Code Conventions

**Naming (convención `_base`, Node):**

| Elemento | Convención | Ejemplo |
|---|---|---|
| Archivos | `kebab-case` | `route-mail.ts`, `motivo-descarte.ts` |
| Carpetas | `kebab-case` | `domain/ruteo/` |
| Funciones, variables | `camelCase` | `routeMail`, `extractAddress` |
| Types/interfaces | `PascalCase`, sin prefijo `I` | `RouteResult`, `RuteoConfig` |
| Enums | `PascalCase` el nombre; pero ver nota abajo sobre `MotivoDescarte` | — |

**Nota sobre el enum de motivos:** ADR-006 y la story fijan los **literales exactos** en minúscula (`no_parseable`, `sin_message_id`, `es_respuesta`, `sin_slug`, `slug_no_mapeado`) porque son lo que se loguea tal cual. Un TypeScript `enum` numérico o con valores `PascalCase` rompería esa igualdad literal. Se implementa como **union de string literals** (`type MotivoDescarte = 'no_parseable' | 'sin_message_id' | 'es_respuesta' | 'sin_slug' | 'slug_no_mapeado'`), no como `enum` de TypeScript — consistente con el resto del código base, que ya usa uniones literales para catálogos cerrados con estos mismos valores como strings (ver `ConnectDiagnosis`, `PublishDiagnosis` en `src/infra/bus/errors.ts` / `src/domain/publicacion/publish-errors.ts`, ambos uniones literales, nunca `enum`).

**Imports (convención `module-imports`, custom de este servicio):**

- Todo import intra-proyecto usa el subpath `#` de Node, nunca `../../../`. `#domain/*` ya cubre el nuevo módulo `ruteo` — **no hace falta ninguna entrada nueva** en `package.json#imports` ni en `tsconfig.json#compilerOptions.paths` (CA-2).
- Todo specifier lleva extensión `.js` explícita, incluso desde `.ts`: `import { routeMail } from '#domain/ruteo/route-mail.js';`.
- Orden: librerías externas → imports absolutos del proyecto (`#...`) → imports relativos del mismo módulo (`./...`), separados por línea en blanco.

**Errores como valores vs. excepciones (convención `_base`):**

- Esta story es el caso explícito de "no hay error que lanzar": todo camino negativo es un valor de retorno tipado, nunca una excepción. `routeMail()` nunca lanza — ni siquiera ante un `recipient` malformado, que es un resultado `sin_slug`, no un error.

- **`IncomingMail`** (`src/domain/ingesta/types.ts`, ya existe desde S-008) — la forma exacta del primer parámetro de `routeMail()`. Solo importan tres campos para esta story: `referenceIds: string[]`, `recipient: string`. `messageId` no lo usa `routeMail()` (lo usa el llamador, S-014, para el log), pero como la story pide una función sobre "IncomingMail parcial", la firma puede tomar sólo un subconjunto tipado (`Pick<IncomingMail, 'referenceIds' | 'recipient'>`) para no acoplar el ruteo a campos que no usa (`senderEmail`, `subject`, `body`, `attachments`).

- **`REDACT_PATHS`** (`src/shared/log-redaction.ts`, ya existe desde S-003/S-004) — incluye `'key'` y `'*.key'` con un riesgo de colisión ya documentado en el propio archivo: *"`key` es un nombre genérico y puede colisionar con un campo legítimo llamado `key` (la clave de un mapa, un identificador)... se cubre [de todas formas]"*. **Consecuencia directa para esta story (CA-16):** el campo del slug en `RouteResult` se llama `slug`, **nunca `key`**, en ningún tipo ni en ningún test.

**`_base` (Node, siempre activa)** — TypeScript estricto, `noUncheckedIndexedAccess`, imports absolutos, `Result<T,E>` no se usa salvo casos puntuales que agreguen claridad (`RouteResult` es exactamente ese caso puntual), comentarios solo para el "por qué".

**`module-imports` (custom del servicio)** — ver "Code Conventions" arriba. Regla verificable: `tsc --noEmit` sin `TS2307`, y el `dist/` compilado arranca limpio.

**`testing` (custom del servicio — Vitest + NATS de Testcontainers, sin base de datos)**

- **Para esta story: unit tests puros, sin containers.** `routeMail()` no toca IMAP ni bus, así que ni `globalSetup` ni NATS aplican a sus tests. Los tests de esta story corren tan rápido como cualquier función pura.
- Reglas aplicables:
  - "Unit tests are for pure functions only." — `routeMail()` lo es en su totalidad.
  - "Test files co-located... under `test/`, suffixed `.test.ts`." — sigue el patrón existente: `test/ruteo/route-mail.test.ts` (paralelo a `test/ingesta/headers.test.ts`).
  - "`describe` names the unit under test; `it` names the scenario." — en inglés los nombres de `describe`/`it`, igual que `test/ingesta/headers.test.ts`.
  - No se requiere fixture `.eml`: a diferencia de `normalize()` (que parsea bytes RFC 822 reales), `routeMail()` opera sobre `IncomingMail` ya normalizado — un objeto TypeScript literal es la entrada correcta y suficiente (CA-17: "tablas de entrada/salida... sin IMAP, sin bus").

## Tasks

### Task 1: Renombrar `extractSenderEmail` a un nombre neutral al insumo

**Status:** Completed

#### Description

`extractSenderEmail()` en `src/domain/ingesta/headers.ts` aísla una dirección de un header con forma `Nombre <mail@dominio>`. Hoy solo se usa sobre `From` (de ahí el nombre), pero CA-3 exige reutilizarla exactamente igual sobre `recipient` en el módulo `ruteo`. Mantener el nombre `extractSenderEmail` haría que su uso en `route-mail.ts` mienta sobre su insumo: no está extrayendo un "sender" ahí, está aislando una dirección de cualquier header con esa forma. Se renombra a un nombre neutral (`extractAddress`) que describe la operación, no el header sobre el que históricamente se usó.

### Task 2: Definir el enum único `MotivoDescarte` y el tipo `RouteResult`

**Status:** Completed

#### Description

CA-7 exige un único enum de los cinco motivos de descarte, definido en un solo lugar. Dos de los cinco (`no_parseable`, `sin_message_id`) ya los produce `ingesta/normalize.ts` como literales de string sueltos (sin tipo compartido); los otros tres (`es_respuesta`, `sin_slug`, `slug_no_mapeado`) los agrega esta story. Como `ingesta/normalize.ts` no puede importar de `ruteo` sin invertir la dirección de dependencia que CA-1 protege, el enum **no puede vivir en `src/domain/ruteo/`** si `ingesta` también necesita importarlo — y si en un futuro cercano (S-014) el tick necesita comparar el motivo que devolvió `normalize()` contra el mismo tipo que devuelve `routeMail()`, ambos productores deben compartir un tipo, no dos.

**Decisión de esta story (el REQ deja la opción abierta explícitamente): el enum vive en `src/shared/motivo-descarte.ts`.** Es la opción que no requiere re-export desde ningún lado y no crea una dependencia de `ingesta` hacia `ruteo` ni viceversa — ambos importan de `shared`, que no importa de ninguno de los dos.

Esta tarea **no modifica `ingesta/normalize.ts`** para que use el nuevo tipo (ese literal `motivo: 'sin_message_id'` sigue funcionando igual porque es un string literal compatible con el tipo unión) — cablear todos los productores al mismo tipo explícitamente es trabajo de integración que le corresponde a S-014, que es la que compone. Esta tarea solo **crea el lugar único de definición** y lo usa en `RouteResult`.

#### Acceptance Criteria

1. Existe `src/shared/motivo-descarte.ts` que exporta un tipo `MotivoDescarte` como unión de string literals: `'no_parseable' | 'sin_message_id' | 'es_respuesta' | 'sin_slug' | 'slug_no_mapeado'`.
2. No es un `enum` de TypeScript — es una unión de literales, para que los valores en runtime sean exactamente los strings en minúscula que ADR-006 exige loguear, sin capa de indirección.
3. El módulo también exporta el tipo `RouteResult`:
   ```ts
   export type RouteResult =
     | { readonly ok: true; readonly projectId: number; readonly slug: string }
     | { readonly ok: false; readonly motivo: MotivoDescarte; readonly slug?: string };
   ```
4. El campo `slug` en la rama `ok: false` es **opcional** (`slug?`), no `slug: string | undefined`: la diferencia importa porque `slug?` permite omitir la clave por completo (verificable con `'slug' in result`), mientras que `string | undefined` permitiría `{ motivo: 'sin_slug', slug: undefined }`, que técnicamente tiene la clave presente. CA-13 exige que el dato **no exista** en el resultado para `es_respuesta` y `sin_slug`, no que exista con valor `undefined`.
5. Ningún campo del tipo se llama `key` en ningún nivel (CA-16).
6. El archivo no importa nada de `#domain/ingesta` ni de `#domain/ruteo` — es una hoja del árbol de dependencias.

**Architectural Context References:**

**Implementation Notes:**

### Task 3: Implementar `routeMail()` en `src/domain/ruteo/route-mail.ts`

**Status:** Completed

#### Description

El corazón de la story: reemplazar `src/domain/ruteo/.gitkeep` por el módulo real. Una única función pura `routeMail()` que implementa el árbol de decisión completo (Flow Context arriba): descarta `es_respuesta` antes de tocar el slug, aísla y normaliza el slug del `recipient`, lo busca en el mapa, y devuelve el `RouteResult` correspondiente. Nunca lanza. Nunca loguea.

#### Acceptance Criteria

1. `src/domain/ruteo/.gitkeep` se elimina; en su lugar existe `src/domain/ruteo/route-mail.ts`.
2. Exporta `routeMail(mail: Pick<IncomingMail, 'referenceIds' | 'recipient'>, config: Pick<RuteoConfig, 'ticketMap' | 'subaddressPrefix'>): RouteResult`.
3. El archivo **no importa nada** de `#domain/ingesta/*` salvo el tipo `IncomingMail` (import de solo-tipo, `import type`) y la función `extractAddress` renombrada en Task 1 — ambos son los únicos acoplamientos permitidos por la story (CA-3 exige reutilizar la función; el tipo es la forma del primer parámetro). No importa nada de `#domain/publicacion/*`.
4. El orden de evaluación es exactamente: (1) `referenceIds.length > 0` → `es_respuesta`; (2) aislar+extraer+normalizar el slug, si no matchea o el slug queda vacío → `sin_slug`; (3) `!ticketMap.has(slug)` → `slug_no_mapeado` con el `slug` incluido; (4) `{ ok: true, projectId: ticketMap.get(slug)!, slug }`.
5. El patrón del subaddress se construye dinámicamente con el `subaddressPrefix` de la config (no hardcodeado a `'tickets'`), con el flag `i` (case-insensitive): `new RegExp('^' + escapeRegExp(subaddressPrefix) + '\\+([^@]+)@', 'i')` — o equivalente. El prefijo se escapa antes de interpolarlo en el regex (un prefijo con caracteres especiales de regex, aunque no está en alcance de configuración típica, no debe romper la construcción del patrón).
6. El slug capturado se normaliza con `.toLowerCase()` antes de compararlo contra el mapa (el mapa ya viene normalizado desde S-012; la normalización del lado del slug capturado es la que falta y la que aporta esta story).
7. La función nunca lanza: cualquier `recipient` que no matchee el patrón (vacío, sin `+`, sin `@`, con slug vacío) resuelve a `sin_slug`, nunca a una excepción.
8. Un comentario en el código documenta el falso positivo aceptado del reenvío (CA-10): un mail reenviado con `References` poblado se descarta como `es_respuesta` aunque traiga un pedido legítimo nuevo, y esto es una decisión de producto aceptada (decisión 9 del PRD, G-04), no un bug.
