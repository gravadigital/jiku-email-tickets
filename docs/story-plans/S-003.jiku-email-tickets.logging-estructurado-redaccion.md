# Story Plan: S-003 (jiku-email-tickets) - Logging estructurado con redacción

## Status

**Status:** Completed

**Progress:** 5/5 tareas completadas

## Story Reference

- **Story:** [S-003](../stories/S-003.logging-estructurado-redaccion.md)
- **Service:** jiku-email-tickets
- **Summary:** Construir el logger único del conector: Pino a stdout, JSON en producción y
  `pino-pretty` en desarrollo, con el nivel tomado de la configuración validada en S-002 y `redact`
  que censura credenciales, tokens, el contenido de la key/creds y —anticipadamente— el cuerpo del
  mail y el contenido de los adjuntos. Es la story que hace observables a S-004 y S-005: cada fallo
  de conexión y cada una de las siete clases de error del SDK salen por acá.

#### `logging` (Pino) — la convención central de esta story

Copiada del catálogo (`.claude/conventions/node/logging.md`), con las desviaciones del servicio
señaladas más abajo.

**Configuración de referencia del catálogo:**

```ts
// src/shared/logger.ts
import pino from 'pino';
import { env } from '@/config/env';

export const logger = pino({
  level: env.LOG_LEVEL ?? 'info',
  base: {
    service: env.SERVICE_NAME,
    env: env.NODE_ENV,
  },
  timestamp: pino.stdTimeFunctions.isoTime,
  formatters: {
    level: (label) => ({ level: label }),
  },
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      '*.password',
      '*.token',
      '*.refreshToken',
      '*.apiKey',
    ],
    censor: '[REDACTED]',
  },
  transport: env.NODE_ENV === 'development'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
});
```

**Estructura obligatoria de cada llamada:**

```ts
logger.info({ context }, 'message');
//          ^^^^^^^^^^   ^^^^^^^^^
//          objeto plano  string fijo
```

- **Primer argumento:** objeto con el contexto. Los campos no varían entre llamadas del mismo log.
- **Segundo argumento:** mensaje corto y **estático**. Sin interpolación de variables.

Mal:
```ts
logger.info(`User ${userId} created in ${ms}ms`);  // mensaje variable
```

Bien:
```ts
logger.info({ userId, durationMs: ms }, 'User created');
```

**Niveles:**

| Nivel | Cuándo |
|---|---|
| `trace` | Muy fino, apagado por defecto |
| `debug` | Información de depuración, apagado en prod |
| `info` | Eventos normales del sistema |
| `warn` | Algo inesperado pero recuperable (retry, fallback) |
| `error` | Un error que rompió una operación |
| `fatal` | El servicio no puede continuar |

Default en prod: `info`.

**Errores:**

```ts
try {
  await processOrder(orderId);
} catch (err) {
  logger.error({ err, orderId }, 'Order processing failed');
  throw err;
}
```

- Pino serializa `err` automáticamente con stack incluido (cuando es un `Error`).
- **Errores esperados** (`AppError` de `error-handling`): loguear con `warn` o `info`, sin stack.
- **Errores inesperados**: loguear con `error`, con stack completo.

**Reglas del catálogo:**

- Un logger por servicio. No múltiples instancias con configuraciones distintas.
- Nunca loguear: contraseñas, tokens, API keys, cookies de sesión, cuerpos con PII. Confiar en
  `redact` **y además no incluirlos explícitamente**.
- No loguear contenidos de respuesta grandes.
- Mensajes cortos, descriptivos, estáticos. Sin emojis. Sin información dinámica en el string.
- En tests: silenciar los logs o usar un transporte de test. No contaminar la salida de CI.

**Desviaciones de este servicio respecto del catálogo — leer con atención:**

| Punto del catálogo | Qué hace este servicio | Por qué |
|---|---|---|
| `import { env } from '@/config/env'` | `createLogger(config)` **recibe** la configuración por parámetro | El prefijo `@/` no existe acá (`module-imports`), y sobre todo: CA-5 exige que el logger no lea el entorno por su cuenta. La configuración se resuelve en `src/config/` y se pasa |
| `env.SERVICE_NAME`, `env.NODE_ENV` | `SERVICE_NAME` viene de `#shared/service-info.js`; `NODE_ENV` **no está en `envSchema`** | S-002 no declaró `NODE_ENV` como variable del schema. Ver "El hueco de `NODE_ENV`" más abajo — **es la única decisión abierta de esta story** |
| Lista de `redact.paths` orientada a HTTP (`req.headers.*`) | Lista propia orientada a credenciales del bus, key JSON y (anticipadas) mail/adjuntos | El servicio no expone HTTP (ADR-001): `req.headers.authorization` no puede ocurrir nunca. Las rutas que sí pueden ocurrir son otras |
| `export const logger = pino({...})` como constante directa | Factory `createLogger()` + singleton derivado | CA-8 exige afirmar sobre la **línea serializada**; con una constante construida en el import, testear eso obliga a interceptar `process.stdout`, que con `fileParallelism: false` contamina otros archivos |
| Niveles: `trace..fatal` | El schema de S-002 agrega **`silent`** | `LOG_LEVELS` en `src/config/schema.ts` incluye `silent`, que Pino soporta nativamente. El logger tiene que respetarlo |

#### `env-config` (`@t3-oss/env-core`) — lo que esta story debe preservar

- **Nunca llamar `process.env.VAR` fuera de `src/config/env.ts`.** El resto del código importa la
  configuración ya resuelta.
- Todas las variables se declaran y validan en el schema. Sin variables no declaradas.
- El servicio falla al arrancar (no en el primer uso) si falta una variable requerida.
- `LOG_LEVEL` se declara acá y lo **consume** el logger — esa es exactamente la integración que
  documenta la convención (`logging`: "`LOG_LEVEL` declared here, consumed by the logger").

#### `module-imports` (custom del servicio) — la más fácil de romper

- Los imports intra-proyecto **DEBEN** usar un prefijo de subpath declarado en `package.json#imports`.
  Nunca rutas relativas que suban directorios (`../../`).
- El especificador **DEBE** llevar extensión `.js` explícita, incluso desde un `.ts`. ESM no la
  infiere.
- Todo prefijo en `package.json#imports` **DEBE** tener contraparte en
  `tsconfig.json#compilerOptions.paths`, y viceversa.
- Los dos lados **DEBEN** apuntar a árboles distintos: `paths` a `./src/*`, `imports` a `./dist/*`.
- **Esta story no agrega ningún prefijo nuevo:** `src/shared/logger.ts` y `src/shared/log-redaction.ts`
  caen bajo `#shared/*`, que ya existe en los dos archivos. No hay que tocar ni `package.json#imports`
  ni `tsconfig.paths` ni el `resolve.alias` de `vitest.config.ts`.

Mapeo vigente:

```jsonc
// package.json — runtime, apunta a dist/
"imports": {
  "#config/*": "./dist/config/*",
  "#domain/*": "./dist/domain/*",
  "#infra/*":  "./dist/infra/*",
  "#shared/*": "./dist/shared/*"
}
```

```jsonc
// tsconfig.json — compilación, apunta a src/
"paths": {
  "#config/*": ["./src/config/*"],
  "#domain/*": ["./src/domain/*"],
  "#infra/*":  ["./src/infra/*"],
  "#shared/*": ["./src/shared/*"]
}
```

Uso: `import { SERVICE_NAME } from '#shared/service-info.js';`

**La verificación que importa es la de runtime**, no `tsc --noEmit`: un mapeo roto pasa el typecheck y
muere al arrancar. `test/build-runtime.test.ts` (S-001) ya ejecuta el `dist/` compilado.

#### `testing` (custom del servicio)

- **Unit tests para funciones puras.** Todo lo de esta story es puro: no toca el bus, no toca IMAP.
  **Ningún test de S-003 usa el contenedor NATS.**
- Tests co-locados con el código o bajo `test/`, sufijo `.test.ts`.
- `describe` nombra la unidad bajo prueba; `it` nombra el escenario. Ambos en inglés llano.
- Los tests **no dependen de las env vars del host**: pasan objetos literales. Es lo que hizo S-002 en
  `test/config/env.test.ts` y esta story lo continúa.
- **Mantener la salida de tests silenciosa** (`LOG_LEVEL=silent`), **pero nunca silenciar los errores
  globalmente** — un error tragado en un servicio cuya única salida son los logs es el peor artefacto
  de test posible.
- Integración con `logging`, textual de la convención: *"assert the **shape** of diagnostic logs for
  discards and failures — in this service the log is the only trace a lost ticket leaves, so it is
  behaviour, not decoration. Silence log output in tests, but assert what would have been logged."*
  **Esto es exactamente lo que esta story instrumenta:** el destino inyectable es lo que permite
  afirmar sobre la línea sin escribirla a la salida de CI.
- Resetear mocks entre tests con `vi.clearAllMocks()` / `vi.unstubAllGlobals()`.

#### `error-handling`

- Jerarquía con `AppError` abstracta (`code`, `httpStatus`, `details` opcional).
- Nunca `throw new Error(...)` desde código de dominio.
- **No incluir información sensible en `message` ni `details`.**
- El "borde" de este servicio es el log, no una respuesta HTTP (nota registrada en REQ-001): la
  traducción al borde que la convención describe se materializa acá como la línea de log.

#### `dockerfile`

Relevante en un solo punto, pero es un punto que rompe producción si se ignora:

- `pino-pretty` va como **`devDependency`**. La stage de producción instala con `--omit=dev`, así que
  el paquete **no existe** en la imagen final. Por eso el logger sólo puede referenciarlo cuando
  `NODE_ENV === 'development'`, y por eso T2 incluye la degradación a JSON: si algún día el transporte
  no resuelve, el worker tiene que seguir logueando igual.

### Relevant ADRs

#### ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito

**Decisión:** Logs estructurados a stdout, JSON en producción, nunca a archivo. Y el log distingue
explícitamente qué sistema rechazó cada comando.

**Contexto que justifica el peso de esta story:** en Jiku, cuando una escritura falla, hay un usuario
mirando una pantalla que recibe un error. Acá no hay nadie. **Un ticket perdido no tiene síntoma.**
Eso convierte a la observabilidad en la preocupación transversal más importante del producto: el log
es el único lugar donde un mail perdido deja rastro.

**Antecedente concreto que condiciona la decisión:** Jiku tiene los transports de archivo de sus dos
backends con `filename: undefined` en producción, porque las variables no están en el compose. Sus
logs a archivo no existen y nadie se dio cuenta. **El conector no puede repetir ese error.** Esa es la
razón real detrás de "nunca a un archivo": no es purismo de contenedores, es un modo de falla
observado.

**Transporte:**

| Pieza | Definición |
|---|---|
| Destino | **stdout**, siempre. Nunca archivo |
| Formato | Estructurado; **JSON en producción** |
| Nivel default | `info` |
| A quién le reporta un fallo | **A nadie.** No hay usuario esperando ni request que responder |
| Métricas por tick | `ingestados`, `parseados`, `creados`, `descartados`, `fallidos` (FG-2, fuera de alcance acá) |
| Healthcheck | **Fuera de alcance v1** |

**Qué nunca se loguea:** credenciales, tráfico IMAP crudo, **el cuerpo del mail** y el contenido de un
adjunto. El cuerpo es contenido de negocio y puede traer datos del cliente: el log es el único rastro
de un ticket perdido, **pero sigue siendo un log, no un depósito de datos del cliente**.

**Implementation Rules (copiadas completas y verbatim del ADR):**

- Los logs MUST ir a **stdout**. MUST NOT configurarse ningún transport de archivo, en ningún entorno
- El formato MUST ser **JSON en producción**
- El nivel por defecto MUST ser `info`, configurable por variable de entorno
- MUST NOT loguearse nunca: credenciales (IMAP, key JSON, token, creds de NATS), tráfico IMAP crudo, el
  cuerpo del mail (`body`), el contenido de un adjunto
- El cliente IMAP MUST configurarse con `logger: false`
- **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado.
  Ningún mail termina sin rastro
- Un alta exitosa MUST loguear `messageId`, `projectId` y el `id` del requisito creado, juntos
- Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`,
  `sin_message_id`, `no_parseable`)
- Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para
  cargarlo)
- Un fallo de comando MUST loguear la **clase de error del SDK** y, cuando exista, el `code` y el
  `hint()`. MUST NOT reducirse a un mensaje genérico de "falló el comando"
- Un `errorCode` desconocido MUST loguearse con su `code` y su `hint()` sin mapearse a otro error
- Cada tick MUST emitir una línea con los cinco contadores: `ingestados`, `parseados`, `creados`,
  `descartados`, `fallidos`
- Un tick que difiere mails por el cap MUST loguear un `warn` con **cuántos** quedaron diferidos
- Un fallo del refresh del token MUST loguearse como `error` (vía `onTokenError`) sin terminar el
  proceso
- El timeout del comando MUST quedar en **15000 ms** (el default del SDK). **MUST NOT bajarse**
- Un tick salteado por solapamiento MUST loguear un `warn`
- MUST NOT implementarse endpoint de healthcheck ni exportador de métricas en v1

**Cuáles de esas reglas caen dentro de S-003 y cuáles no** — la distinción importa porque la mayoría
de la lista describe *puntos de log* que las stories siguientes van a escribir, no la *capacidad* que
esta story construye:

| Regla | ¿S-003? | Dónde cae |
|---|---|---|
| stdout siempre, nunca transport de archivo | **Sí** | T2 (CA-1) |
| JSON en producción | **Sí** | T2 (CA-2) |
| Nivel default `info`, configurable | **Sí** | T2, ya declarado en el schema de S-002 (CA-5) |
| Nunca credenciales / key / creds / token | **Sí** | T1 + T2: es la lista de `redact` (CA-3, CA-4) |
| Nunca cuerpo del mail ni contenido de adjunto | **Sí, anticipadamente** | T1: las rutas se declaran ahora aunque los datos no existan (CA-7) |
| `logger: false` en el cliente IMAP | No | FG-2. No hay cliente IMAP todavía |
| Una línea por mail con `messageId` y resultado | No | FG-2 |
| Alta exitosa loguea `messageId` + `projectId` + `id` | No | S-005 |
| Motivos de descarte, slug buscado | No | FG-3 |
| Clase de error del SDK + `code` + `hint()` | No | S-005 — **pero sale por el logger que construye esta story** |
| `errorCode` desconocido sin mapear | No | S-005 |
| Cinco contadores por tick, cap diferido, tick solapado | No | FG-2 |
| Fallo del refresh vía `onTokenError` sin morir | No | S-004 — **pero sale por este logger** |
| Timeout en 15000 ms | No | Ya resuelto en S-002 (`MIN_TIMEOUT_MS`) |
| Sin healthcheck ni métricas | **Sí, por omisión** | No agregar nada de eso |

**Riesgo del ADR que esta story mitiga sólo a medias:** *"alguien agrega un log de debug que imprime
el mail completo y los datos del cliente terminan en los logs"*. La mitigación registrada es la regla
en Implementation Rules más code review. **No hay guard técnico.** `redact` cubre el caso en que el
dato viaja en el **objeto de contexto**; no cubre el caso en que alguien lo interpola **dentro del
string del mensaje**. CA-6 y TS-17 atacan justamente ese segundo caso, mecanizándolo hasta donde se
puede.

#### ADR-005: Identidad como machine user de Zitadel

Aplica a esta story por un solo punto, pero es el que define la mitad de la lista de `redact`:

- El **access token vive sólo en memoria**: nunca a disco, nunca al log (NFR-S02). El SDK lo expone
  como **getter, no como string**, lo que reduce la superficie de que termine en un objeto de
  contexto de log.
- La **key JSON del machine user** es la credencial durable: el campo `key` del archivo **es la clave
  privada RSA**. Un volcado accidental de ese objeto es la filtración más grave posible de este
  servicio.
- Un fallo al cargar la key debe decir "la key no se pudo cargar" **sin volcar su contenido**.

#### ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus

Aplica indirectamente: las siete clases de error del SDK que S-005 va a mapear se emiten por este
logger, y sus objetos de error pueden arrastrar contexto sensible. Por eso T4 cubre el caso
`{ err: Error }` (TS-19): `redact` tiene que seguir operando sobre los otros campos del contexto
aunque uno de ellos sea un `Error` serializado por Pino.

#### ADR-001: Worker único sin persistencia

- **Nada de base de datos**, nada de volumen de escritura. Refuerza "nunca a un archivo": no hay
  volumen montado donde escribir aunque se quisiera.
- **El servicio no expone HTTP.** Por eso las rutas `req.headers.authorization` / `req.headers.cookie`
  del catálogo **no se copian**: son ruido en una lista que se lee para auditar qué está protegido.

### API Context

**No aplica.** El conector no expone HTTP: ni endpoint, ni puerto, ni especificación OpenAPI.
`docs/apis/` está vacío por decisión declarada (ADR-001, overview del servicio). Un `/health` de
relleno sería un contrato falso.

**Consecuencia concreta para esta story:** el "borde" observable de este servicio es el log. La
sección que en otro servicio sería "formato de respuesta de error" acá es la forma de la línea de log,
y está descrita en Flow Context y en las Implementation Rules de ADR-006.

### Database Context

**No aplica.** El conector no alcanza PostgreSQL (ADR-001). No hay documento en `docs/db-schemas/`, ni
migraciones, ni cliente de base de datos.

**Consecuencia concreta para esta story:** el logging va a **stdout, nunca a un archivo ni a una
tabla** (NFR-O01). Si un test parece necesitar persistencia, el código de producción está guardando
algo que no debe.

### Integration Points

#### `AppConfig` de `src/config/index.ts` — el contrato de entrada del logger

Es la única dependencia interna del logger. Copiado verbatim del código vigente:

```ts
export interface AppConfig {
  servers: string;
  instance: string;
  credsFile: string;
  keyFile: string;
  zitadelProjectId: string;
  issuer: string;
  timeoutMs: number;
  verifyProjectId: number;
  logLevel: (typeof LOG_LEVELS)[number];
}
```

Con:

```ts
export const LOG_LEVELS = ['trace', 'debug', 'info', 'warn', 'error', 'fatal', 'silent'] as const;
```

**`silent` está en la lista y el catálogo `logging` no lo menciona.** Pino lo soporta nativamente
(`level: 'silent'` suprime todo). El logger debe pasarlo tal cual, sin traducirlo ni filtrarlo.

**Cinco de los nueve campos de `AppConfig` son sensibles o son topología** y **no deben ir a la línea
de arranque**: `credsFile`, `keyFile` (rutas a secretos — una ruta a un archivo de credenciales es
información sobre dónde está el secreto), `zitadelProjectId` y `servers` (topología del despliegue).
S-002 ya tomó esta decisión en `src/index.ts` y la dejó comentada; T3 la preserva.

#### El hueco de `NODE_ENV` — **la única decisión abierta de esta story**

El catálogo `logging` lee `env.NODE_ENV` para dos cosas: el campo `env` del `base`, y el
`transport: NODE_ENV === 'development' ? pino-pretty : undefined`.

**Pero `NODE_ENV` NO está declarado en `envSchema` de S-002.** Verificado: el schema declara nueve
variables (`JIKU_CREDS`, `JIKU_KEY_FILE`, `JIKU_PROJECT_ID`, `JIKU_VERIFY_PROJECT_ID`,
`JIKU_INSTANCE`, `JIKU_SERVERS`, `JIKU_ISSUER`, `JIKU_TIMEOUT`, `LOG_LEVEL`) y ninguna es `NODE_ENV`.
El `.env.example` tampoco la lista.

Esto es un choque real entre dos criterios de aceptación:

- **CA-2 exige** discriminar el formato por `NODE_ENV`.
- **CA-5 y `env-config` prohíben** que el logger lea `process.env` por su cuenta.

**Resolución adoptada (T2 la implementa así):** agregar `NODE_ENV` al `envSchema` de S-002 como
`z.enum(['development', 'test', 'production']).default('production')` y propagarla a `AppConfig` como
`nodeEnv`. El logger la recibe por parámetro, como todo lo demás.

**Por qué se resuelve así y no leyendo `process.env.NODE_ENV` en el logger:**

1. Leerlo en el logger rompe la propiedad verificable de S-002 CA-1 (`grep process.env src/` devuelve
   **un solo archivo**), que TS-14 vuelve a afirmar en esta story. Esa propiedad es más valiosa que la
   comodidad de leer una variable.
2. El default `production` (no `development`) es deliberado: el modo caro y bonito debe ser el que se
   pide explícitamente, no el que se obtiene por olvido. Un despliegue que olvidó declarar `NODE_ENV`
   emite JSON, que es lo correcto; el error inverso —un contenedor de producción emitiendo salida
   coloreada de `pino-pretty`, con el paquete ausente de la imagen— es peor.
3. Es un cambio aditivo con default: **no rompe ningún test de S-002** ni ningún despliegue existente.

**Alcance del cambio en T2:** una línea en `envSchema`, una entrada en `EXPECTATIONS` de
`src/config/errors.ts`, un campo en `AppConfig`, una línea en `loadAppConfig()` y una línea en
`.env.example`. Los tests de S-002 que afirman sobre `ALL_REQUIRED` no se ven afectados porque
`NODE_ENV` tiene default y por lo tanto nunca aparece en la lista de faltantes.

#### La key del machine user — forma exacta, verificada en el SDK instalado

Esto es lo que hace que la lista de `redact` sea precisa en vez de aproximada. De
`node_modules/@gravadigital/jiku/dist/node/service-user.d.ts`:

```ts
export interface ServiceAccountKey {
    type?: string;
    keyId: string;
    key: string;        // <-- LA CLAVE PRIVADA RSA, en PEM (PKCS#1 o PKCS#8)
    userId: string;
    expirationDate?: string;
}
```

El SDK la valida así (de `service-user.js`, verbatim):

```js
if (!key.key || !key.keyId || !key.userId) {
    throw new JikuError('jiku/auth: the service account key is missing key, keyId or userId; it does not look ' +
        'like a Zitadel machine user key');
}
...
this.#privateKey = createPrivateKey(key.key);
```

**El campo se llama `key` a secas.** Ese es el nombre que la lista de `redact` tiene que cubrir, y es
un nombre peligrosamente genérico: una ruta `*.key` puede colisionar con campos legítimos llamados
`key` en otros contextos. Es un riesgo aceptado y anotado en T1 — redactar de más en un log es
recuperable; redactar de menos una clave privada RSA no lo es.

El token, del mismo módulo: `token()` devuelve un `string` y la respuesta OAuth trae `access_token`.
`currentToken()` devuelve `this.#tokens?.access_token ?? ''`.

#### Technical Details

**Architectural Context References:**

- **ADR-006 — Implementation Rules:** "MUST NOT loguearse nunca: credenciales (IMAP, key JSON, token,
  creds de NATS), tráfico IMAP crudo, el cuerpo del mail (`body`), el contenido de un adjunto". Esta

- **ADR-006 — qué SÍ se loguea:** "Cada mail procesado MUST dejar al menos una línea de log con su

- **ADR-005:** el campo `key` de la key JSON **es la clave privada RSA**. Es el dato más sensible del
  servicio.
- **Integration Points → "La key del machine user":** la forma exacta
  `{ type?, keyId, key, userId, expirationDate? }`, verificada en el SDK instalado. Los nombres de la
  lista salen de ahí, no de una suposición.
- **Convención `logging`:** `censor: '[REDACTED]'`, paquetes `pino` + `pino-pretty` (dev only).
- **Convención `dockerfile`:** `pino-pretty` como `devDependency` (criterio 2).
- **Convención `_base`:** constantes globales en `SCREAMING_SNAKE_CASE`, archivo en `kebab-case`.

**Files to Create/Modify:**

- `package-lock.json` (modificar — resultado de `npm install`)
- `src/shared/log-redaction.ts` (crear)

**Implementation Notes:**

- **Sintaxis de `redact.paths` de Pino, que condiciona toda la lista.** El comodín `*` matchea **un
  solo nivel**. Una ruta con `*` al principio (`'*.token'`) cubre `{ auth: { token } }` pero **no**
  cubre `{ token }` en la raíz, ni `{ a: { b: { token } } }` a dos niveles. Por eso cada entrada va
  duplicada: la forma con comodín y la forma en raíz. **Verificar esto contra la versión instalada
  durante la implementación** — es exactamente la clase de detalle donde una suposición razonable
  produce una lista que parece proteger y no protege.
- **Si Pino de esta versión soporta comodines profundos** (`'**.token'` o equivalente), preferirlos y
  simplificar la lista. Si no, la duplicación es el precio y hay que dejarlo comentado para que nadie
  la "limpie" después.
- **Sobre `'*.key'` y `'key'`, el riesgo aceptado:** `key` es un nombre genérico y puede colisionar con
  campos legítimos llamados `key` en otros contextos (una clave de un mapa, un identificador). La
  consecuencia de la colisión es que un campo inocuo aparezca como `[REDACTED]` — molesto, y

**Implementation Notes:**

- **Forma del helper de captura.** Pino escribe a cualquier objeto con un método `write(str)`. La
  forma más simple es un sink que acumula strings y expone las líneas parseadas:

  ```ts
  export interface LogCapture {
    readonly stream: pino.DestinationStream;
    lines(): Record<string, unknown>[];
    raw(): string[];
  }
  ```

  **`raw()` es imprescindible**, no un extra: el criterio 5 exige afirmar que la línea **no contiene**
  la subcadena del secreto, y esa aserción se hace sobre el string crudo. Sobre el objeto parseado no
  se puede detectar un secreto que se filtró en un campo inesperado.

- **Cuidado con el buffering de Pino.** Según cómo se construya el destino, las escrituras pueden no
  ser síncronas. Si las líneas no aparecen inmediatamente, usar `pino.destination({ sync: true })`
  sobre el sink, o forzar el flush. **Verificarlo temprano**: un test que lee `lines()` antes del flush
  pasa vacío y "verde", que es el peor modo de falla de una suite de seguridad.

- **TS-14 y TS-17 son tests que leen el código fuente.** Implementarlos con `readFile` sobre `src/`
