**El árbol de decisión del tick (post S-032), que es lo que se verifica:**

```
for por UID (descarga → \Seen → normalize)
  route = routeMail(mail, config.ruteo)
  ├─ intencion 'alta'        → destino = await lookupTicket({ space, slug, logger })   ← ANTES de los adjuntos
  │    ├─ found              → procesarAdjuntosDelMail → requirements.new → creados += 1
  │    │                       → recordThreadEntry({ space, messageId, requirementId, logger })
  │    ├─ consultable        → warn { messageId, motivo: 'slug_no_mapeado', slug } 'mail descartado'; descartados += 1
  │    └─ !consultable       → warn { messageId, motivo: 'slug_no_consultable', slug } 'mail descartado'; descartados += 1
  ├─ intencion 'comentario'  → hilo = await lookupThread({ space, referenceIds, logger })  (nunca consulta el slug)
  │    ├─ found              → adjuntos (+ reuso S-029) → requirements.{id}.comment (visibilityLevel 'public')
  │    │                       → comentados += 1 → recordThreadEntry(del Message-Id de la RESPUESTA)
  │    ├─ consultable        → warn { messageId, motivo: 'hilo_desconocido' } 'mail descartado'
  │    └─ !consultable       → warn { messageId, motivo: 'es_respuesta' } 'mail descartado'
  └─ motivo 'sin_slug'       → warn { messageId, motivo: 'sin_slug' } 'mail descartado'
finally → logger.info({ ingestados, parseados, creados, descartados, fallidos, comentados }, 'tick completado')
```

### Testing (convención `testing`, custom del servicio)

Reglas que aplican directamente (verbatim de `docs/architectures/jiku-email-tickets/conventions/testing.md` §Rules):

- **One shared NATS container per suite, started in `globalSetup`.** Never start a container in
  `beforeAll` per file, and never inside an `it`.
- **Never add a database container, a migration step, or a seed dataset.** This service has no
  database.
- **Do not mock the bus.** Integration tests use the real NATS container via
  `Client.fromConnection()`.
- **Import the NATS client from `@gravadigital/jiku/nats`, never from `nats`.** […] This holds in
  test code exactly as it holds in production code.
- **Double only at the boundary:** IMAP through the `MailSource` interface, the presigned `PUT`
  through a `fetch` stub. Never mock this service's own domain functions.
- **Every SDK error class handled in production code has a test** that asserts the diagnosis it
  produces.
- **Mail fixtures are real `.eml` bytes**, never hand-constructed parsed objects.
- Tests must not depend on host env vars or external services. Everything is started or doubled by
  the test setup.
- `describe` names the unit under test; `it` names the scenario.
- **No wall-clock sleeps to wait for a condition.**

**Excepciones autorizadas y vigentes** a "un contenedor por suite" (cada una con su razón escrita en
su helper): `test/bus/auth-helpers.ts` (`--auth`, el compartido no puede tenerlo) y
`test/infra/kv/helpers.ts` (`-js` + `JIKU_KV`, el compartido no tiene JetStream). Esta story agrega
**una tercera con la misma forma** (story §Infraestructura de test): un NATS con JetStream y
**usuarios con permisos estáticos**, para CA-6 caso 3. Va con **tag `nats:2.11-alpine`** para no
entrar en el conteo de `shared-container.test.ts`, en el `beforeAll` de **un solo archivo**.

**Mails en los tests del tick:** las suites del KV (`e2e-kv.test.ts`, `tick-propiedades-kv.test.ts`)
construyen el RFC 822 **inline como `Buffer`** (`mailNuevo()`, `mailRespuesta()`,
`mailSlugNoMapeado()`, `mailSinSlug()`), que sigue siendo bytes reales parseados por `mailparser`.
Esta story usa la misma forma.

### Hallazgos verificados al planificar (no estaban en la story)

1. **Gran parte de CA-5, CA-6 (caso 1), CA-8 y CA-10 ya está implementada y verde desde S-032.**
   `e2e-kv.test.ts` tiene el ciclo encadenado (TS-31/32/33) y el arranque sin bucket y contra
   JetStream apagado (TS-34, TS-37, TS-38); `tick-propiedades-kv.test.ts` tiene la redacción
   (TS-1 a TS-8), los dos orígenes de `hilo_desconocido` (TS-16, TS-18, TS-19, TS-20, con el TS-17
   del TTL **ya borrado**), los contadores (TS-27 a TS-30), la idempotencia (TS-51 a TS-53) y el
   dedup (TS-54 a TS-56). **Esta story no los reescribe**: los conserva (se mapean en la cobertura) y
   agrega **sólo lo que falta**, que es lo que enumera la sección "Lo que se agrega" de cada tarea.
2. **El rechazo de permisos del servidor nunca se probó contra un servidor real, ni en el SDK.**
   `jiku-ts/test/integration/kv.test.ts` dice en su cabecera *"What these cannot show is the
   PERMISSION boundary: test/nats.conf enforces none"*, y el `JikuKVPermissionDenied` de
   `jiku-ts/test/kv.test.ts` se construye con un `PermissionViolationError` fabricado. CA-6 caso 3 es
   **la primera vez** que esa ruta corre contra un `nats-server` real. Se verificó en el código que
   **debería** funcionar: `@nats-io/nats-core` (`protocol.js` `processError()` →
   `muxSubscriptions.handleError()`) rechaza el request en vuelo cuyo `requestSubject` coincide con
   el `subject` del `-ERR 'Permissions Violation for Publish to "…"'`, y el SDK
   (`kv.js` `#transportError()`) lo convierte en `JikuKVPermissionDenied` con el subject rechazado y
   `requiredKVPermissions(instance)` en el mensaje. **Ver Hallazgo 4 si no ocurre.**
3. **El mensaje del SDK para un bucket sin `allow_direct` CONTIENE la palabra "grant"**
   (`"…granting it lets every identity read every other's entries. Do not grant it. Fix the bucket
   instead…"`, `kv.js` `checkKVStream()`). Por eso *"ninguna mención de grants"* (CA-6 caso 2) se
   afirma sobre el **texto del conector** (`error.message`, el `msg` del `fatal`), sobre la
   **ausencia del campo `subject`** y sobre `diagnosis !== 'kv_sin_permisos'` — **no** sobre la línea
   serializada entera, cuyas `causes` traen el texto del SDK que justamente dice *no* agregar grants.
   Es el mismo criterio que ya usa `space.test.ts` TS-24 (`message` sin `/grant|permis/i`). Una
   aserción `raw not /grant/` sobre toda la línea fallaría sin que el conector esté mal.
4. **Si el servidor real entrega el rechazo como timeout y no como violación**, el diagnóstico sería
   `desconocido` (`JikuError` de timeout) tras `timeoutMs`. Eso **no** es un bug del conector (su
   clasificación por clase es correcta) sino del SDK o de `nats-core`. Regla para el implementador:
   **no relajar el test a `desconocido`, no reclasificar por texto en `errors.ts`** (ADR-002 lo
   prohíbe) y **no tocar el SDK**: dejar el test con la expectativa de CA-6, marcarlo con `it.fails`
   **sólo** si se confirma este caso, con un comentario que cite este hallazgo, y reportarlo en el
   resumen de la implementación como hallazgo para los dueños del SDK. Para que la falla sea rápida
   y legible, el cliente de ese test se construye con `timeoutMs: 2_000` (`ClientOptions.timeoutMs`).
5. **El README tiene más prosa del mecanismo viejo que la que nombra CA-11.** Además de la
   precondición 8 (fila y aclaración con los dos `nats kv add`) y la sección *"El Mapa de Tickets vive
   en un bucket KV del bus"* (líneas ~216-252), quedan: la línea ~276 (*"se leen una sola vez al
   arrancar, igual que el Mapa de Tickets"* — el mapa ya no se lee al arrancar), la ~282 (*"vive en un
   bucket KV del bus"*), la ~315 (*"se carga con `nats kv put` sobre el bucket, y el conector lo
   sigue en caliente"*) y la ~319 (*"tres líneas JSON … la del Mapa de Tickets cargado desde el KV"*;
   la tercera línea real es `'espacio KV abierto'`, `src/startup.ts`). Todas son *"la explicación del
   `watch()`"* que CA-11 hace desaparecer, así que entran en la Task 1.
6. **El encabezado del README dice "Las ocho precondiciones, a cargo de U-02"** y CA-11 exige que la
   8 diga que **no la crea U-02**. No es contradictorio si se lee "a cargo" como "verificar antes de
   desplegar"; la Task 1 lo deja explícito en la fila (U-02 la **verifica**, el deploy de Jiku la
   **crea**) en vez de cambiar el título, que anclan otros casos de `deployment-docs.test.ts`.
7. **`test/story-028-docs.test.ts` corta la Parte 2 por el título `'# Parte 2: el alcance del KV'` y
   el siguiente `'# Contraste de capabilities'`** (la Parte 3 queda adentro del corte). La Parte 2
   rehecha **conserva ese prefijo de título** para no romper el corte; y el caso de capabilities
   exige que `test/infra/kv/e2e-watch-tick.test.ts` figure en el documento, lo que sigue siendo cierto
   porque el cierre de REQ-005 **conserva su historia** (CA-13).
8. **Para leer "todas las claves que escribió" (CA-3) sin el `KV` del SDK** (que no lista), el lado
   del test usa la API de JetStream sobre la conexión **cruda y sin restricciones** del contenedor:
   `$JS.API.STREAM.INFO.KV_JIKU_KV` con cuerpo `{"subjects_filter":"$KV.JIKU_KV.>"}` devuelve
   `state.subjects` (subject → cantidad), y `$JS.API.STREAM.MSG.GET.KV_JIKU_KV` con
   `{"last_by_subj":"<subject>"}` devuelve `message.seq`. Con `max_msgs_per_subject: 1` la cantidad
   siempre es 1, así que **"ninguna clave cambió" se afirma por la secuencia**, no por la cantidad.
   Son operaciones estándar del API de JetStream que este repo todavía no usa: el implementador las
   verifica contra el contenedor al escribir el helper (si `subjects_filter` no devolviera
   `state.subjects` en `nats:2.11-alpine`, el fallback es `$JS.API.STREAM.MSG.GET` por cada subject
   esperado, sin listar).
9. **Lo que escribe `nats kv del`** es un mensaje en el **mismo subject** con el header
   `KV-Operation: DEL` (el SDK hace lo mismo en `delete()`, `kv.js` línea ~211), y `get()` del SDK
   devuelve `undefined` ante ese marcador (`kv.js` ~190). Con `deny_delete: true` el stream admite el
   marcador (es un write, no un borrado de mensaje). El lado del test lo replica con
   `connection.request(subject, Empty, { headers })` y `headers()` de `@gravadigital/jiku/nats`.

#### ADR-001: Worker único sin persistencia propia

- **Decisión:** un proceso, sin base de datos, el `\Seen` de IMAP como **única** idempotencia,
  procesamiento secuencial, sin reintento. El estado vive en un almacén **del bus** (no es
  persistencia propia).
- **Implementation Rules (verbatim):**
  - El proyecto MUST ser un único proceso Node.js sin servidor HTTP: no expone puerto, no tiene
    framework web, no define rutas
  - El proyecto MUST NOT declarar dependencias de acceso a base de datos: `pg`, `sequelize`,
    `sequelize-typescript`, `typeorm`, `prisma`, `knex` o equivalentes
  - El proyecto MUST NOT declarar `@aws-sdk/client-s3` ni ningún cliente de storage con credenciales
  - El proyecto MUST NOT persistir estado en disco: sin archivos de estado, sin SQLite, sin caché en
    disco, sin volumen montado de escritura
  - El único mecanismo de deduplicación MUST ser el flag `\Seen` de IMAP, aplicado con
    `messageFlagsAdd` por UID
  - Un mensaje MUST marcarse `\Seen` en el mismo paso en que se descarga y parsea, antes de publicar el
    comando
  - Un mensaje que no se pudo descargar MUST NOT marcarse `\Seen` (así el próximo tick lo reintenta)
  - Un comando fallido MUST NOT reintentarse: se loguea y se descarta el mail
  - El procesamiento MUST ser secuencial: un mail a la vez, un tick a la vez, sin `Promise.all` sobre
    mails ni sobre ticks
  - Los tres módulos internos (Ingesta, Ruteo, Publicación) MUST comunicarse por llamada de función
    dentro del proceso, sin transporte intermedio
  - El despliegue MUST correr **exactamente 1 instancia** por casilla de mail
- **Cómo aplica:** CA-7 verifica que un mail descartado por `slug_no_consultable` **quedó `\Seen`**
  (no se reintenta) y que el tick siguiente se recupera **sin reconstruir nada**; CA-9 verifica que el
  pico sigue siendo de un mail a la vez.

#### ADR-002: Consumir el SDK oficial `@gravadigital/jiku` como cliente del bus

- **Decisión:** el conector no implementa el protocolo; usa el SDK, una conexión por proceso, y
  maneja los errores por las clases del SDK.
- **Implementation Rules (verbatim):**
  - El cliente del bus MUST ser `@gravadigital/jiku` en rango `^1.0.0`
  - El proyecto MUST NOT declarar `nats` como dependencia directa
  - El conector MUST NOT construir subjects a mano: el subject se arma con `client.command()`, nunca con
    concatenación de strings
  - El conector MUST NOT armar ni parsear envelopes del protocolo a mano
  - El conector MUST NOT fijar `inboxPrefix` por su cuenta: lo fija el SDK siempre
  - La identidad MUST construirse con `ServiceUser.fromKeyFile()` — no con un token obtenido a mano ni
    con un JWT armado en el conector
  - `connect()` MUST llamarse **exactamente una vez** al arrancar el proceso, y el cliente resultante
    MUST conservarse por toda la vida del proceso. Prohibido conectar por mail o por tick
  - El `user-id` del subject MUST salir de `auth.userId` (derivado de la key), **nunca** de una variable
    de entorno
  - La configuración del bus MUST leerse con `loadConfig()` del SDK, no redeclarando los defaults a mano
  - El timeout MUST quedar en el default del SDK (**15000 ms**). MUST NOT bajarse — ver
    [ADR-006](ADR-006-observabilidad-por-logs.md)
  - `onTokenError` MUST estar registrado y MUST loguear el fallo del refresh como `error` sin terminar
    el proceso
  - El runtime MUST ser Node.js **≥ 22.12** (el `engines` floor del SDK es parte de su superficie
    pública: subirlo es un major)
  - El proyecto MUST usar **ESM** (`"type": "module"`): el SDK es ESM-only
  - Los errores del bus MUST manejarse por las clases del SDK (`JikuPermissionDenied`, `JikuFailure`,
    `JikuTimeout`, `JikuNoEndpoint`, `JikuInvalidRequest`), no inspeccionando strings de mensaje
- **Cómo aplica:**
  - Los tests importan el cliente crudo **sólo** de `@gravadigital/jiku/nats` (también `headers`).
  - Las reglas sobre subjects son del **código de producción**: el lado del test que hace de U-02 sí
    arma `$KV.JIKU_KV.<clave completa>` a mano, **a propósito**, porque eso es exactamente lo que
    hace `nats kv put` y es lo que CA-1 quiere probar (que lo que escribe un operador es lo que el
    conector lee). Ese armado vive **sólo en `test/`**.
  - El `timeoutMs: 2_000` del cliente de CA-6 caso 3 es del **cliente de test** (`Client.fromConnection`),
    no del conector: la regla del timeout de 15000 ms es del código de producción y no cambia.
  - El diagnóstico es por clase (`instanceof`): ver Hallazgo 4 sobre qué **no** hacer si el servidor
    no entrega la violación.

#### ADR-004: Resolver el proyecto con un KV del bus y no usar el plano de lectura

- **Decisión de fondo (no cambia):** el proyecto se resuelve contra un mapa `slug → projectId` que el

- **Implementation Rules vigentes en el texto (verbatim), con la reformulación de REQ-008 que manda:**

  | Regla vigente en el texto de la ADR | Reformulada por REQ-008 (lo que se verifica) |

#### ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito

- **Implementation Rules que tocan esta story (verbatim):**
  - MUST NOT loguearse nunca: credenciales (IMAP, key JSON, token, creds de NATS), tráfico IMAP crudo, el
    cuerpo del mail (`body`), el contenido de un adjunto
  - **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado.
    Ningún mail termina sin rastro
  - Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`,
    `sin_message_id`, `no_parseable`, `hilo_desconocido`) *(REQ-008 agrega `slug_no_consultable`;
    S-034 enmienda el texto)*
  - Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para
    cargarlo)
  - Cada tick MUST emitir una línea con los seis contadores: `ingestados`, `parseados`, `creados`,
    `descartados`, `fallidos`, `comentados`
  - El timeout del comando MUST quedar en **15000 ms** (el default del SDK). **MUST NOT bajarse**
- **Cómo aplica:** CA-6 verifica que cada causa de arranque sale con **su** `diagnosis` y no manda a
  revisar el sistema equivocado (G-05); CA-7/CA-10 que `slug_no_consultable` suma en `descartados`
  **sin un séptimo contador**; CA-8 que ningún log nuevo lleva el valor crudo de una entrada y que
  `kvPrefix` es el único dato nuevo del espacio. **Invariante 22 del PRD:** no se loguean nunca
  credenciales, tráfico IMAP crudo, el cuerpo del mail, el contenido de un adjunto **ni el texto de un
  comentario**.
