# Story Plan: S-014 (jiku-email-tickets) - Los cinco motivos de descarte en el tick

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-014](../stories/S-014.cinco-motivos-descarte-en-el-tick.md)
- **Service:** jiku-email-tickets
- **Summary:** Cablear `routeMail()` (S-013) en el punto del tick donde hoy el mail se descarta sin consumidor, emitir una única línea `warn 'mail descartado'` por cada uno de los cinco motivos (con el slug **sólo** en `slug_no_mapeado`), contar los cinco como `descartados` (nunca `fallidos`), y corregir el `catch` de `normalize()` para que `MissingMessageIdError` pase de `fallidos` a `descartados` distinguiendo por clase, no por texto.

## Architectural Context

### Tech Stack

- **Lenguaje:** TypeScript (Node ≥ 22.12), `strict: true`, `noUncheckedIndexedAccess: true`, `target: ES2022`.
- **Runtime:** Node.js, worker sin HTTP ni base de datos (ADR-001).
- **Logging:** Pino, vía `createLogger()` (`src/shared/logger.ts`) con redacción estructural (`src/shared/log-redaction.ts`).
- **Testing:** Vitest. Sin containers: dominio puro + integración en memoria (`MailSource` doblado), igual que S-010/S-011.
- **Sin dependencias npm nuevas.**

- **Patrón:** el tick (`src/domain/ingesta/tick.ts`) es el único punto que compone `ingesta` + `ruteo` +

  es pura y nunca loguea; el tick decide qué hacer con el resultado.
- **Error handling:** distinción por clase (`instanceof`), nunca por texto de mensaje — mismo criterio
  que el resto del servicio (ver convención `error-handling` y el comentario de `MissingMessageIdError`).
- **Logging:** objeto de contexto primero, mensaje estático después; el mensaje `'mail descartado'` es
  el mismo literal que ya usa `normalize()` para `sin_message_id` — no se inventa un mensaje nuevo.

### Relevant ADRs

**ADR-006: Observabilidad por logs estructurados a stdout, con el origen del rechazo explícito**

- **Decision:** Logs estructurados a stdout, JSON en producción. Cada mail procesado deja al menos una
  línea de log con su resultado. Un descarte MUST loguear `messageId` y el motivo; un descarte por slug
  no mapeado MUST incluir el slug buscado.
- **Implementation Rules** (verbatim, las que aplican a esta story):
  - Los logs MUST ir a **stdout**. MUST NOT configurarse ningún transport de archivo, en ningún entorno.
  - El formato MUST ser **JSON en producción**.
  - MUST NOT loguearse nunca: credenciales, tráfico IMAP crudo, **el cuerpo del mail** (`body`), el
    contenido de un adjunto.
  - **Cada mail procesado MUST dejar al menos una línea de log** con su `messageId` y su resultado.
    Ningún mail termina sin rastro.
  - Un descarte MUST loguear `messageId` y el **motivo** (`sin_slug`, `slug_no_mapeado`, `es_respuesta`,
    `sin_message_id`, `no_parseable`).
  - Un descarte por slug no mapeado MUST incluir **el slug buscado** (es el dato que hace falta para
    cargarlo).
  - Cada tick MUST emitir una línea con los cinco contadores: `ingestados`, `parseados`, `creados`,
    `descartados`, `fallidos`.

**ADR-002: SDK oficial del bus** — citado por la story como el precedente de "manejo por clase, no por
texto" para distinguir errores. Esta story aplica el mismo criterio a `MissingMessageIdError`: el `catch`
de `normalize()` distingue con `instanceof MissingMessageIdError`, nunca parseando `err.message`.

### Flow Context

### Integration Points

**Contrato de `routeMail()` (S-013)** — `src/domain/ruteo/route-mail.ts`:

```ts
export function routeMail(
  mail: Pick<IncomingMail, 'referenceIds' | 'recipient'>,
  config: Pick<RuteoConfig, 'ticketMap' | 'subaddressPrefix'>,
): RouteResult
```

- Es **síncrona** (no devuelve `Promise`), **pura** (nunca lanza, nunca loguea).
- Orden de evaluación interno (el tick NO reimplementa esto, sólo reporta el resultado):
  1. `referenceIds.length > 0` → `{ ok: false, motivo: 'es_respuesta' }` (sin `slug`).
  2. `recipient` sin forma de subaddress o slug vacío → `{ ok: false, motivo: 'sin_slug' }` (sin `slug`).
  3. Slug con forma válida pero ausente del `ticketMap` → `{ ok: false, motivo: 'slug_no_mapeado', slug }`
     (el **único** motivo que lleva `slug`).
  4. Resuelto → `{ ok: true, projectId: number, slug: string }`.

**Tipos de `src/shared/motivo-descarte.ts`** (copiados verbatim — son el contrato exacto a usar en el tick):

```ts
export type MotivoDescarte =
  | 'no_parseable'
  | 'sin_message_id'
  | 'es_respuesta'
  | 'sin_slug'
  | 'slug_no_mapeado';

export type RouteResult =
  | { readonly ok: true; readonly projectId: number; readonly slug: string }
  | { readonly ok: false; readonly motivo: MotivoDescarte; readonly slug?: string };
```

`slug?` es opcional-ausente, no `string | undefined`: `'slug' in result` debe ser `false` quando el motivo
no es `slug_no_mapeado`. Esto ya lo garantiza `routeMail()`; el tick sólo debe **propagar** la key
condicionalmente al armar el objeto de log (`...(result.slug !== undefined ? { slug: result.slug } : {})`),
nunca escribir `slug: undefined` a mano.

**Contrato de `normalize()` (S-008)** — `src/domain/ingesta/normalize.ts`:

```ts
export async function normalize(raw: Buffer, logger: Logger): Promise<IncomingMail>
```

- Si `parsed.messageId === undefined`: **ya loguea** `logger.warn({ motivo: 'sin_message_id' },
  'mail descartado')` y lanza `MissingMessageIdError`. **El tick NO debe volver a loguear este caso** — la
  línea ya existe (CA-3 exige UNA sola línea).
- Si `simpleParser` lanza por cualquier otro motivo (mail no parseable): la excepción se propaga tal cual,
  sin log propio de `normalize()`. Ese es el caso `no_parseable` que el tick debe loguear con el `uid`
  (comportamiento YA existente en `tick.ts`, líneas 116-126 actuales — no cambia).

**Clase `MissingMessageIdError`** — `src/domain/ingesta/errors.ts`:

```ts
export class MissingMessageIdError extends AppError {
  readonly code = 'SIN_MESSAGE_ID';
  readonly httpStatus = 500;
  constructor() { super('El mail no tiene header Message-Id: se descarta.'); }
}
```

La clase YA EXISTE. El tick debe importarla y usar `instanceof MissingMessageIdError` en su `catch`.

**`REDACT_PATHS` (`src/shared/log-redaction.ts`)** — relevante para CA-5:

- Incluye `'key'` y `'*.key'` (protege la clave privada RSA del machine user). **El campo del slug se
  llama `slug`, nunca `key`** — si se llamara `key`, el valor saldría `[REDACTED]` en producción sin
  fallar y sin avisar. `messageId`, `motivo` y `slug` están explícitamente fuera de `REDACT_PATHS`
  (comentario al final del archivo: "ADR-006 exige explícitamente que esos campos SÍ se logueen").
- También incluye `'body'`, `'*.body'`, `'text'`, `'*.text'`, `'html'`, `'*.html'`, `'content'`,
  `'*.content'` — el cuerpo del mail nunca debe aparecer en la línea de descarte (CA-14), y aunque el tick
  no lo incluya de todas formas, la redacción es la defensa estructural si algo lo agregara por error.

## Tasks

### Task 1: Cablear `routeMail()` en el punto del descarte, con su log y su conteo

**Status:** Completed

#### Description

Invocar `routeMail(mail, config.ruteo)` dentro del loop de `runTick()`, en el punto donde hoy el mail
normalizado se descarta sin consumidor (comentario actual: *"`mail` se descarta aca: no se acumula en
ningun array del tick... No hay consumidor"*). Cuando el resultado es `{ ok: false, ... }`, emitir la
línea `warn` de descarte con el `messageId`, el `motivo`, y el `slug` sólo si está presente en el
resultado, e incrementar `counters.descartados`. Cuando el resultado es `{ ok: true, ... }`, por ahora no
hacer nada más (el alta es S-015): el mail se descarta igual, sin publicar, y `creados` sigue en 0.

Esta tarea es la primera integración real de `ingesta` + `ruteo`, deliberadamente sin publicación en el
alcance — permite verificar CA-6 (nada se crea) sin que un bus de por medio enmascare el resultado.

#### Acceptance Criteria

1. Dentro del `try` que envuelve `normalize()`, después de `counters.parseados += 1`, se invoca
   `routeMail(mail, config.ruteo)` de forma síncrona (no `await`, `routeMail` no es async).
2. Si el resultado es `{ ok: false, motivo, slug? }`: se loguea
   `logger.warn({ messageId: mail.messageId, motivo, ...(slug !== undefined ? { slug } : {}) },
   'mail descartado')` — objeto primero, string estático `'mail descartado'` después.
3. La key `slug` está presente en el objeto de contexto **si y sólo si** `result.slug !== undefined`
   (nunca `slug: undefined` explícito).
4. `counters.descartados += 1` se incrementa en la rama de descarte; `counters.fallidos` **no** cambia
   para este camino.
5. La línea `'mail procesado'` (con `resultado: 'normalizado'`) que hoy se emite incondicionalmente tras
   `normalize()` se reordena o condiciona de forma que **no** se emite una línea adicional para un mail
   descartado (CA-3 exige UNA sola línea de descarte, no una de "procesado" + otra de "descartado").
6. Si el resultado es `{ ok: true, projectId, slug }`: no se loguea nada nuevo en esta story (la línea
   del alta es de S-015) y no se incrementa ningún contador adicional; `creados` permanece en el literal
   `0` del `finally`.
7. El objeto se descarta tras el ruteo: no se acumula en ningún array, ni el `IncomingMail` ni el
   `RouteResult`, entre iteraciones del loop.
8. El `finally` del tick sigue emitiendo la línea de métricas con `descartados: counters.descartados`
   (dejar de usar el literal `0` actual para `descartados` en la línea `'tick completado'`).

**Implementation Notes:**
- El punto exacto es el comentario actual (líneas ~110-116 de la versión leída durante la planificación):

  counters.parseados += 1;
  logger.info({ messageId: mail.messageId, resultado: 'normalizado' }, 'mail procesado');

  'normalizado'` no debe emitirse para ese mail (ya fue "normalizado" pero el resultado real es un

  éxito del ruteo, o eliminarla en este alcance si S-015 la reintroduce con el alta — decisión de
  implementación, pero el test TS-1/TS-2/TS-3 (una sola línea `warn`) es el criterio de aceptación real.
- `mail.referenceIds` y `mail.recipient` son los únicos campos que `routeMail()` necesita del
  `IncomingMail` ya normalizado (`Pick<IncomingMail, 'referenceIds' | 'recipient'>`).

### Task 2: Corregir el `catch` de `normalize()`: `MissingMessageIdError` pasa a `descartados`

**Status:** Completed

#### Description

El `catch` que envuelve `await normalize(raw.source, logger)` hoy cuenta **todo** fallo como `fallidos`,
incluyendo `MissingMessageIdError` — que ya existe como clase (S-008) precisamente para distinguir este
caso, y que hoy el tick no usa. Esta tarea corrige esa rama: `instanceof MissingMessageIdError` incrementa
`descartados`; cualquier otro error (`no_parseable`) sigue incrementando `fallidos`, sin cambios en su
comportamiento actual (línea `'mail no se pudo normalizar'` con el `uid`, sin `messageId`).

#### Acceptance Criteria

1. El `catch` importa y usa `MissingMessageIdError` de `#domain/ingesta/errors.js`.
2. `if (cause instanceof MissingMessageIdError) { counters.descartados += 1; } else { counters.fallidos
   += 1; }` — la variable capturada del `catch` se nombra explícitamente (hoy es `catch { ... }` sin
   binding; debe pasar a `catch (cause) { ... }` para poder inspeccionar la clase).
3. Para el caso `MissingMessageIdError`, **no** se emite una línea de log adicional desde el tick: la
   línea `'mail descartado'` con `motivo: 'sin_message_id'` ya la emitió `normalize()` antes de lanzar
   (CA-3: una sola línea agrupable, ya existente).
4. Para cualquier otro error (`no_parseable`), el comportamiento **no cambia**: se sigue incrementando
   `fallidos` y logueando `logger.warn({ uid }, 'mail no se pudo normalizar')` — sin `messageId` (no se
   conoce en este punto de fallo).
5. El bucle continúa con el siguiente UID en ambos casos (ninguna rama relanza ni aborta el `for`).
6. El mail queda `\Seen` en ambos casos (ya se marcó antes de `normalize()`, sin cambios — CA-8 de S-010).

#### Technical Details

**Architectural Context References:**
- ADR-002 (citado por la story): distinción "por CLASE de error, no por mensaje" — mismo criterio ya
  aplicado en otras partes del servicio (ver comentario de `MissingMessageIdError` en `errors.ts`).
- Convención `error-handling`: nunca parsear el texto de un error para decidir comportamiento; usar la
  jerarquía de clases (`AppError` y sus subclases).
- El comentario ya presente en `TickCounters` (`tick.ts` líneas 18-24) queda desactualizado tras esta
  story y debe actualizarse: ya no es cierto que "esta story no distingue el descarte por Message-Id
  faltante de cualquier otro fallo" — ahora sí lo hace.

**Files to Create/Modify:**
- `src/domain/ingesta/tick.ts` — el bloque `catch` dentro del loop (líneas ~116-126 de la versión leída
  durante planificación), y el comentario JSDoc de `TickCounters` que describe el comportamiento actual
  (desactualizarlo rompería la propiedad de que los comentarios documentan el código real).

**Implementation Notes:**
- El helper `extractMessageIdIfAny()` actual siempre devuelve `undefined` — sigue siendo correcto: ni
  `MissingMessageIdError` ni un fallo de parseo genérico exponen un `messageId` recuperable (el propio

- No confundir con la línea `warn` que emite `normalize()` internamente (`motivo: 'sin_message_id'`,
  **sin** `messageId` tampoco, por la misma razón: el mail no lo tiene). Son dos líneas distintas en
  puntos distintos del código — la de `normalize()` es la única para este camino; el tick no debe
