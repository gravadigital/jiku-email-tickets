# Story Plan: S-012 (jiku-mail-connector) - Configuración del Mapa de Tickets, prefijo y placeholders

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-012](../stories/S-012.configuracion-mapa-tickets-prefijo-placeholders.md)
- **Service:** `jiku-mail-connector`
- **Summary:** Declara las cinco variables del ruteo en `src/config/schema.ts`, carga y valida el
  Mapa de Tickets **dentro de la validación del schema** —para que sus fallos entren en la **misma
  lista única** de fail-fast que los del bus y los de IMAP—, y expone el bloque `ruteo` entero y
  normalizado (`ReadonlyMap<string, number>`) en `AppConfig`. Es la primera story de REQ-003 y la que
  aterriza el **cambio de comportamiento** respecto de REQ-002: el Mapa de Tickets pasa a ser
  **requerido**.

**Lo que esta story NO hace, y conviene tener claro para no invadir S-013/S-015:**

- **No** extrae el slug del `recipient` ni hace ningún `map.get()` (eso es S-013).
- **No** arma ningún payload ni usa los placeholders (eso es S-015).

**Estrategia de testing:** Vitest. Los tests de configuración son **unitarios y puros**: pasan objetos

prueba el compositor y por eso monta el entorno del proceso con su helper `withEnv()` y lo restaura
en un `finally`). Para el archivo del mapa, los tests escriben archivos temporales reales — es el
filesystem, no un doble: `readFileSync` es la operación bajo prueba.

### La restricción de `createEnv` — LEER ESTO ANTES DE ESCRIBIR CÓDIGO

**Esta es la parte del plan que decide si la story cumple o no CA-3, y es contraintuitiva. Está
verificada empíricamente contra `@t3-oss/env-core@0.13.11` y `zod@4.4.3` instalados en este repo,
no inferida de la documentación.**

`createEnv({ server: envSchema })` **no valida un `z.object()`**. `envSchema` es un **diccionario
plano de shapes**, y la librería lo recorre con `parseWithDictionary()`, validando **cada clave por
separado** y **acumulando todos los issues** antes de invocar `onValidationError` **una sola vez**:

```js
// node_modules/@t3-oss/env-core/dist/standard.js — el recorrido real
function parseWithDictionary(dictionary, value) {
  const result = {}; const issues = [];
  for (const key in dictionary) {
    const propResult = dictionary[key]["~standard"].validate(value[key]);
    if (propResult.issues) { issues.push(...); continue; }   // <- NO corta: sigue con las demás
    result[key] = propResult.value;
  }
  if (issues.length) return { issues };
  return { value: result };
}
```

**Consecuencia 1 — la buena.** Toda validación que viva **en una clave** (incluido un `.transform()`
que lea el filesystem y emita issues con `ctx.addIssue()`) se agrega correctamente con las demás. Un
`IMAP_HOST` ausente y un `TICKET_MAP_FILE` roto salen **juntos, en una sola lista**. Esto es
exactamente lo que CA-3 exige, y sale gratis por construcción.

**Consecuencia 2 — la trampa.** El diseño de la story y del REQ dicen *"un `superRefine` sobre el
objeto parseado"* para la regla de las dos fuentes. **Eso, escrito de la forma obvia, rompe CA-3.**
`createEnv` acepta un escape hatch, `createFinalSchema(shape, isServer)`, que permite construir un
schema único sobre todo el entorno; pero si ese schema es un `z.object(shape).superRefine(...)` —o
un `.check(...)`— **el refinement NO corre cuando alguna clave del objeto ya falló**, porque Zod
corta ahí. Verificado:

```
// z.object(shape).superRefine(reglaDeDosFuentes), entorno = { B: 'b' }
// (falta A, y falta el mapa en las dos fuentes)
CASE1 ISSUES: [[["A"],"Invalid input: expected string, received undefined"]]
             ^^^ el issue del mapa NUNCA aparece — CA-3 incumplido, en silencio
```

`.check()` se comporta igual. **No uses ninguno de los dos para la regla de las dos fuentes.**

**La forma que sí cumple — el híbrido, y es lo que hay que implementar:**

1. **Las seis formas de mapa mal formado viven en las claves**, como `.transform()` con
   `ctx.addIssue()` sobre `TICKET_MAP` y sobre `TICKET_MAP_FILE`. Se agregan solas.
2. **Sólo la regla de las dos fuentes** (que es genuinamente cross-field: mira dos claves a la vez)
   vive en `createFinalSchema`, implementada como un **Standard Schema propio** que corre el
   `z.object(shape).safeParse()` **y además** la regla, y **concatena las dos listas de issues**
   siempre — sin cortar.

Verificado sobre el repo, con las cinco situaciones que los criterios exigen:

```
CA-3 (falta IMAP_HOST + archivo del mapa roto):
  [[["IMAP_HOST"],"expected string, received undefined"],[["TICKET_MAP_FILE"],"no es JSON parseable"]]
  ^^^ LAS DOS, en una sola lista, en un solo formato
CA-1 (ninguna de las dos fuentes):  [[["TICKET_MAP"],"el Mapa de Tickets es requerido"]]
CA-2 (las dos fuentes a la vez):    [[["TICKET_MAP"],"se declararon las dos fuentes"]]
CA-7 caso 6 (archivo inexistente):  [[["TICKET_MAP_FILE"],"no se puede leer el archivo"]]
CA-8 (mapa vacío declarado):        arranca; el Map resuelto es []
Fuente archivo, ya normalizada:     [ [ 'alfa', 42 ], [ 'beta', 7 ] ]   (de {"Alfa":42,"beta":7})
```

**Forma de referencia del wrapper** (no es copiar-pegar literal, es la estructura que tiene que
tener; los mensajes y nombres finales salen de `EXPECTATIONS`):

```ts
createFinalSchema: (shape) => {
  const object = z.object(shape);
  return {
    '~standard': {
      version: 1,
      vendor: 'jiku-mail-connector',
      validate(value: Record<string, unknown>) {
        const parsed = object.safeParse(value);
        const issues = parsed.success
          ? []
          : parsed.error.issues.map((i) => ({ message: i.message, path: i.path }));

        // La regla cross-field corre SIEMPRE, haya fallado o no una clave. Ese "siempre" es
        // literalmente CA-3: con un superRefine de Zod este bloque no se ejecutaria.
        const inline = value.TICKET_MAP !== undefined;
        const file = value.TICKET_MAP_FILE !== undefined;
        if (!inline && !file) issues.push({ message: '...', path: ['TICKET_MAP'] });
        if (inline && file) issues.push({ message: '...', path: ['TICKET_MAP'] });

        if (issues.length > 0) return { issues };
        return { value: parsed.data };
      },
    },
  };
},
```

**Dos notas de tipos, para que no sorprendan:**

- `createFinalSchema` cambia el tipo de retorno de `createEnv` a
  `StandardSchemaV1.InferOutput<TFinalSchema>`. El `Env` inferido tiene que seguir saliendo del
  schema (CA-9 de S-002 sigue vigente, y hay un test de propiedad que lo afirma): mantené
  `z.infer<z.ZodObject<typeof envSchema>>` como fuente del tipo, y tipá el wrapper para que su
  output sea ese mismo tipo.
- `createEnv` devuelve un `Proxy` sobre el objeto parseado. Un `Map` pasa por el `Proxy` sin
  problema (verificado), pero **no lo serialices**: `JSON.stringify(new Map(...))` da `{}`, lo que
  puede hacer parecer que el mapa se perdió cuando está intacto. Es una trampa de depuración, no un
  bug.

### Relevant ADRs

#### ADR-004: Resolver el proyecto con un KV local y no usar el plano de lectura

**Decisión:** El proyecto se resuelve contra un KV local —el Mapa de Tickets— cargado a mano, con el
`projectId` como valor. El conector no consulta el bus: sólo escribe.

| Aspecto | Definición |
|---|---|
| Estructura | `slug` (string, único, minúsculas) → `projectId` (int) |
| Fuente | Variable de entorno o archivo montado |
| Momento de carga | **Al arrancar.** Sin recarga en caliente en v1 |
| Mapa vacío | **Estado válido**: el worker arranca y descarta todo con log |
| Mapa mal formado | **Fail-fast**: el worker no arranca |
| Validación del `projectId` | **Ninguna.** No se verifica que el proyecto exista |

**Implementation Rules (copiadas verbatim; las que esta story ejecuta van marcadas):**

- **[S-012]** El Mapa de Tickets MUST cargarse desde variable de entorno o archivo montado, **al arrancar**
- **[S-012]** El mapa MUST validarse al arrancar. Un mapa mal formado (JSON inválido, `projectId` no entero, dos
  entradas con el mismo `slug`) MUST provocar **fail-fast**: el proceso no arranca
- **[S-012]** Un mapa **vacío** MUST ser aceptado como estado válido: el worker arranca y descarta todo con log
- **[S-012]** Las claves del mapa MUST normalizarse **a minúsculas** al cargarlo
- *(S-013)* El slug extraído del mail MUST normalizarse **a minúsculas** antes de buscarlo (comparación en
  minúsculas **en las dos puntas**)
- **[S-012]** El valor de cada entrada MUST ser el `projectId` entero de Jiku. MUST NOT ser el nombre del proyecto
  ni su slug
- **[S-012]** El conector MUST NOT verificar contra Jiku que el `projectId` exista antes de publicar
- **[S-012]** El conector MUST NOT publicar en el plano de consultas del bus (`jiku-queries.*`)
- *(S-013)* El slug MUST extraerse del `recipient` con la regex `^<prefijo>\+([^@]+)@`, case-insensitive, con el
  prefijo configurable (default: `tickets`)
- *(S-013)* El `recipient` MUST tomarse de `Delivered-To`, con `To` como **único** fallback
- *(S-014)* Un mail sin match de slug MUST descartarse con log, sin crear nada
- *(S-014)* Un slug sin entrada en el mapa MUST descartarse con log que **nombre el slug buscado**
- **[S-012]** El mapa MUST vivir sólo en memoria: MUST NOT escribirse a disco ni cachearse fuera del proceso

**Lo que ADR-004 le exige a esta story y no está en los criterios:** el `subaddressPrefix` es
**configurable con default `tickets`** porque la regla del slug lo nombra así. La story declara la
variable; quien la consume es S-013.

#### ADR-001: Worker único sin persistencia

Relevante por lo que **prohíbe**: no hay base de datos, ni volumen de escritura, ni migraciones. El
`Map` del mapa vive **sólo en memoria**. Si en algún momento la implementación parece necesitar
escribir el mapa a algún lado (cache, archivo derivado, snapshot), está mal: ADR-004 lo prohíbe
explícitamente en su última regla.

#### ADR-006: Observabilidad por logs

Relevante por una sola razón en esta story: **el fallo de configuración no tiene síntoma diferido**.
Un worker sin healthcheck que arranca con el mapa roto y lo descubre en el primer mail es
exactamente el fallo que el fail-fast existe para evitar. Es la misma justificación con la que
`POLL_CRON` se valida con `cron.validate()` en el arranque en vez de en `cron.schedule()`.

### Integration Points

**Ninguno externo.** Esta story no habla con el bus, ni con Zitadel, ni con IMAP, ni con `core`. Su
única frontera con el mundo es **el filesystem local**: un `readFileSync` sobre la ruta de
`TICKET_MAP_FILE`, sincrónico y una sola vez al arrancar.

**Por qué sincrónico, declarado:** el schema de `createEnv` no admite refinements asincrónicos
(`ensureSynchronous()` lanza si un validador devuelve una `Promise` — está en el código de la
librería, citado arriba). Y bloquear el event loop en el arranque es gratis: no hay ningún trabajo
concurrente todavía.

### Code Conventions

Del `_base` de Node (convención siempre activa) y de las dos custom del servicio:

| Elemento | Convención | Ejemplo en este repo |
|---|---|---|
| Archivos | `kebab-case` | `log-redaction.ts`, `publish-errors.ts` |

| Tipos / interfaces | `PascalCase`, sin prefijo `I` | `AppConfig`, `ImapConfig`, `PollConfig` |

**Imports (convención custom `module-imports`):** subpath imports nativos de Node declarados en
`package.json#imports` (`#config/*`, `#domain/*`, `#infra/*`, `#shared/*`), **con extensión `.js`
explícita** incluso desde `.ts`. Orden: librerías externas (`node:*`, npm) → imports absolutos del
proyecto (`#...`) → relativos (`./...`), separados por línea en blanco.

**Variables de entorno (convención `env-config`):** todas se declaran y validan en un solo lugar.
`process.env` **nunca** se lee fuera de `src/config/env.ts` — y hay un test de propiedad que lo
afirma escaneando `src/` (CA-12).

**Comentarios (`_base`):** por default, ninguno. Se comenta **sólo el porqué** cuando no es obvio.
Este módulo en particular comenta deliberadamente cada decisión contraintuitiva, justamente para que
no se revierta — y el escáner de propiedades **quita los comentarios antes de buscar**
(`stripComments()` en `test/shared/source-scan.ts`), así que un comentario que mencione
`process.env` no rompe el test.

## Task 1: Carga y validación del Mapa de Tickets en `src/config/schema.ts`

**Status:** Completed
**Categoría:** Data / Logic
**Dependencias:** Ninguna

### Descripción

Declarar las cinco variables nuevas en `envSchema` y, para las dos del mapa, implementar la carga y
validación **como `.transform()` de cada clave**, de modo que sus fallos entren como issues más en la
misma lista que produce `parseWithDictionary()`.

Es el núcleo de la story y donde vive la lógica.

### Criterios de Aceptación de la tarea

- `envSchema` declara **veintidós** claves: las diecisiete actuales más `TICKET_MAP`,
  `TICKET_MAP_FILE`, `SUBADDRESS_PREFIX`, `PLACEHOLDER_TITLE`, `PLACEHOLDER_BODY`.
- Los tres defaults salen de **constantes exportadas** (`DEFAULT_SUBADDRESS_PREFIX`,
  `DEFAULT_PLACEHOLDER_TITLE`, `DEFAULT_PLACEHOLDER_BODY`), siguiendo el precedente de
  `DEFAULT_IMAP_PORT` / `DEFAULT_POLL_CRON`.
- `TICKET_MAP` y `TICKET_MAP_FILE` son ambas `.optional()` a nivel de clave. **Su obligatoriedad es
  cross-field y se resuelve en T2** — declararlas requeridas acá haría imposible la regla "una de las
  dos".
- El `.transform()` de `TICKET_MAP` parsea el JSON y construye el `Map` normalizado.
- El `.transform()` de `TICKET_MAP_FILE` **lee el archivo con `readFileSync`** y después aplica
  exactamente la misma validación. Las dos fuentes comparten **una sola función de parseo** — dos
  copias divergen.
- Los seis casos de mapa mal formado emiten `ctx.addIssue({ code: 'custom', ... })` y devuelven
  `z.NEVER`. **Nunca `throw`**: un throw dentro del transform escapa de `createEnv` y rompe la lista
  única.
- La detección de duplicados corre **sobre las claves originales, antes de construir el `Map`**,
  contando cuántas colapsan en cada slug normalizado (`trim().toLowerCase()`).
- La limitación de `JSON.parse` con claves idénticas queda **documentada en un comentario** del
  código, con la razón (CA-6). No se finge cumplida.
- El módulo **no menciona `process.env`**.

### Detalles Técnicos

**Forma de la función de parseo compartida** (una sola, usada por las dos fuentes):

```
parseTicketMap(raw: string, ctx): ReadonlyMap<string, number> | typeof z.NEVER
  1. JSON.parse dentro de un try   -> falla: issue 'no es JSON parseable'
  2. z.record(z.string(), z.number().int().positive()).safeParse(parsed)
                                   -> falla: issue 'no es un objeto de pares slug -> projectId'
  3. por cada clave: slug = clave.trim().toLowerCase()
       slug === ''                 -> issue 'slug vacio'
       contar colisiones por slug
  4. algún slug con count > 1      -> issue 'slugs duplicados'
  5. new Map(entries.map(([k, v]) => [k.trim().toLowerCase(), v]))
```

**Verificado en este repo** (`zod@4.4.3`) que los cinco casos producen el issue esperado y que el
paso 2 rechaza tanto `2.5` como `0`, `-3`, `"42"`, `[1,2,3]` y `"alfa"`.

**Sobre el orden de los pasos 3 y 4:** los issues de slug vacío y de duplicado se pueden acumular en
la misma pasada, pero **cortá después del primero de cada tipo**. Emitir un issue por cada slug
duplicado inunda la lista única con ruido cuando el mapa es grande; uno que nombre el problema
alcanza, y el operador va a mirar el mapa entero igual.

**Sobre `readFileSync`:** encoding `'utf8'`, dentro de un `try`. El `catch` cubre a la vez el archivo
inexistente, el ilegible y el directorio — los tres son "no se puede leer" y no hace falta
distinguirlos: el operador arregla lo mismo en los tres casos. **El mensaje del issue no incluye la
ruta ni el contenido** (los mensajes salen de `EXPECTATIONS`, que no interpola nada — ver T3).

**ADRs y reglas que aplican:** ADR-004 (normalización a minúsculas al cargar; el valor es el
`projectId` entero; el mapa vive sólo en memoria; sin validación contra Jiku); ADR-001 (nada se
escribe a disco).

**Convenciones:** constantes en `SCREAMING_SNAKE_CASE` y exportadas; comentarios sólo del porqué,
sobre las decisiones contraintuitivas (que son varias acá: por qué el transform y no un refine, por
qué la detección de duplicados no puede correr sobre el objeto parseado, y la limitación de
`JSON.parse`).

## Task 4: El bloque `ruteo` de `AppConfig`

**Status:** Completed
**Categoría:** API (contrato interno)
**Dependencias:** Task 1, Task 2

### Descripción

Declarar la interfaz `RuteoConfig` y componer el bloque `ruteo` en `loadAppConfig()`, con el mismo
criterio con que `AppConfig` ya expone `imap` y `poll`.

### Criterios de Aceptación de la tarea

- `AppConfig` tiene **trece** campos; el nuevo es `ruteo: RuteoConfig`.

  string`, `placeholderTitle: string`, `placeholderBody: string`.

  los defaults. Mismo criterio que los bloques `imap` y `poll`.
- El orden de `loadAppConfig()` **no cambia**: `loadEnvFromProcess()` primero, `loadConfig()` del SDK
  después.
- Los doce campos preexistentes conservan exactamente sus valores.

### Detalles Técnicos

La fuente del `ticketMap` es **una de las dos claves**, la que esté declarada:

```ts
// Exactamente una de las dos esta definida — T2 lo garantiza, no hace falta re-validar aca.
ticketMap: env.TICKET_MAP ?? env.TICKET_MAP_FILE,
```

**No re-valides la regla de las dos fuentes en el compositor.** Si llegaste hasta acá, T2 ya la
verificó; una segunda comprobación sería la duplicación de validación que ADR-004 rechaza en otro
contexto y que acá simplemente se desincroniza.

**El comentario de redacción del bloque nuevo:** `AppConfig` ya lleva un comentario largo explicando
por qué ningún punto de log emite el objeto completo. El bloque `ruteo` **entra bajo esa misma
regla** y agrega una razón propia — el mapa es la topología comercial del despliegue, los
`projectId` de todos los clientes habilitados. Escribilo en el mismo lugar y con el mismo tono que el
comentario de `imap`.

**Nota de tipo:** `ReadonlyMap` en la interfaz es lo que impide que un consumidor haga `.set()` sin
darse cuenta. El `Map` real que el schema construye es mutable; el tipo de la interfaz es lo que lo
sella. No hace falta un `Object.freeze` — no congelaría el `Map` de todas formas.
